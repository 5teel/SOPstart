## Project Description

SafeStart is a multi-tenant SaaS progressive web app that helps blue-collar tradespeople and inspectors follow Standard Operating Procedures (SOPs) on-site. Organizations upload existing SOP documents (Word/PDF), AI parses them into structured mobile-friendly procedures, and workers walk through them step-by-step on their phones — with photo capture, completion tracking, and supervisor sign-off.

**Target market:** New Zealand industrial/manufacturing organizations (glass manufacturing, machine shops, etc.) with 50-500 SOPs across departments.

## Architecture

### Route Structure (App Router)
- `(auth)/` — Login, sign-up, invite, join flows
- `(protected)/` — Authenticated routes behind middleware
  - `dashboard/` — Worker/supervisor home
  - `sops/` — SOP library browse, `[sopId]` detail, `[sopId]/walkthrough` step-by-step mode
  - `activity/` — Completion records, supervisor review (`[completionId]`)
  - `admin/sops/` — SOP management, upload, `[sopId]/review`, `[sopId]/assign`, `[sopId]/versions`
  - `admin/team/` — Team/org member management
- `api/sops/` — REST API routes (parse, publish, assignments, sections, download-url, parse-job)
- `~offline/` — Offline fallback page

### Key Directories
- `src/actions/` — Server actions (auth, sops, assignments, completions, versioning)
- `src/components/sop/` — SOP-specific UI (walkthrough, steps, photos, sections, search)
- `src/components/activity/` — Completion/activity UI
- `src/components/admin/` — Admin panel UI
- `src/components/layout/` — Shared layout (nav, sidebar, etc.)
- `src/components/providers/` — React context providers
- `src/hooks/` — Custom hooks (useAssignedSops, useCompletions, useOnlineStatus, usePhotoQueue, useSopDetail, useSopSync, useNotifications)
- `src/stores/` — Zustand stores (completionStore, network, walkthrough)
- `src/lib/parsers/` — File parsing pipeline (extract-docx, extract-pdf, gpt-parser, image-uploader, ocr-fallback)
- `src/lib/offline/` — Offline infrastructure (db, photo-compress, query-persister, sync-engine)
- `src/lib/supabase/` — Supabase client variants (client, server, admin, middleware)
- `src/lib/validators/` — Zod schemas (auth, sop)
- `src/types/` — TypeScript types (sop, auth, database.types)

### Data Model (core types)
- **Sop** — Top-level SOP record (title, status, version, source file, confidence scores, OCR flag)
- **SopSection** — Sections within an SOP (type, title, content, sort_order, confidence, approved flag)
- **SopStep** — Individual steps within sections (text, warning/caution/tip, tools, time estimate, photo_required)
- **SopImage** — Images attached to SOPs/sections/steps (stored in Supabase Storage)
- **ParseJob** — Tracks async AI parsing pipeline (queued → processing → completed/failed)
- Statuses: SOP lifecycle is `uploading → parsing → draft → published`

### Multi-tenant & Roles
- Organization-scoped data with RLS policies
- Roles: Worker, Supervisor, SOP Admin, Safety Manager
- SOP assignment by role/trade

### Offline Strategy
- Service worker via Serwist for asset caching
- Dexie (IndexedDB) for offline SOP data
- Photo queue with compression for deferred upload
- Sync engine for reconnection reconciliation

## Pathways Map Maintenance (`journeys.ts`) — GSD triggers

`src/lib/journeys/journeys.ts` is the **single source of truth** for the `/pathways` UX-flow map: the page renders entirely from it, and the "All screens" panel is read live from the route tree and **flags any screen no pathway covers**. It only stays accurate if it's updated alongside the flows it describes. The GSD framework will NOT do this automatically — Claude MUST keep it current at these points (mirrors the `## Learnings` GSD-trigger model):

1. **`/gsd-plan-phase`** — if a phase adds, removes, or reroutes any user-facing screen or flow, add the `journeys.ts` edit as an explicit task in PLAN.md.
2. **`/gsd-execute-phase`** — whenever a `page.tsx` route is added/removed/renamed, or a navigation / redirect / server-action flow changes, update `journeys.ts` in the **same commit** (add or extend the relevant `Journey`; keep `route` values real so coverage + deep-links work).
3. **`/gsd-verify-work` / `/gsd-code-review`** — confirm `/pathways` → "All screens" shows **0 not-mapped** for the phase's new routes. A flagged screen = an unfinished pathways update. (Open the page, or grep `src/lib/journeys/journeys.ts` for each new route.)
4. **`/gsd-new-milestone` / roadmap** — when scoping new personas or surfaces, add their pathways so the map reflects intended flows, not just shipped ones.

**Rule of thumb: a new route or changed flow is not "done" until `journeys.ts` reflects it** (and `src/lib/uat/tests.ts` is updated when the change is worth team review). This rule is mirrored in `.planning/codebase/CONVENTIONS.md` so GSD planning/execution agents pick it up from project intel.

## Learnings

_Log mistakes, errors, and patterns discovered during development sessions here._

- **[2026-07-07] The builder canvas renders EXCLUSIVELY from sop_sections.layout_data — any route that inserts sections without also emitting layout_data ships an invisible SOP** — AI-prompt drafts (and every non-docx upload) wrote sections + sop_steps but layout_data NULL, so the Phase 26 builder opened "Nothing here yet" over a fully-drafted SOP; only DOCX parses ever ran `parsedSopToPerSectionLayoutData`. Rule: sections + steps rows are the WORKER-view data; the ADMIN builder needs the converter + `materializeJunctionsForLayout` + layout_data write as a mandatory trio wherever sop_sections are inserted. Fixed for parse + ai-prompt routes (`47290b0`) + prod backfill script (`scripts/backfill-section-layouts.ts`, only touches SOPs where every section lacks layout). All five section-inserting routes now emit the trio (video routes swept same day). (Prod bug report, builder 1ae63606)

- **[2026-07-05] Best-effort pipelines that upsert ALL columns null-clobber good data on partial failure — omit failed steps from the payload (PostgREST upsert only updates provided columns)** — Running `backfill-agent-metadata.mjs` locally without `VOYAGE_API_KEY` overwrote all 5 prod SOP embeddings with NULL and printed 100% OK: `synthesizeSop` wrote `embedding: null` + `tags: []` unconditionally, so any fail-open step (missing key, exhausted Anthropic credits) destroyed previously-good columns while `last_synthesis_status='ok'` claimed success. Two rules: (1) in a per-step try/catch pipeline, a FAILED step's fields must be conditionally spread out of the write (`...(x !== null && {x})`) — distinguish "step failed" (null) from "step succeeded, found nothing" (empty); status must say `partial`, not `ok`. (2) The Anthropic 400 "credit balance too low" failure mode is invisible in fail-open pipelines — empty tags/summary across ALL rows with status ok = billing/infra failure, not "no metadata" (same family as 2026-06-02 VERIFY_MODEL rot). Fixed in `3a4202b` + source-contract regression test. (Phase 26.5 first prod backfill)

- **[2026-07-05] New cookie-less API routes (cron/webhook/bearer-auth) MUST be exempted in `src/lib/supabase/middleware.ts` or the session middleware 307-redirects them to /login before the handler's own auth ever runs** — Phase 26.5's synthesis-sweep route shipped green (8/8 auth spec, tsc, build) but the first live `POST` returned the login page HTML: `updateSession` treats every non-public path without a session cookie as a browser needing login. The specs read the route source directly, so middleware interception was invisible — same "tested in isolation, never exercised end-to-end" class as the 2026-06-24 Deepgram WS learning. Rule: any route authenticated by header (not cookie) needs (1) an exemption in the middleware's public-route list and (2) a source-contract test asserting the exemption exists (added to `synthesis-sweep-auth.spec.ts`). Fixed in `314e148`. (Phase 26.5 first live call)

- **[2026-07-05] SECURITY DEFINER RPCs that accept an org/tenant id PARAMETER are PostgREST-exposed cross-tenant read holes — REVOKE EXECUTE from anon/authenticated unless identity derives from auth.uid() inside the function** — Phase 26.5's `match_sop_agent_metadata` similarity RPC took `p_organisation_id` as a caller-supplied parameter (service-role callers in `similarity.ts` self-enforce org-scope, so the parameter felt safe). But every Postgres function is auto-exposed at `POST /rest/v1/rpc/<name>` to ANY authenticated user, who can pass any org's UUID — the 00030-precedent SECURITY DEFINER helpers were only safe because they derive identity from `auth.uid()` internally, never from a parameter. This was live on prod (migration pushed in-wave) until code review caught it; fixed in 00041 by `REVOKE EXECUTE FROM PUBLIC, anon, authenticated; GRANT TO service_role` (verified live via `has_function_privilege`). Rule: a SECURITY DEFINER function is EITHER self-scoping via auth.uid() and client-callable, OR parameter-trusting and locked to service_role — never both. Sibling of the recurring 2026-06-15/2026-06-26 service-role class, new surface (RPC instead of admin-client). Same review-fix pass (`3448d56`): ~7 legacy `src/actions/*` files still decode JWTs with raw `atob` (2026-06-26 Base64URL crash class) — flagged in `26.5-REVIEW-FIX.md` for a dedicated `parseJwtPayload` sweep. (Phase 26.5 code review)

- **[2026-07-03] Full-engine swap over a FROZEN data contract is safe + cheap when the contract is UI-framework-agnostic — and behavioural parity tests are what make it provable** — Phase 26 replaced the entire Puck editor with a bespoke inline editor (18 block types, 16 field editors, tiered inserter, smart ghosts, Konva annotation) and it verified PASS 8/8 with **zero regressions to the parse→AI-review→verify→publish spine**. Two reusable patterns: (1) **The `layout_data` JSON + `sop_section_blocks` junctions + `block_provenance` were the real contract, not Puck.** Because the parser, validators, AI reviewer, publish gate, and autosave never imported Puck, "replace Puck" reduced to a `type→component` registry + a `content[]` reducer + re-wiring 4 UI bindings — and the KEEP files (publish route, `useSelectionSync`, parse pipeline, reviewer orchestrator) stayed **git-diff-empty against the phase parent**, which is the cleanest possible preservation proof. When contemplating a big framework swap, first check whether the framework is actually in the data path or just the render path — if render-only, the swap is far smaller than it looks. (2) **Every RE-WIRE/RE-IMPLEMENT carried a BEHAVIOURAL parity test naming the old behaviour it replaced** (real publish route → 400 `unverified_blocks`; real `ReviewerFlagsPanel` via QueryClientProvider; react-dom/server render harnesses shelled out via `tsx` subprocess because Playwright's JSX transform can't render real components) — this is exactly the discipline the [2026-06-05] source-contract learning demanded, and it's why no dead feature slipped through the way 21.6's empty `onClick` did. Also: a pre-phase **golden fixture captured in Wave 0** (deterministic converter output, since GPT parse isn't byte-reproducible) gave R6 byte-equivalence a real baseline. And when deleting a source-of-truth file that a test reads live (`puck-config.tsx` fed the field-map P14 parity test), snapshot its data into a committed fixture first so the guarantee survives the deletion. (Phase 26 — v5.0 opener)

- **[2026-06-24] Deepgram streaming WS: a grant JWT must use the `bearer` subprotocol, NOT `token` — and the whole WS path was a latent never-run bug** — Phase 22 voice failed at runtime with a generic "WebSocket error" on speak (after the earlier missing-`DEEPGRAM_API_KEY`-on-Railway issue was cleared). Root cause: `deepgram-stream.ts` opened `new WebSocket(url, ['token', access_token])`, but `access_token` is a JWT minted by `/v1/auth/grant`. Deepgram's `Sec-WebSocket-Protocol: token, <x>` only accepts a **raw `DEEPGRAM_API_KEY`**; a temporary/grant JWT must go via the **`bearer`** subprotocol. Verified directly against Deepgram with a Node `ws` repro (read local key → mint grant token → open WS): `['token', rawKey]`→OPEN, `['token', grantJWT]`→HTTP 401 INVALID_AUTH, `['bearer', grantJWT]`→OPEN. The `encoding=opus`/`sample_rate`/`keyterm` params were NOT the cause (`encoding=opus` opened fine with the raw key). Two meta-lessons: (1) this WS path shipped in Phase 12.5 and was **never exercised end-to-end** — only `/api/voice/token` was tested in isolation, so the wrong subprotocol sat latent until Phase 22 first ran it on a real device (same source-contract blind spot as the [2026-06-05]/[2026-06-08] learnings). (2) To debug an opaque browser "WebSocket error", reproduce the handshake server-side with the `ws` package + the real key — Deepgram returns a precise `err_code`/`err_msg` on the HTTP upgrade that the browser's `onerror` hides. Fixed in `6ca51ff` (`'token'`→`'bearer'`). Related same-feature fix `be6a118`: the client collapsed every non-2xx from `/api/voice/token` into one opaque `token_grant_failed` string — propagate the server's specific code (401/503/502) to the UI instead.

- **[2026-06-24] Deepgram streaming with MediaRecorder: send NO `encoding`/`sample_rate` — let the container auto-detect, or you get ZERO transcripts** — Follow-on to the `bearer` fix above: once the WS connected, speaking produced no transcription and no error. `deepgram-stream.ts` built the URL with `encoding=opus&sample_rate=48000` (from `pickRecorderFormat`), but MediaRecorder emits a **containerized** stream (`audio/webm;codecs=opus`, or ogg/mp4). `encoding=opus` tells Deepgram to expect **raw, headerless Opus packets**; given a WebM container it silently fails to decode and returns no Results (socket stays open, no error frame). Fix: omit `encoding` and `sample_rate` entirely for container formats — Deepgram detects codec + rate from the container header. Proven by converting a speech WAV → webm/opus (ffmpeg) and streaming it to Deepgram both ways: `encoding=opus&sample_rate` → 0 transcripts; no-encoding → full transcript. Only set `encoding`/`sample_rate` for genuinely raw PCM (`linear16`, `mulaw`). General Deepgram rule: **containerized audio ⇒ no encoding params; raw audio ⇒ encoding + sample_rate required.** Fixed in `24ea54d`. (Reproduce voice-stream bugs server-side with the `ws` package + ffmpeg-static, both already in node_modules — far faster than device round-trips.)

- **[2026-06-24] Playwright `await import('@/...')` dynamic imports fail in phase22-stubs context — use source-contract assertions or a separate unit project** — The Wave-0 `tests/phase22/intent-classifier.spec.ts` guarded with `fs.existsSync` + `test.skip()` so the dynamic import never executed when the module was absent. When Plan 02 created the module, the guard passed and `await import('@/lib/voice/intent-classifier')` ran — but Playwright's Node.js runner doesn't apply its TypeScript compiler to dynamic `import()` calls the way it does for static imports. Node.js native ESM import sees the `.ts` file with `export` keyword and throws `SyntaxError: Unexpected token 'export'`. Fix: replace dynamic-import unit tests in `phase22-stubs` with source-contract assertions (`fs.readFileSync` + `toContain` on gate ordering, exports, type names), and create real behavioral unit tests in `src/lib/voice/__tests__/intent-classifier.test.ts` under the `phase15-unit` project (which has `testDir: './src/lib/voice/__tests__'` and resolves `@/` via static imports through Playwright's TS compiler). Lesson: dynamic `import('@/...')` in Playwright tests outside `testDir`-scoped projects will fail at runtime. Use static imports or move the test to the right project. (Phase 22-02)

- **[2026-06-27] A pure (sync) export in a `'use server'` file passes `tsc` + unit tests but BREAKS `next build` — "Server Actions must be async functions" — and the phase shipped green** — Phase 23-03 added `computeNextVersionLineage`, a pure sync helper, as an `export` in `src/actions/versioning.ts` (which starts with `'use server'`). Next.js enforces that **every value export of a `'use server'` module is an async function**; a sync export fails `next build` with `x Server Actions must be async functions` the moment the module is imported into a build graph (here via `versions/page.tsx`). It survived because: `tsc --noEmit` does NOT enforce the server-action constraint (only `next build`'s SWC/webpack pass does — same family as the [2026-06-02] "next build scope ≠ tsc scope" learning), the executor self-checks ran `tsc`, and the phase's own 23-07 "bundle check" reported a size without a clean production build — so it only surfaced on the real Railway deploy. Fix: move the pure helper OUT of the action file into a normal module (`src/lib/builder/version-lineage.ts`) and import it back into `versioning.ts`; repoint the unit-test import + its source-contract assertion strings. Rules: (1) `'use server'` files may export ONLY async functions — type/interface exports are fine (erased at compile), but any pure/sync value helper MUST live in a non-server module. (2) A phase is NOT verified until a real `npm run build` (next build) runs clean — `tsc` green is necessary, not sufficient; a "bundle size" number is not proof of a successful build. Run `npm run build` as the final gate before declaring any phase touching `src/actions/*` done. Fixed in `5badb2c`. (Phase 23 Railway deploy)

- **[2026-06-26] JWT org claim decoded with `atob` is wrong (Base64URL ≠ Base64) AND the [2026-06-15] admin-client cross-org pattern recurred — both caught only at code review, not by green stub tests** — Phase 23 code review surfaced two systemic issues across the new AI-field + completions + versioning + roster surfaces. (1) **`atob` on a JWT payload**: the pattern `JSON.parse(atob(token.split('.')[1]))` was copy-pasted into 10+ server callsites to read `organisation_id` from the Supabase access token. `atob` decodes standard Base64, but JWT payloads are **Base64URL** (`-`/`_`, no padding) — it works for ASCII-only claims but throws `InvalidCharacterError` on any claim byte needing `+`/`/`, crashing that action for the user. Fix: one shared `parseJwtPayload()` in `src/lib/supabase/jwt.ts` that maps `-→+`, `_→/`, pads, then `atob`, wrapped in try/catch → `{}`; import everywhere (returns `Record<string, unknown>` so callsites need `as string | undefined` casts). (2) **The [2026-06-15] cross-tenant admin-client hole recurred**: `signOffCompletion` org-scoped the write only inside the `role==='supervisor'` branch, so a `safety_manager` could sign off / mutate another org's completion (admin-client fetch returns any row by id; update filtered only on `id`). Same lesson as 6 weeks earlier — service-role writes MUST self-enforce `row.organisation_id === caller.organisationId` on every path, and add `.eq('organisation_id', …)` to the write. Meta-lesson: all 8 plans shipped GREEN (phase23 stubs + unit + tsc) yet a privilege-escalation hole, a cross-org hole, and silent clone-corruption bugs (section/step ID maps matched by `sort_order`/`step_number` instead of array index → mis-assigned steps when values repeat) all survived to the `gsd-code-review` gate — exactly the [2026-06-05] source-contract blind spot. **Do not skip code review on a phase just because stubs are green; security/correctness logic is invisible to presence-assertion tests.** Fixed in the 23 review-fix pass (CR-01..04, WR-02/03/05/06/07). (Phase 23 code review)

- **[2026-06-15] "Writes via admin server action only" junction tables need the SERVICE-ROLE client in the action — the regular session client gets "new row violates RLS"** — Phase 25's three junction tables (`member_departments`, `block_departments`, `sop_departments`) were created with `SELECT using(true)` and deliberately NO authenticated INSERT/UPDATE/DELETE policy (the 00031 recursion-avoidance pattern: the real gate stays on the parent table). The migration comment said "writes via admin server actions only" — but all three `assign*Departments` actions wrote with the normal session client (`ctx.supabase` from `requireAdmin()`), so every toggle was denied with `42501 new row violates row-level security policy for table "sop_departments"`. Two rules: (1) when a table has no authenticated write policy by design, its server action MUST use `createAdminClient()` (service-role) for the write, not the session client. (2) service-role bypasses RLS, so the action must then enforce org-scoping ITSELF — confirm the parent row (member/SOP/block) is in `ctx.organisationId` and filter the supplied department ids to the org — otherwise you trade an RLS-deny bug for a cross-tenant-write hole. This was systemic across all 3 assigners (rule #5). It shipped green because the phase's runtime DB-write tests were `test.fixme` stubs — the source-contract tests only assert the action EXISTS, never exercise the insert (same blind spot as the [2026-06-05] source-contract learning). Any junction-write action should have at least one runtime test that actually performs the insert as an authenticated admin. Fixed in commit `23c4f0a`. (Phase 25 UAT)

- **[2026-06-15] PostgREST schema-cache staleness after DDL → false "table not found" in post-migration assertions** — Phase 25's `apply-phase25-migrations.mjs` reported 3 of 4 new junction tables MISSING immediately after `supabase db push` SUCCESS, with the error "Could not find the table 'public.block_departments' **in the schema cache**". The tables existed — this is PostgREST error `PGRST205` (its schema cache hadn't reloaded after the DDL), NOT Postgres `42P01` (table genuinely absent). Tells it apart: (1) the phrase "in the schema cache"; (2) `db push` succeeded; (3) the data migration `00036` had already INSERTed into those junctions (so they must exist) and its final null-org `DELETE` ran (count=0 confirmed). Two fixes: (a) reload the cache — `NOTIFY pgrst, 'reload schema';` (run via the Supabase **Management API** `POST /v1/projects/{ref}/database/query` with `SUPABASE_ACCESS_TOKEN`, or the dashboard SQL editor) — Supabase auto-reloads within ~1 min but assertions running instantly after push hit the stale window; (b) to VERIFY existence bypassing PostgREST entirely, query `to_regclass('public.<table>')` through the same Management API (raw SQL, no cache). Also: assertion scripts that probe tables via the supabase-js REST client (`.from('x').select()`) must treat `PGRST205` distinctly from `42P01` — the Phase 25 script spuriously PASSED `departments` (its branch treated any non-42P01 error as a pass) while FAILING the junctions (their branch failed on any error), masking that all four were equally cache-stale. (Phase 25 wave-2 migration apply)

- **[2026-06-08] React #418 hydration mismatch on the builder had TWO causes — invalid `<li>` nesting + `navigator.onLine` read at store module-load** — After the Puck-hook crash (below) was fixed, the Build stage logged `Minified React error #418` (server-rendered text/markup ≠ client) on every load. A non-minified `next dev` render (authenticated Playwright) revealed both causes: (1) **Invalid nesting** — `BuilderTreeRail` wraps each section in `<li>` AND `TreeSectionRow` rendered its own `<li>` inside it → `<li><li>`; the browser relocates the inner `<li>`, so client DOM ≠ server HTML. Fix: `TreeSectionRow` root `<li>` → `<div>` (the outer `<li>` is the real list item). (2) **navigator at module-load** — `stores/network.ts` seeded `isOnline: typeof navigator !== 'undefined' ? navigator.onLine : true`; server has no navigator (→ true) but the client seeds from the real value, so the SAVE pill text diverged on first paint. Fix: default `isOnline: true` (SSR-safe) and sync the real value in `useOnlineStatus`'s effect (`setOnline(navigator.onLine)` — effects are client-only, run AFTER hydration, so no mismatch). General rule: NEVER derive first-render output from `navigator`/`window`/`Date.now()`/`Math.random()` at module-load or in render — seed a stable SSR-safe constant and reconcile in an effect. To diagnose, reproduce in `next dev` (non-minified) — the warning prints the exact `Server: … Client: …` diff and the offending element stack; the minified prod #418 does not. Fixed in commit pushed 2026-06-08 (TreeSectionRow + network + useOnlineStatus).
- **[2026-06-08] Puck editor hooks (`useGetPuck`/`usePuck`) throw if a component renders OUTSIDE `<Puck>` — crashed the entire Build stage** — Phase 21.6's `BuilderTreeRail` and `AddMenu` both call `useGetPuck()`, but they render as siblings of `<main>` (which holds `<Puck>`), i.e. OUTSIDE the provider. `useGetPuck` throws `usePuckGet must be used inside <Puck>` on mount, taking down the whole client tree → Next.js default "This page couldn't load" for EVERY SOP on the admin builder. A code comment even asserted "use useGetPuck (not usePuck) because it renders OUTSIDE <Puck>" — WRONG: *both* Puck hooks require the context. Fix pattern: to dispatch into Puck from a component outside the provider, add a `puck` override (Puck 0.21 `overrideKeys` = header/headerActions/fields/fieldLabel/drawer/drawerItem/componentOverlay/outline/**puck**/preview; `puck` wraps the whole editor UI INSIDE the context), call `useGetPuck()` there, park `dispatch` in a stable `useRef`, and have the outside component invoke it via a callback prop. Keep the override component's identity STABLE (define once via `useMemo([])`) or Puck remounts the editor on every overrides rebuild.
