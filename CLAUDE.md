## Project Description

SafeStart is a multi-tenant SaaS progressive web app that helps blue-collar tradespeople and inspectors follow Standard Operating Procedures (SOPs) on-site. Organizations upload existing SOP documents (Word/PDF), AI parses them into structured mobile-friendly procedures, and workers walk through them step-by-step on their phones — with photo capture, completion tracking, and supervisor sign-off.

**Target market:** New Zealand industrial/manufacturing organizations (glass manufacturing, machine shops, etc.) with 50-500 SOPs across departments.

- **Dev port**: 4200 (`npm run dev`)

## Architecture

### Route Structure (App Router)
- `(auth)/` — Login, sign-up, invite, join flows
- `(protected)/` — Authenticated routes behind middleware
  - `dashboard/` — Worker/supervisor home
  - `sops/` — SOP library browse, `[sopId]` detail, `[sopId]/walkthrough` step-by-step mode
  - `activity/` — Completion records, supervisor review (`[completionId]`)
  - `admin/sops/` — SOP management, upload, `[sopId]/review`, `[sopId]/assign`, `[sopId]/versions`
  - `admin/team/` — Team/org member management
- `api/sops/` — REST API routes (parse, publish, assignments, sections, download-url, parse-job)
- `~offline/` — Offline fallback page

### Key Directories
- `src/actions/` — Server actions (auth, sops, assignments, completions, versioning)
- `src/components/sop/` — SOP-specific UI (walkthrough, steps, photos, sections, search)
- `src/components/activity/` — Completion/activity UI
- `src/components/admin/` — Admin panel UI
- `src/components/layout/` — Shared layout (nav, sidebar, etc.)
- `src/components/providers/` — React context providers
- `src/hooks/` — Custom hooks (useAssignedSops, useCompletions, useOnlineStatus, usePhotoQueue, useSopDetail, useSopSync, useNotifications)
- `src/stores/` — Zustand stores (completionStore, network, walkthrough)
- `src/lib/parsers/` — File parsing pipeline (extract-docx, extract-pdf, gpt-parser, image-uploader, ocr-fallback)
- `src/lib/offline/` — Offline infrastructure (db, photo-compress, query-persister, sync-engine)
- `src/lib/supabase/` — Supabase client variants (client, server, admin, middleware)
- `src/lib/validators/` — Zod schemas (auth, sop)
- `src/types/` — TypeScript types (sop, auth, database.types)

### Data Model (core types)
- **Sop** — Top-level SOP record (title, status, version, source file, confidence scores, OCR flag)
- **SopSection** — Sections within an SOP (type, title, content, sort_order, confidence, approved flag)
- **SopStep** — Individual steps within sections (text, warning/caution/tip, tools, time estimate, photo_required)
- **SopImage** — Images attached to SOPs/sections/steps (stored in Supabase Storage)
- **ParseJob** — Tracks async AI parsing pipeline (queued → processing → completed/failed)
- Statuses: SOP lifecycle is `uploading → parsing → draft → published`

### Multi-tenant & Roles
- Organization-scoped data with RLS policies
- Roles: Worker, Supervisor, SOP Admin, Safety Manager
- SOP assignment by role/trade

### Offline Strategy
- Service worker via Serwist for asset caching
- Dexie (IndexedDB) for offline SOP data
- Photo queue with compression for deferred upload
- Sync engine for reconnection reconciliation

## Pathways Map Maintenance (`journeys.ts`) — GSD triggers

`src/lib/journeys/journeys.ts` is the **single source of truth** for the `/pathways` UX-flow map: the page renders entirely from it, and the "All screens" panel is read live from the route tree and **flags any screen no pathway covers**. It only stays accurate if it's updated alongside the flows it describes. The GSD framework will NOT do this automatically — Claude MUST keep it current at these points (mirrors the `## Learnings` GSD-trigger model):

1. **`/gsd-plan-phase`** — if a phase adds, removes, or reroutes any user-facing screen or flow, add the `journeys.ts` edit as an explicit task in PLAN.md.
2. **`/gsd-execute-phase`** — whenever a `page.tsx` route is added/removed/renamed, or a navigation / redirect / server-action flow changes, update `journeys.ts` in the **same commit** (add or extend the relevant `Journey`; keep `route` values real so coverage + deep-links work).
3. **`/gsd-verify-work` / `/gsd-code-review`** — confirm `/pathways` → "All screens" shows **0 not-mapped** for the phase's new routes. A flagged screen = an unfinished pathways update. (Open the page, or grep `src/lib/journeys/journeys.ts` for each new route.)
4. **`/gsd-new-milestone` / roadmap** — when scoping new personas or surfaces, add their pathways so the map reflects intended flows, not just shipped ones.

**Rule of thumb: a new route or changed flow is not "done" until `journeys.ts` reflects it** (and `src/lib/uat/tests.ts` is updated when the change is worth team review). This rule is mirrored in `.planning/codebase/CONVENTIONS.md` so GSD planning/execution agents pick it up from project intel.

## Learnings

_Log mistakes, errors, and patterns discovered during development sessions here._

- **[2026-08-04] "Route directory is deleted" is not "nothing links to it" — the Phase 30 dead-weight spec asserted the first and the Miller pane shipped a 404 on its PRIMARY CTA** — `SopWorkerBrowser`'s detail pane linked to `/sops/[sopId]/walkthrough`, a route Phase 30 removed when Walk it became `?tab=walk`. `tests/phase30/dead-weight.spec.ts` already had a test named "*/sops/[sopId]/walkthrough route (page + orphan layout) is deleted*" — it checked `fs.existsSync` on the directory and passed, while the app's most important worker action pointed at that exact URL. Internal hrefs are not type-checked (2026-06-08 dead-href class, third instance), so tsc, `next build` and the full suite were all green. Rule: **a deletion guard must assert the absence of REFERENCES, not just the absence of the file** — pair every `existsSync(...).toBe(false)` with a `src/` sweep for links to it. Now mechanical in the same spec (anchor the regex on `/sops/` so `@/stores/walkthrough` imports aren't false positives; mutation-proven both ways). Sibling finding in the same fix: that spec's department-filter assertion pinned the literal `sopDeptMap[sop.id]`, which a same-day refactor renamed — repoint source-contract assertions in the commit that renames what they grep (2026-07-13). Fixed in `09c1b7b`.

- **[2026-08-04] A partially-specified `WITH CHECK` is MORE dangerous than none at all — omitting it inherits the org-scoped `USING`, writing one replaces it** — The RLS audit after the `sops` read hole (below) swept all 36 tenant-owned tables. Five write policies had no `WITH CHECK`; four were **safe**, because Postgres falls back to the `USING` expression when the check is absent, and those `USING` clauses were org-scoped (`sops`, `parse_jobs`, `video_generation_jobs`, `sop_pipeline_runs`). The single hole was the one policy that DID specify a check: `organisation_members.admins_can_update_member_roles` had `USING (organisation_id = current_organisation_id())` but `WITH CHECK (current_user_role() = 'admin')` — so an admin could take a member row in their own org and rewrite its `organisation_id`, pushing a user into another tenant. The check had been written to express one rule ("only admins change roles") and silently discarded the org rule it never mentioned. Rules: (1) **if you write a `WITH CHECK` at all, restate every predicate the `USING` clause carries** — it is a replacement, not an addition; (2) when auditing, "no WITH CHECK" is not a finding by itself, but "WITH CHECK present and weaker than USING" always is; (3) `USING` governs which rows you may TOUCH, `WITH CHECK` governs what a row may BECOME — a tenant column is rewritable unless the check names it. Fixed in migration 00062 (applied live) and generalised into `tests/lint/rls-org-scope.spec.ts`, which parses every migration in order and fails on: an unscoped policy on any table carrying `organisation_id`, a `WITH CHECK` that drops an org predicate its `USING` has, or a table mixing scoped and unscoped SELECT policies. Mutation-proven with a planted probe migration — all three assertions go red, then green when it is removed (a parser-based guard that finds nothing passes vacuously, per [2026-05-25]/[2026-06-05]).

- **[2026-08-04] Postgres OR-combines permissive RLS policies, so ONE unscoped SELECT policy makes every other policy's org check decorative — `sops` leaked 15 of 30 rows to every tenant, and the tell was a WRITE guard firing** — `public.sops` carried four SELECT policies; only `org_members_can_view_sops` had an org predicate. `sops_visible_by_department` was `(all_departments = true) OR NOT EXISTS(sop_departments for this sop) OR sop_in_user_departments(id)` — **no org scope at all** — so its second arm matched *any untagged SOP in any organisation*, and `sops_visible_by_sub_trade` did the same for any SOP without sub-trade tags. Measured live: 15 of 30 SOPs readable by every authenticated user across three orgs, and the admin library rendered 7 foreign-org SOPs to a user with exactly one membership. **The symptom that exposed it was not a security alert but a UX bug**: assigning a department returned "SOP belongs to another organisation" — `assignSopDepartments`'s write guard correctly refusing a row the read path should never have surfaced. Three rules: (1) **a tagging/visibility arm exists to NARROW within a tenant, so it must be conjoined (`org = current_organisation_id() AND (…)`), never added as a sibling policy** — sibling policies are OR'd, and OR only ever widens; (2) when a write guard rejects something the UI just showed the user, suspect the READ path first — the guard is usually right and the list is usually wrong; (3) a `NOT EXISTS(...)` arm ("this row has no tags, so show it") is the highest-risk shape there is, because it matches the *most* rows precisely when data is least curated. Fixed in migration 00061 (applied live, before/after asserted) plus `tests/lint/sops-select-policies-org-scoped.spec.ts`, which walks every migration in order, tracks the LAST definition of each policy name (drops included, per [2026-07-28]), and fails on any surviving `sops` SELECT policy without `current_organisation_id` — mutation-proven by flipping the new `AND` to `OR`. Same class as [2026-07-20] on `sop_observations`, second occurrence: **audit the OTHER tenant-scoped tables for sibling policies whose arms lack an org conjunct.**

- **[2026-08-03] A success panel gated on state that one branch never writes = a feature that silently does nothing — and the plan's own human-verification steps were factually wrong about which code path they exercised** — Phase 40's blocking checkpoint (40-14 Task 3) told the operator to upload "an MP4 larger than 10MB (this forces the resumable TUS path)". Tracing the code showed `startVideoSopUpload` has NO size branch at all — the dropzone and versions-page paths always use TUS; the only 10MB threshold is `VideoPreviewPanel.tsx:151` and it measures the **extracted audio**, not the source video. The operator, having no large SOPs, was blocked on a precondition that didn't exist. Then the upload itself ran to 100% and displayed nothing: `UploadDropzone.tsx`'s success panel renders on `success && uploadedSopIds.length > 0`, and the video branch never called `setUploadedSopIds` while both document branches did — pre-existing (confirmed in `26a8223^`), so plan 40-02 relocated the bug when it extracted the branch rather than introducing it. Every gate the phase ran — tsc, `next build`, 54 phase40 tests, code review, phase verification — reads source; none watch a screen, so a missing state write on a success path is invisible to all of them ([2026-07-14] `--accent-ok` class, third instance). Three rules: (1) **when a plan authors human-verification steps, derive the trigger condition by tracing the branch, not by restating a constant found nearby** — a threshold in a sibling file is not the threshold on your path; (2) when extracting a branch into a shared routine, diff its side-effects against the sibling branches that stayed inline (`setUploadedSopIds` was in both document arms and neither the old nor the new video arm) — an extraction preserves bugs it doesn't inspect; (3) a UI state variable that gates a whole panel deserves a grep for **every** write site the moment any branch is refactored. Fixed in `dd4477c`. (Phase 40 plan 40-14 human checkpoint)

- **[2026-07-29] A "repoint every write path" sweep that enumerates call sites by feature misses the sibling function in the SAME file — and extending a surface onto a hot pattern replicates the pattern's vulnerability** — Phase 40 (DAT-01) repointed six SOP-creating write paths onto `category_slug` and even fixed `uploadNewVersion` to carry it forward, but `cloneSopAsDraft` / `restoreVersionAsNew` — sibling functions in the same `versioning.ts` file — were never in the enumerated list, so every clone/restore silently dropped the category (cascading into wrong cadence, skipped approval chain, dropped collection). Same phase, same file: plan 40-07's new video branch copied the existing TUS-token idiom, which returns `SUPABASE_SERVICE_ROLE_KEY` to the browser — extending a pattern IS shipping a fresh instance of its bug (two Phase-6 instances predated; the phase added a third). Two rules: (1) a column/contract sweep must be keyed on the DATA (grep every `.insert(`/`.update(` on the table, every function returning the row type), not on a planner-enumerated feature list — the miss is always the sibling nobody listed; (2) before extending any existing idiom to a new branch, check whether the idiom itself is on the known-vulnerable list (service-role material in client-reachable returns) — "matches the surrounding code" is not a defense when the surrounding code is the bug. Both caught by code review + phase verification, not the green 1326-test suite. (Phase 40 verification)

- **[2026-07-28] A migration-applier whose fallback applies only ITS OWN migration silently re-drops any later corrective migration — and its "ALL PASS" assertions never noticed, because they didn't pin the restored clause** — Phase 37's `apply-phase37-migration.mjs` fallback applied 00056 alone; 00057 existed precisely to restore the `sop_observation_refs_in_org` conjunct 00056 had dropped, so every re-run of the tool re-opened the cross-tenant write hole while its post-apply assertion group printed green (it checked two conjuncts of the policy's `with_check`, not the restored third). Two rules: (1) an applier script's file list must include every LATER migration that corrects the one it ships — and the apply ORDER is load-bearing, so assert it by index comparison in a spec; (2) a post-apply assertion must pin EVERY security-relevant clause of the object it verifies, cross-checked against the migration SQL itself, or the assertion certifies whatever happens to be live. Sibling finding, same phase (CR-01, the 2026-06-15/07-20 service-role class again): an org-scope predicate was fed the FETCHED ROW's `organisation_id` (attacker-influenced — it's whatever org the supplied UUID belongs to) instead of the session org; any value derived from a client-supplied id is untrusted even when it "obviously" matches. Both caught by phase verification, not the green suite; closed in 37-07/37-08 with positional source-contract guards plus a directory-wide sweep asserting every `src/app/(protected)` page importing the admin client also compares `organisationId`. (Phase 37 gap closure)

- **[2026-07-24] Any CSV export of user-controlled data is a formula-injection surface — RFC-4180 quoting alone is NOT enough** — Phase 35's `generateTrainingCsv()` shipped with correct RFC-4180 quote/comma/newline escaping but no neutralization of leading `=`/`+`/`-`/`@`, while the feature's own UAT script told admins to open the file in Excel and hand it to auditors — a worker email or SOP title like `=HYPERLINK(...)` would execute on open. Quoting and formula-triggering are orthogonal: `csvField()` must ALSO apostrophe-prefix fields starting with a formula trigger and force-quote bare `\r`. Sibling finding, same phase: the derivation ladder's `needs_support` reset hardcoded its floor to `'read'`, fabricating a completion for observed-only workers — a state-machine reset must floor to the actual evidence (`hasCompletion ? 'read' : 'not_started'`), never a constant. Both passed tsc/build/full-suite green and were caught only by the phase code-review gate. Fixed in `1a6fccf` + `81524c7` with unit tests. (Phase 35 code review)

- **[2026-07-20] An RLS SELECT policy's org-wide branch without a role check is an org-wide disclosure hole — and a cross-ORG isolation test will never catch it** — Phase 34's `sop_observations` read policy OR'd `observed_worker_id = auth.uid()` (worker self-read) with `organisation_id = current_organisation_id()` (intended for supervisors/admins) but put NO role check on the org branch, so any plain worker could read every peer's observations + supervisor notes via PostgREST — while the SC-4 runtime proof passed green, because it only probed supervisor sessions across orgs, never a plain-worker session within the same org. Sibling finding, same phase: RLS also silently EMPTIES same-org reads a server action legitimately needs (`listWorkerSopsForPicker`'s `sop_assignments` queries return zero rows for supervisor callers — feature dead for the primary persona, works for admins, so admin-run UAT masks it). Two rules: (1) every RLS branch needs its own positive AND negative runtime probe per role — one probe per policy is not coverage; enumerate (role × own-row/other-row × same-org/cross-org) for the roles that matter. (2) When a session-client server action reads a table on the observed/target user's behalf, check whose rows RLS will actually return — "query runs fine" for an admin caller proves nothing for supervisor/worker callers. Caught by phase code review + verifier, NOT by the green test suite. (Phase 34 verification)

- **[2026-07-18] Worktree checkouts CRLF-normalize files and break `\n`-literal source-contract specs — repo has no `.gitattributes`** — During the Phase 32 review-fix pass, a fresh git worktree checkout re-smudged source files to CRLF, breaking specs that assert exact `\n`-joined literals against `fs.readFileSync` content. Any future worktree-based executor hits this. Fixes: add `.gitattributes` (`* text=auto eol=lf`), or normalize (`content.replace(/\r\n/g,'\n')`) before matching in source-contract specs. Until then: "spec passes on main tree, fails in worktree" = suspect line-ending drift first. (Phase 32 review-fix)

- **[2026-07-14] An undefined CSS custom property renders the element WRONG and fails NOTHING — `background: var(--accent-ok)` made the primary "verify step" button invisible on 48 cards** — `--accent-ok` and `--accent-step` were referenced BARE by six builder components (ReviewStation, NavRow, BuilderStageStepper, OrientationStrip, AddMenu, BuilderTreeRail) but declared in NO stylesheet. CSS resolves an undefined custom property to nothing, so the declaration silently drops: the verify CTA rendered `color:#fff` on a transparent background — white-on-light-grey, invisible — while every other style on the button applied normally. It passed `tsc`, `next build`, ESLint, and the full Playwright suite, because an undefined token is not a build error, not a type error, and not a runtime error. The ONLY reason it went unnoticed for so long is that the single reference which supplied a fallback (`globals.css var(--accent-step, #3b82f6)`) always looked right. Auditing the rest found six more of the same class (`--accent-hazard`, `--accent-mcu`, `--ink-200/400/600`, `--paper-1`): pill text colours silently falling back to `inherit`, missing hairline borders, missing input surfaces. Sibling of the 30-07 undefined `--brand-yellow` publish-CTA bug — that one was also caught by eye, which is the tell that this class has no automated net. Three rules: (1) **a CSS token bug is invisible to every gate the project has — only a human or a screenshot catches it**, so after any UI change, LOOK at the deployed page; green tests prove nothing about whether a control is visible. (2) Never reference `var(--x)` bare unless you have confirmed `--x` is declared — `grep -rn -- "--x:" src/`; prefer `var(--x, <fallback>)` at the callsite when in doubt (a fallback is self-healing). (3) Now enforced mechanically: `tests/lint/no-undefined-css-tokens.spec.ts` fails CI on any fallback-less `var(--x)` that no stylesheet declares (registered in the `phase15-stubs` project regex per the [2026-05-25] unregistered-spec learning; verified discoverable with `--list`). Fixed in `91829b8`. (Check-stage scroll-column pass, builder 203be502)

- **[2026-07-13] A pane that claims to show real content but renders a hardcoded sentence — because the hook fetched the data then threw it away** — The builder's Check stage promised "THE STEP, IN THE APP — this is what the worker will see on their phone" but rendered, for all 48 steps: the block's 60-char preview (already shown verbatim in the left rail) + a canned `This step has been parsed from the source document…` string that was byte-identical on every block. So a 636×550px pane carried ~60 chars of duplicated information and the remainder was whitespace — and there was literally nothing to review against the source pane, defeating the stage's purpose. Root cause was one line: `useVerifyChecklist` SELECTed `snapshot_content` (the full authored block) and then discarded it, keeping only `previewFromSnapshot(...)` — so `ReviewStation` *could not* render the real block even in principle, and the empty space got filled with boilerplate. Fix was ~15 lines with zero new queries: keep (Zod-validated) `snapshot_content` on `ChecklistBlock`, then render via the EXISTING `blockContentToPuckProps()` + `blockKindToPuckType()` + `BLOCK_COMPONENTS` — the same registry the worker read path (`LayoutRenderer`) and the edit host (`BlockEditShell`) already use, so there's no forked renderer to drift. Two rules: (1) **when a UI surface renders placeholder/boilerplate prose where real content belongs, suspect the data layer discarded it — grep the hook's row mapping before redesigning the layout.** Whitespace complaints are often a data-plumbing bug wearing a CSS costume; restyling would have shrunk the box while keeping it meaningless. (2) Before building any block/step preview, check `BLOCK_COMPONENTS` + the `puck-to-block-content.ts` converters — the render path for every block type already exists and is battle-tested; a bespoke preview switch is always the wrong call. Also swept: the per-block "AI safety check — all clear" box (48 repetitions of nothing, each carrying a second RE-RUN AI REVIEWER button duplicating the page header's) now renders only when the block actually has flags. Fixed in `9616dd4`. (Prod UX report, builder 203be502)

- **[2026-07-13] Source-contract guards go stale-RED when the code they grep moves modules — and a red safety guard is a guard that stopped guarding** — Phase 29 factored the publish gate out of `api/sops/[sopId]/publish/route.ts` into `assertPublishGates()` in `src/lib/governance/publish-core.ts` (so the chain-gate divert could reuse the identical checks), but `tests/builder/builder-review-flow.spec.ts` and `tests/phase26/spine-regression.spec.ts` still grepped the ROUTE FILE for the `unverified_blocks` / `status: 400` literals. Both had been failing red — on the publish gate, the safety keystone that stops unverified SOPs reaching workers. The gate itself was fine; only the assertions were pointing at the wrong file. This is the exact failure the [2026-07-13] auth-refactor note predicted ("source-contract specs pin exact guard strings — refactoring the idiom means repointing those assertions in the same commit"), now observed on a second surface. Rules: (1) when you extract a guarded behaviour into a shared module, `grep -rn "<the-literal>" tests/` and repoint every assertion **in the same commit**; (2) prefer guards that assert the behaviour WHERE IT LIVES **plus** that the caller still CALLS it (`toContain('assertPublishGates(')`) — that survives relocation and checks wiring rather than mere token presence (the 2026-06-05 dead-feature class); (3) a persistently-red guard on a safety-critical path is not "a flaky test to fix later" — triage whether the *guard* or the *gate* broke, immediately. - **[2026-05-13] RLS recursion via cross-table existence checks → 500s on every query** — Phase 15 migration 00030 created two policies that recursed: `sops.sops_visible_by_sub_trade` checked `not exists (… from sops_sub_trades)` AND `sops_sub_trades.sops_sub_trades_read_for_org` checked `exists (… from sops)`. Postgres detected `42P17 infinite recursion detected in policy for relation` and PostgREST surfaced it as 500 on ANY query touching `sops` — including unrelated joins like `/sop_assignments?select=…,sops(…)`. Detection: a single RLS migration shouldn't break unrelated queries; if you see broad 500s after adding a policy, suspect cross-policy recursion FIRST. - **[2026-05-15] `unpdf.extractImages` / pdfjs requires a fresh `Uint8Array` per call** — Reusing the same `Uint8Array` view across successive `extractImages(data, p)` calls (or after a prior `getDocumentProxy(data)` call) crashes with `DataCloneError: Cannot transfer object of unsupported type` at `LoopbackPort.postMessage`. pdfjs holds internal worker state on the input ArrayBuffer; the second call hits a structured-clone boundary that rejects the mutated buffer. - **[2026-06-02] Claude Code `isolation="worktree"` branches from the SESSION-START commit, not live `master`** — During Phase 21.5 wave execution, each parallel executor's worktree was created off the commit that was HEAD when the session began (`2f18028`), NOT the orchestrator's current `master` HEAD after prior waves merged.
