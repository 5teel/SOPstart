## Project Description

SafeStart is a multi-tenant SaaS progressive web app that helps blue-collar tradespeople and inspectors follow Standard Operating Procedures (SOPs) on-site. Organizations upload existing SOP documents (Word/PDF), AI parses them into structured mobile-friendly procedures, and workers walk through them step-by-step on their phones — with photo capture, completion tracking, and supervisor sign-off.

**Target market:** New Zealand industrial/manufacturing organizations (glass manufacturing, machine shops, etc.) with 50-500 SOPs across departments.

## Technology Stack

- **Framework**: Next.js 16 (App Router) with React 19
- **Language**: TypeScript 5
- **Styling**: Tailwind CSS 4 (PostCSS plugin)
- **Database/Auth**: Supabase (Postgres, Auth, Storage, RLS policies)
- **State**: Zustand (client stores), TanStack React Query (server state)
- **Offline**: none since Phase 55 (2026-10-03) — the app is online-only; `public/sw.js` is a committed kill-switch that unregisters any previously-installed service worker. Do not reintroduce Serwist/Dexie/idb-keyval.
- **AI Parsing**: OpenAI API (GPT) for document-to-structured-SOP conversion
- **File Parsing**: mammoth (DOCX), unpdf (PDF), tesseract.js (OCR)
- **Forms**: React Hook Form + Zod validation
- **Testing**: Playwright (integration + E2E)
- **Icons**: Lucide React
- **Theme**: next-themes (dark mode default)
- **Dev port**: 4200 (`npm run dev`)

## Architecture

### Route Structure (App Router)
- `(auth)/` — Login, sign-up, invite, join flows
- `(protected)/` — Authenticated routes behind middleware
  - `dashboard/` — Worker/supervisor home
  - `sops/` — `[sopId]` is the one SOP focus screen (Browse, Walk, and Edit via `?mode=edit`); the old tabbed page, walkthrough route, builder and versions page are deleted (Phase 58-16) and their addresses redirect in the proxy
  - `activity/` — Completion records, supervisor review (`[completionId]`)
  - `admin/sops/` — upload, new (blank / AI), `[sopId]/assign`
  - `admin/team/` — Team/org member management
- `api/sops/` — REST API routes (parse, publish, assignments, sections, download-url, parse-job)

### Key Directories
- `src/actions/` — Server actions (auth, sops, assignments, completions, versioning)
- `src/components/focus/` — the SOP focus screen (frame, browse, walk, `admin/` editor behind a lazy seam); `src/components/sop/` — plant stage, lenses, standard labels
- `src/components/activity/` — Completion/activity UI
- `src/components/admin/` — Admin panel UI
- `src/components/layout/` — Shared layout (nav, sidebar, etc.)
- `src/components/providers/` — React context providers
- `src/hooks/` — Custom hooks (useWorkerSops, useSopDetail, useStepPhotos, useCompletions, useBuilderAutosave, useNotifications, useViewport)
- `src/lib/parsers/` — File parsing pipeline (extract-docx, extract-pdf, gpt-parser, image-uploader, ocr-fallback)
- `src/lib/supabase/` — Supabase client variants (client, server, admin, middleware)
- `src/lib/validators/` — Zod schemas (auth, sop)
- `src/types/` — TypeScript types (sop, auth, database.types)

### Data Model (core types)
- **Sop** — Top-level SOP record (title, status, version, source file, confidence scores, OCR flag)
- **SopSection** — Sections within an SOP (type, title, content, sort_order, confidence, approved flag)
- **SopStep** — Individual steps within sections (text, warning/caution/tip, tools, time estimate, photo_required)
- **SopImage** — Images attached to SOPs/sections/steps (stored in Supabase Storage)
- **ParseJob** — Tracks async AI parsing pipeline (queued → processing → completed/failed)
- **SopFocusStep** — Generated hazard / ppe / step / check rows in `sop_focus_steps` (Phase 56), written only by `scripts/convert-sops-to-steps.ts`, re-runnable by `(section_id, source_key)`. The old SOP page and builder still read `sop_steps` / `layout_data` until Phase 58; each SOP has `sop_conversion_runs` rows (before/after counts, ok flag)
- **Standard** / **StandardAttachment** — `standards` (one org-wide list, e.g. LOTO) and `standard_attachments` (a standard on a SOP, section or step); managed from the builder Tools menu, shown to workers as quiet labels. `sops.placement` (`site` / `machine`) is kept in sync by a trigger on `sop_machines`; the UI never writes it
- **Decision** — Append-only `decisions` ledger (Phase 56). Write only through `recordDecision()` in `src/lib/decisions/record.ts` (org and actor come from the session; agent rows must name the agent). The database refuses UPDATE / DELETE / TRUNCATE for every role
- Statuses: SOP lifecycle is `uploading → parsing → draft → published`

### Multi-tenant & Roles
- Organization-scoped data with RLS policies
- Roles: Worker, Supervisor, SOP Admin, Safety Manager
- SOP assignment by role/trade

### Worker Walk Path (online-only since Phase 55)
- SOP list/detail read straight from Supabase via React Query (`useWorkerSops`, `useSopDetail`)
- A walk's state lives in the in-memory `completionStore`; photos upload directly to Storage via a signed URL (`useStepPhotos` → `getPhotoUploadUrl`), tagged to the active completion id
- `submitCompletion` validates every photo path against the exact `{org}/completions/{localId}/{photoId}.{jpg|png}` shape and is retry-safe (duplicate-key retries insert only missing photo rows)

## Conventions

- **Design tokens: `src/styles/blueprint-theme.css` is the one place colours are defined.** Components use them as Tailwind utilities (`text-accent-escalate`, `bg-accent-signoff/10`, `border-ink-200`) or as `var(--token)`; pastel pill/callout fills use the derived `--tint-*-bg/-border` pair. Raw Tailwind palette classes (`text-red-400`) and bare hex in component code are banned by `tests/lint/design-tokens.spec.ts` (canvas/data files allowlisted there). Need a new colour? Add the token + its `--color-*` line in the `@theme inline` block, never a literal at the call site.
- **Spacing, radius, type are tokens too** (same file, `@theme` block): type is Tailwind's xs/sm/base/lg/xl/2xl plus `text-micro` (10px) / `text-meta` (11px) / `text-ui` (13px) / `text-reading` (15px); tap targets are `tap` (44px) / `tap-glove` (60px) / `tap-row` (72px) as `min-h-tap`, `h-tap-row` …; other lengths use the numeric scale (`h-14`, `w-42`), never `h-[56px]`; radius vocabulary is four — `rounded` (chips), `rounded-lg` (controls, cards), `rounded-2xl` (sheets), `rounded-full`. Inline styles use `var(--text-meta)` / `var(--radius-lg)`. All enforced by the same lint spec.
- Paper theme app-wide (`body[data-theme="paper"]`): paper/ink neutrals, one semantic accent per role (step, measure, decision, escalate, signoff, inspect, zone, voice, ai); steel-900 + brand-yellow survive only as dark chrome in the annotation tools
- PWA-first: large tap targets (glove-friendly), mobile-optimized
- Supabase RLS for all data access; `admin.ts` client for elevated operations only
- Server actions in `src/actions/` for mutations; API routes for complex operations (parsing, file handling)
- Zod schemas in `src/lib/validators/` for all form/API validation
- Database migrations in `supabase/migrations/` (numbered sequentially)
- **Living source-of-truth maps** — `src/lib/journeys/journeys.ts` (UX pathways → `/pathways`) and `src/lib/uat/tests.ts` (UAT/design feedback → `/uat`) render their pages entirely from config. Treat them like the route tree: when a flow/screen/feature changes, update the config in the **same change**. See `## Pathways Map Maintenance` below.

## Architecture Decisions (ADRs)

`docs/adr/` holds numbered Architecture Decision Records; `docs/adr/README.md` is the index and the rules. **Accepted ADRs are binding.**

1. Every `/gsd-plan-phase`, `/gsd-execute-phase`, `/gsd-quick` and executor reads `docs/adr/README.md` before planning or building. A plan or change that contradicts an accepted ADR **stops and asks Simon** — never proceed, never work around it.
2. A structural choice (where work runs and what triggers it, data ownership, security boundaries, external services, infrastructure) gets a new ADR **in the same commit** as the change; a mechanically checkable one also gets a guard under `tests/lint/` named in its `Enforced by` line.
3. Never edit an accepted ADR's decision — supersede it with a new one.

Current: ADR-0001 (record decisions) · **ADR-0002 (no scheduled jobs — work runs on the event that causes it or the read that needs it; no cron routes, no cron services)** · ADR-0003 (site templates are code in `src/lib/site/presets.ts`; `site_layouts.preset` picks the picture's rooms, resolved server-side via `roomsFor()` into `layout.rooms`) · **ADR-0004 (design principles: attention follows the objectives — safe SOP use > records > authoring; information not instructions; plain names, no rooms, no "walk"; library by the work; site map = one object per SOP; one design source in `blueprint-theme.css`; brand yellow is the wordmark's; motion never makes anyone wait)**.

## Capability Matrix

`.planning/codebase/CAPABILITY-MATRIX.md` is the single authority on who can see and do what — every org role x every capability the app surfaces, access channel only (RLS + server-action guards). Obligation (is a role required to complete a SOP) is a separate channel, tracked by the Phase 44a obligation record, and must never be inferred from an access cell in that matrix.

Maintenance trigger (mirrors the Pathways Map convention below):
1. Any change to an RLS policy, a `require*` guard in `src/lib/auth/guards.ts`, or a role check in `src/actions/*` updates the matrix in the same commit.
2. `/gsd-plan-phase` adds the matrix edit as an explicit task when a phase changes a capability gate.
3. `/gsd-code-review` and `/gsd-verify-work` confirm the matrix matches the gates the phase touched.

## Pathways Map Maintenance (`journeys.ts`) — GSD triggers

`src/lib/journeys/journeys.ts` is the **single source of truth** for the `/pathways` UX-flow map: the page renders entirely from it, and the "All screens" panel is read live from the route tree and **flags any screen no pathway covers**. It only stays accurate if it's updated alongside the flows it describes. The GSD framework will NOT do this automatically — Claude MUST keep it current at these points (mirrors the `## Learnings` GSD-trigger model):

1. **`/gsd-plan-phase`** — if a phase adds, removes, or reroutes any user-facing screen or flow, add the `journeys.ts` edit as an explicit task in PLAN.md.
2. **`/gsd-execute-phase`** — whenever a `page.tsx` route is added/removed/renamed, or a navigation / redirect / server-action flow changes, update `journeys.ts` in the **same commit** (add or extend the relevant `Journey`; keep `route` values real so coverage + deep-links work).
3. **`/gsd-verify-work` / `/gsd-code-review`** — confirm `/pathways` → "All screens" shows **0 not-mapped** for the phase's new routes. A flagged screen = an unfinished pathways update. (Open the page, or grep `src/lib/journeys/journeys.ts` for each new route.)
4. **`/gsd-new-milestone` / roadmap** — when scoping new personas or surfaces, add their pathways so the map reflects intended flows, not just shipped ones.

**Rule of thumb: a new route or changed flow is not "done" until `journeys.ts` reflects it** (and `src/lib/uat/tests.ts` is updated when the change is worth team review). This rule is mirrored in `.planning/codebase/CONVENTIONS.md` so GSD planning/execution agents pick it up from project intel.

## Deployed-site evals (replaces human-verify checkpoints)

Simon does not run manual click-path UAT. Every phase that touches a user-facing surface ships an eval in `tests/evals/<area>.eval.ts` (Playwright project `evals`), and the orchestrator runs it after pushing:

```bash
npm run eval -- --phase <N>     # waits for Railway to serve HEAD (/api/version), runs against https://sopstart.com
```

- Fixture accounts: `eval-admin@sopstart.com` (admin) and `eval-worker@sopstart.com` (worker) in the SOPstart org — `node scripts/eval-fixtures.mjs` provisions them idempotently; sessions are minted via `tests/evals/lib/session.ts` (admin magic link → verifyOtp → `sb-<ref>-auth-token` cookie), never by typing a password.
- Output: `.planning/evals/latest/EVAL-REPORT.md` + screenshots; `--phase N` also writes `<N>-EVAL.md` into the phase directory. Claude READS the screenshots (CSS-token and sizing bugs are invisible to assertions — 2026-07-14) before declaring a pass.
- Evals self-skip without `EVAL_BASE_URL`, so `npm run test` never hits production.
- GSD hooks: `/gsd-plan-phase` adds "extend/author the eval" as a task on any UI phase and replaces `autonomous: false` human-verify tasks with an eval run; `/gsd-verify-work` and the verifier treat `<N>-EVAL.md` as the UAT artefact. Escalate to Simon only with a specific failing screenshot.

## Learnings

_Log mistakes, errors, and patterns discovered during development sessions here._

- **[2026-10-08] `git worktree remove --force` follows a `node_modules` junction and empties the MAIN checkout's `node_modules`** — Phase 63-04 built the parent commit in a temporary worktree with `node_modules` junctioned in from the main tree (to skip an install); removing the worktree deleted the junction's TARGET contents, and the main tree needed `npm ci`. Rule: before `git worktree remove`, delete the junction itself with `cmd /c rmdir <worktree>\node_modules` (removes the link, not the target), or install fresh in the worktree. Same phase: the `/page` bundle gate moved +3 KB from `next/font` alone (~227 B in `app/layout-*.js`) — a font added to the root layout is charged to every route; the baseline move was recorded as an orchestrator decision (834 → 837).

- **[2026-10-06] Turning `/` into a redirect failed every Railway deploy — the healthcheck path was `/` and Railway needs a 2xx** — The promo-reel change made a signed-out `/` 307 to `/welcome`; `railway.json` `healthcheckPath: "/"` then saw only 307s for 5 minutes, the deployment ended FAILED and the old build stayed live, so the eval silently ran against the previous commit (the poll loop never saw the new SHA and fell through after 20 minutes). Read the failure through the GraphQL `buildLogs(deploymentId)` query (the CLI `railway logs --build` stream hung). Rules: (1) the healthcheck targets `/api/version` (pinned by `tests/lint/version-route-public.spec.ts`); (2) any change to what `/` returns signed out is a deploy change; (3) an eval wrapper that polls `/api/version` must stop on timeout, not run the eval against whatever is live.

- **[2026-10-06] `organisation_members` had no delete policy, so "remove member" succeeded for a year while removing nobody -- a write that matches zero rows returns no error** — Phase 59 (59-05) found `removeMember` deleting through the session client: 00002/00062 define select, insert and update policies only, so RLS filtered the delete to zero rows, PostgREST returned success, the action said "Member removed" and the row stayed. Same family as the 2026-06-15 and 2026-09-30 entries (check every command's policy before trusting a write that returns no error), and its sibling in the same phase: a safety manager's role change said "Role updated" while the admin-only `WITH CHECK` silently filtered the row. Rules: (1) every session-client `.update()` / `.delete()` ends in `.select('id')` and treats an empty result as a failure the user sees; (2) when auditing a table's policies list the commands it HAS -- a missing command is a silent no-op, not an error; (3) a table with no write policy by design takes its write in a plain module with the service client, scoped to the session org (`src/lib/members/remove.ts`); (4) a second "best effort" server call made after the real one (the old client-side `recordSignature` after a sign-off) is a skippable legal record -- do it inside the same action, after the state change. (Phase 59 plans 05/06)

- **[2026-10-06] The first lazy module that imports a stylesheet costs ~1.4 KB of mini-css runtime in the SHARED chunk, and it only shows up when something finally imports the module -- measure the seam, not the component; and Railway's bundle gate reads 1-2 KB different from a local build of the same commit** — 59-08's `SignOffPanel` imported the lightbox CSS and went unnoticed through four plans because nothing imported the pane; the moment 59-12 mounted it, webpack added `d.miniCssF` / `d.f.miniCss` to the runtime every route downloads and `/` read +3 KB. Diagnosis was the 2026-10-05 recipe (dump and diff the summed file list against a parent-commit build); the baseline move 831 -> 834 was an orchestrator decision, not an executor edit. Afterwards the same commit measured 833 locally, 834 and 832 on two Railway builds (chunk-hash order changes what the sum rounds to), so a baseline sitting exactly at tolerance is a coin-flip -- when a lazy module is added, run `npm run build` in the plan that mounts it and record the gate number then. Separately: `--grep-invert "live|probe"` does not exclude every DB-reading spec, so a full-suite run still burns OTP budget (see 2026-09-28). (Phase 59 plan 12)

- **[2026-10-06] Deleting a view can orphan a feature for another ROLE -- grep every role's entry points before deleting a page** — Phase 59 (59-15) retired the supervisor Activity view; the only supervisor-reachable path into `RecordObservationModal` ran through it, so supervisors lost "Record observation" while admins kept it on `/admin/training`. Caught because the plan's sweep listed every reader of the deleted components, not because any test failed (the action and its guard were untouched). Recorded as a gap for Phase 61 in the matrix and `journeys.ts`. Rule: before deleting a page, list the modal or action each of its components opens and, for each, name one remaining entry point per role that could use it. (Phase 59 plan 15)

- **[2026-10-06] Deployed-eval traps that each burned a run in Phase 59** — (1) A card that renders `0` until its query lands matches `getByText(/^Sent back: \d+$/)` immediately; the "before" and "after" reads were both 0. Read the expected number from the database with the same query the card uses (here the 50 newest rows), then wait for the exact text. (2) `hasText: /\b1 photos?\b/` never matched "1 photo" because Playwright's text is the element's textContent and the row's button follows with no space ("photoSign off") -- no trailing `\b`. (3) `getByTestId('back-to-site').click()` clicked the centre of the full-width wrapper, not its link; click `.locator('a')` (hung locators and empty clicks look the same as a broken page). (4) `inviteUserByEmail` is refused for `@x.invalid` ("is invalid") and the project's built-in SMTP rate-limits invites ("email rate limit exceeded") after one or two an hour, so an eval that sends a real invite can run about once an hour and its first red after a re-run is the limit, not the product -- the Office showed the error truthfully; use `eval-invite-<run>@sopstart.com` and space full runs. (5) A Railway deployment can end `FAILED` seconds after "image push" with no logs and nothing wrong in the build; `railway redeploy` did nothing, `serviceInstanceDeployV2(commitSha)` via the GraphQL API (token in `~/.railway/config.json`) queued ~20 minutes then built and deployed the same commit -- check `gh api repos/:owner/:repo/commits/<sha>/statuses` before waiting out the eval runner's 15 minutes. (6) A serial `describe` skips every case after the first failure, so one red hides the rest of the file: run `npx playwright test --project=evals --workers=1 --retries=0 <file>` against the live site to find the whole list, then one full `npm run eval` for the report. (7) A segmented control sized to fit with a one-digit count clipped its last tab at 400 px with the real org's two-digit count (16); only the real-org shot showed it -- fixture shots (4 rows) never would, so a fixed-width control gets read against the real org's largest number before it is called done. (Phase 59 plan 16)

- **[2026-10-05] Phase 58's first deployed eval run was 7 red out of 60 and every cause was fixture or eval code, none was product — evals that self-skip carry their bugs until the last plan, and each red re-run spends the shared OTP budget** — Authored across plans 58-01..17 and never run until 58-18, the eval files held: (1) a walk fixture guarded "write the 5 steps only when none exist", but the 58-14 converter run had already filled the table with a 2-step copy, so the fixture froze in the old shape and the walk eval timed out looking for a hazard step; (2) four sibling evals (`cut-features`, `governance`, `one-screen`) built `new RegExp(`...${id}\?mode=edit`)` — inside a template literal `\?` is just `?`, a regex quantifier, so the pattern made the last UUID digit optional and never matched the real `?` in the href (the failure message even printed identical expected and received strings); (3) fixture AI findings had no `run_id`, but `GET /ai-reviewer` keeps a CLEARED row only when it belongs to the newest run, so the row vanished the moment the eval cleared it and the "Cleared · logged in the decision ledger" line never rendered; (4) `deleteEvalCompletions` did not know `sop_completion_signatures`, which the new walk submit writes, so every cleanup threw on the FK and took down the next eval's `beforeAll`; (5) two assertions encoded behaviour the shipped design contradicts (a forked draft starts unchecked — it carries ticks, 58-08; hazards before PPE — D-07 is "hazard and PPE first, in source order"); (6) `getByText` strict-mode hit the rail row AND the step card. Rules: (a) a fixture's "already set up" guard must key on its OWN marker (`source_key = 'new:eval-…'`), never on "any rows exist" — a converter or migration may have filled the table first; (b) in `RegExp` template literals write `\\?`, and `grep -nE 'RegExp\(`[^`]*[^\\]\\\?' tests/evals` before pushing any eval; (c) a fixture row the product filters by a relation (run id, version, org) must carry that relation or it disappears on first state change; (d) when a plan adds a child-table write to a submit path, extend `tests/evals/lib/*cleanup*` in the same plan; (e) before encoding behaviour in an eval, read the shipped module, not the plan text; (f) the eval runner re-runs the WHOLE suite (~10 min, ~12 minted sessions each), and six runs plus the full suite drained the OTP budget so six phase46 live probes then failed with `verifyOtp … rate limit` — read every failure and every screenshot of a run before re-running, and author evals against the deployed site as each plan lands (a one-case `--grep` run) instead of in one batch at the end. Fixed in `9a43d0bf`.

- **[2026-10-06] Phase 60's deployed eval was authored from plan text and never run until the last plan -- 8 of its first 12 cases needed a fix, and a `toPass` over a missing element hung silently; one real layout bug was visible only in a screenshot** -- Eval defects: (1) `locator.textContent()` auto-waits for the element, so `.catch(() => '')` on an ABSENT badge (a zero count renders no badge) waited out the whole `toPass` window -- bound it (`{ timeout: 1000 }`) or `count()` first; (2) the shared eval-site `Eval site fixture SOP` is a DRAFT: a worker's browse address 404s on it and a draft row has no `Ask ›`, so any case that asks, walks or is browsed by a worker must use the published plant or walk fixture; (3) a heading uppercased in source fails a case-sensitive `toContainText` (assert `/notifications/i`); (4) a notification that is read leaves the unread list by design (Show read), so asserting `data-unread="false"` on a `.first()` row fails when the locator moves; pin rows by title; (5) the bell does not poll, so an eval must wait for the asker's action to land (`ask-picker` closes) before loading the recipient's page. Product bug: the Ask picker popover (`absolute w-72 max-w-full`) sat inside the tiny `Ask ›` wrapper, so `max-w-full` collapsed it to a one-word-per-line column clipped at the panel edge -- every assertion passed; only reading `60-ask-picker.png` showed it (same class as 2026-07-14 / 2026-10-05). Rules: (a) an absolutely positioned popover must not use `max-w-full` against a shrink-wrapped anchor; (b) a plan that authors eval cases without running them (60-16) must budget a fix round at the sign-off plan, and the executor of the authoring plan should run each case once against a deploy; (c) running the eval file repeatedly burns the shared OTP budget -- by the time the full suite ran, six phase46 live probes failed with the `verifyOtp` rate-limit string; (d) a sibling eval's row-height ceiling (People row < 120) is a contract a new row element silently breaks -- grep `getBoundingClientRect` ceilings when adding a line to a shared row. Bundle gate: `/sops/[sopId]` finished at 794 against the re-baselined 795 and `/page` at 836 against 834 (+2, at the edge) -- recorded, not chased. Not yet explained: the 60-16 d case (publish diverts into a two-step chain but the first approver's "Your approval is next" notification never appears within 30 s).

- **[2026-10-05] Fixed hit-area geometry authored as fractions from a sketch floated off the floor on the real scene, and every gate stayed green** — Phase 57's four rooms (`src/lib/site/rooms.ts`) were placed from sketch-008 fractions, the one overlap spec (`rooms.spec.ts`) only checks rooms against each other, and the first deployed eval passed 44/44 — yet the real org's screenshot showed Smoko and Workshop sitting on the white ground outside the building.
