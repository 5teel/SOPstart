<objective>
The server half of SIT-02/03/04 plus the scene-intake UI: every server action the editor and the builder call, the Gemini route, and the empty state that creates the first scene.

Purpose: one write path per concern, shared by every surface — the editor (51-05) and the builder modal (51-06) both link SOPs through `setSopMachines` (D-12), and both scene on-ramps (upload, generate) record the layout through `upsertSiteLayout`, so the natural-size probe exists exactly once (2026-09-27 "the same classifier written twice will drift").

Output: `src/actions/site.ts` (7 async exports), `POST /api/admin/site/generate`, `SiteEmptyState`, the env example entries, and the activated contract spec.

Decisions implemented: D-04 (session client + `requireAdminContext()`; the tables carry an admin write policy, so no service-role client is needed — and none is used), D-05 (signed URLs, `<org>/<layout>/scene.<ext>`), D-06 (Gemini via API route, validated prompt, 16:9 2K, key-absent hides Generate, env example), D-07 (plain file input — `UploadDropzone` is coupled to SOP-creation sessions and HEIC/TUS; server-side sharp probe records natural size), D-11 (two large choices), D-12 (same action for both linking surfaces).

Discretion recorded: generation is an API route (a multi-second paid call; `maxDuration = 120`), not a server action. The server refuses both on-ramps when the org already has a layout (HTTP 409 / action error) — the editor works on the org's first layout, and this also caps paid generations to one per org. Upload uses a signed upload URL (the same idiom as SOP documents) rather than streaming the file through a Next route: requests passing the session middleware are buffered only up to its body limit, and a 15 MB scene would not survive that.
</objective>
