<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `getPhotoUploadUrl` server action | client supplies ids that become a storage path |
| browser → Supabase Storage signed upload URL | photo bytes |
| browser → `submitCompletion` | completion payload and photo paths |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-55-04 | Tampering / Elevation | `getPhotoUploadUrl` trusting `input.orgId` (cross-tenant upload into another org's folder via service-role signing) | mitigate | org taken from `getSessionContext()` only; `orgId` removed from the input type; ids validated as UUIDs so a crafted id cannot add path segments; contract test in worker-path-contract |
| T-55-03-01 | Tampering | `submitCompletion` | accept | unchanged: Zod-validated, organisation from session, idempotent on client UUID; sop_id-to-org is not cross-checked (pre-existing; rows land only in the caller's org) |
| T-55-03-02 | Denial of service | photo upload failure loses evidence | mitigate | the chip shows "Upload failed — remove and try again" and the photo gate stays closed until a photo is uploaded; nothing is silently queued |
| T-55-03-03 | Tampering | eval leaves the fixture "done" | mitigate | `deleteEvalCompletions` in beforeAll/afterAll, real-org hard-assert inside the helper |
</threat_model>
