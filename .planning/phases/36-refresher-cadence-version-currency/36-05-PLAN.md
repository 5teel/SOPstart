<objective>
Close the evidence-orphaning gap: widen every competency evidence query from "the current sop_id" to "every sop_id in that SOP's version lineage", remap the fetched rows onto the canonical current SOP, and supply the version/interval inputs the pure layer needs.

Purpose: this is the load-bearing work of Phase 36 (RESEARCH Pitfall 1). `sop_completions` / `sop_observations` / `completion_sign_offs` are keyed to a SPECIFIC sop row, not to a lineage root. Phase 35's reads are scoped to the current sop_id only, so the instant a SOP is superseded a worker who trained on v1 reads as `not_started` — literally the orphaning CMP-03 exists to prevent. The "outdated version" chip is the easy 20% once this is in place.
Output: one private lineage resolver + three widened reads + a source-contract guard.
</objective>

    - When two required SOPs share a root (a superseded version whose junction rows lingered — RESEARCH Open Question 3), attribute lineage members to the required row with the HIGHEST `version`, so evidence is never double-counted across two columns.
    - Never derive currency from `superseded_by`: `cloneSopAsDraft` + `performPublish` do not set it, so it is not a reliable signal. Currency comes from the monotonic `version` integer of the SOP row the requirement junctions point at. Say this in the helper's doc comment.

Keep `sopVersion` as the completion's OWN stamped version — that value is the version-currency comparison input and must not be rewritten.
    - Populate `MatrixSop.currentVersion` and `MatrixSop.refresherIntervalMonths` from the maps.
    - Sign-offs need no widening: they are keyed by `completion_id`, and the completion set is already widened.
    - Update the module header comment to record the Phase 36 posture: evidence is fetched lineage-wide and remapped to the canonical current sop before it reaches the pure layer, so `classify.ts` and `matrix.ts` never learn about versions.
