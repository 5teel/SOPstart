<objective>
Close the two goal-level gaps found by `34-VERIFICATION.md` / `34-REVIEW.md` CR-01 and CR-02:

1. **CR-01 (BLOCKER, same-org privacy leak):** The `sop_observations_read_org` SELECT policy's org-wide branch has no role check, so any authenticated same-org user — including a plain worker — can read every observation in the org via PostgREST, including peers' `needs_support` verdicts and supervisors' free-text coaching notes. Fix with a new migration mirroring the `sop_completions` (00010) role-scoped pattern, push it live, and add runtime RLS probes covering both the worker-negative and supervisor-positive branches (per the CLAUDE.md 2026-07-20 RLS-branch-coverage learning: every branch needs its own positive AND negative probe per role).

2. **CR-02 (dead assigned-first picker for supervisors):** `listWorkerSopsForPicker` reads `sop_assignments` with the session client, whose RLS only exposes rows visible to the *caller*, not the observed worker — so for a supervisor recording on behalf of a worker (the phase's primary persona), `assignedIds` is always empty and the D-06 "assigned-first" ordering silently never fires. Fix by role-gating the action and reading `sop_assignments` via the admin client with explicit org self-scoping on both queries, keyed to the *observed* worker's role, not the caller's.

Fold in WR-01 (cheap, same files already being touched): add Zod validation to `setObservationLabels` so a malformed label payload can't crash every worker's `/profile` render.

Purpose: Phase 34's own stated goal ("tamper-evident, trustworthy evidence layer") cannot hold while any worker can read every peer's observations, and Phase 35's classifier should not be built on top of an unproven privacy invariant.
Output: Migration 00054 (live), one new runtime spec (gap 1), a fixed `listWorkerSopsForPicker` + one new source-contract spec (gap 2), and Zod-validated observation labels.
</objective>
