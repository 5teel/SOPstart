## Trust Boundaries

| Boundary | Description |
|----------|-------------|

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-07-01 | Tampering | macro-enabled Office file uploaded as a new SOP version | mitigate | `isBlockedMacroFile` added to `uploadNewVersion` (currently absent — this closes a real gap), plus the client-side `BLOCKED_EXTENSIONS` check via `validateIntakeFile` |
| T-40-07-02 | Elevation of Privilege | `uploadNewVersion` service-role write to another org's SOP lineage | mitigate | The existing `oldSop.organisation_id !== organisationId` assertion (WR-07) is preserved verbatim and pinned as an acceptance criterion; every new field the video branch writes is derived from that already-verified `organisationId`, never from the request |
| T-40-07-03 | Spoofing | file whose MIME type misrepresents its content routed to the wrong pipeline | mitigate | `getSourceFileType` throws on unknown types and the action returns an error rather than defaulting — replacing an `extensionMap` that silently defaulted everything to `'docx'` |
| T-40-07-04 | Denial of Service | 2GB video uploaded to the new-version or pipeline surface | mitigate | `validateIntakeFile` enforces `MAX_VIDEO_FILE_SIZE` client-side; the TUS resumable path is the same one the creation dropzone already uses in production for 2GB uploads |
| T-40-07-05 | Repudiation | new version created but never transcribed, leaving an empty draft | mitigate | `startVideoSopUpload` fires `/api/sops/transcribe` in its success callback and reports `{ ok: false, error }` otherwise; the `parse_jobs` row is created with `current_stage: 'uploading'` so the progress surface shows a stalled job rather than nothing |
