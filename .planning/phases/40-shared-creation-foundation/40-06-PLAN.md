**`scripts/backfill-sop-category.mjs`.** Default mode is `--dry-run`; a live write requires the explicit flag `--apply`. Print a summary table in both modes.

Order of operations, exactly:

*Step 0 — audit record, written BEFORE any write.* Read every `sops` row's `id, organisation_id, category, category_tag, category_slug` and write them to `.planning/phases/40-shared-creation-foundation/category-backfill-audit.json`. This file is the rollback record — the retired columns are nulled in step 4 and are otherwise unrecoverable. Refuse to continue with `--apply` if the audit file cannot be written.

*Step 1 — deterministic pass (idempotent re-run of the migration's SQL).* For rows where `category_slug is null`, resolve via `normaliseToCategorySlug(category_tag)` then `normaliseToCategorySlug(category)`. Write only the rows that resolved.

*Step 2 — AI mapping of the residue, mapped per DISTINCT VALUE, not per row.* Collect the distinct still-unresolved `category`/`category_tag` strings (the survey showed this is a handful of values, not thousands). Send that list, plus the full vocabulary, in **one** LLM call asking for a `{ originalValue: slug | null }` object, with `null` meaning "no reasonable match". Validate every returned slug with `isValidCategorySlug`; drop anything that fails. Then apply the resulting dictionary to the rows. Mapping distinct values rather than rows makes the pass cheap, deterministic to review, and recordable in the audit file — append the dictionary to it.
  **Null-clobber rule (CLAUDE.md [2026-07-05], non-negotiable):** the update payload must be built by conditional spread — `{ ...(slug ? { category_slug: slug } : {}) }` — so a value the model could not map, or a failed call, results in **no write at all** for those rows, never a blanket `category_slug: null`. If the LLM call throws entirely, log it, mark the run `partial`, and continue to step 3 — do not let a fail-open path report success (the [2026-07-05] "status ok, zero cost, all rows destroyed" signature).

*Step 3 — remap the two settings tables keyed by the old free-text value.* Using the SAME resolved dictionary (deterministic map plus AI map):
  - `sop_review_cadences`: for each row, if its `category` value maps to a slug, update it to the slug. The primary key is `(organisation_id, category)`, so a remap that would collide with an existing row for the same org must be resolved by keeping the row with the **shorter** `months` (the more frequent review — the safer of two conflicting cadences) and deleting the other. Log every collision.
  - `approval_chains`: same remap, same `(organisation_id, category)` key. On collision, keep the row with **more** steps (the stricter chain) and log it. An approval chain that stops matching is a safety regression — never silently drop one.
  Both loops iterate rows scoped by `organisation_id` and pass `organisation_id` in every write filter. The service-role client bypasses RLS and has no automatic org scoping (CLAUDE.md [2026-06-15]/[2026-07-05]); the org value must come from the row being processed, and each write must carry `.eq('organisation_id', row.organisation_id)` in addition to the key.
  `collections` rows are deliberately NOT renamed — plan 40-05 resolved that question: existing collections keep their names and their admin-customised colour/sort, and `ensureSopCollectionsForOrg` now matches by vocabulary label so a label-equal collection is reused. Print a list of `collections` names that match no vocabulary label so an operator can see which ones will stop gaining members.

*Step 4 — retire the old data.* Only after steps 1-3 complete without a fatal error, and only under `--apply`: `update public.sops set category = null, category_tag = null` for every row, in `organisation_id`-scoped batches. This is what makes SC-5's "zero rows left behind" true. Guard it: refuse to run step 4 if the audit file does not exist on disk, and refuse if step 2 reported a total LLM failure (`partial` status) — a partial run must be re-run with the model reachable before the source data is destroyed.

*Step 5 — summary.* Print: rows total, resolved by pass 1, resolved by pass 2, left uncategorised, cadence rows remapped, cadence collisions, chain rows remapped, chain collisions, retired-column rows nulled, and the run status (`ok` | `partial`). Never print `ok` when any step failed.

**`scripts/verify-category-backfill.mjs`.** Read-only, no flags, safe to run any time. It is the SC-5 proof and must pin **both** retired columns, not one:
- `select count(*) from public.sops where category is not null` → must be 0
- `select count(*) from public.sops where category_tag is not null` → must be 0
- `select count(*) from public.sops where category_slug is null` → reported (uncategorised rows are legitimate per D-02, but the number must be visible)
- `select count(*) from public.sop_review_cadences where category not in (<vocabulary>)` → reported; a non-zero value means legacy cadence keys survive
- `select count(*) from public.approval_chains where category not in (<vocabulary>)` → reported; same
- exit code 1 if either of the first two counts is non-zero, so the script is CI-usable as well as operator-usable
Print each query's SQL alongside its result so the output is self-evidencing.
