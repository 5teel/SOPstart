<objective>
Close 40-REVIEW.md CR-04 / WR-02: one click on the failed-state "Try again" button wipes a draft's sections and strands the SOP in `parsing`, with no recovery path.

Purpose: `reparseSop` deletes `sop_sections` and resets `status: 'parsing'` FIRST, then fetches the SOP and checks the source file exists — so when the file is missing (incomplete upload, storage cleanup, or an AI-prompt SOP whose `source_file_path` is the synthetic `ai-prompt/{userId}/{ts}`) it returns an error with the sections already destroyed. On top of that, `ParseJobStatus` routes `input_type === 'ai_prompt'` retries to `/api/sops/ai-prompt`, which requires `promptText` (Zod min 20) — the body only carries `sopId`, so it 400s silently because the `fetch(...).catch()` never inspects the response — and even with a prompt that route creates a brand-new SOP rather than re-parsing this one. Reachable from both `PromptClient` and `VoiceDraftClient`.

This is a bug fix, not a feature: verify before destroying, do not offer an action that cannot work, and stop swallowing the error. Re-driving an AI-prompt job from its persisted `parse_jobs.prompt_text` is the fuller fix and is explicitly out of scope here.

Output: a `reparseSop` that destroys nothing until its preconditions hold, and a retry affordance that is absent where it would destroy.
</objective>
