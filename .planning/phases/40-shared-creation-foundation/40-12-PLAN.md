Every caller of these three routes is a browser fetch from an authenticated admin surface — `UploadDropzone`, `VideoFormatSelectionModal`, `versions/page.tsx`, `VideoPreviewPanel`, `ParseJobStatus` and `startVideoSopUpload`. There is no server-to-server or cron caller, so an admin session guard breaks nothing. Confirm this with `grep -rn "api/sops/parse\|api/sops/transcribe\|api/sops/restructure" src/` before editing, and state the caller list in the SUMMARY.

In EACH of the three route files, at the very top of `POST` — after `sopId` is read and validated as present, and BEFORE `createAdminClient()` is called or any query runs:

1. `const { userId, role, organisationId } = await getSessionContext()` (import from `@/lib/auth/session-context`).
2. `if (!userId)` → 401 `{ error: 'Not authenticated' }`.
3. `if (!role || !['admin', 'safety_manager'].includes(role))` → 403 `{ error: 'Admin access required' }`.
4. `if (!organisationId)` → 403 `{ error: 'No organisation found' }`.
5. Create the admin client, then fetch the target SOP's org and compare it to the SESSION org:
   `const { data: sopOrg } = await admin.from('sops').select('organisation_id').eq('id', sopId).maybeSingle()`
   `if (!sopOrg || sopOrg.organisation_id !== organisationId) return 404 { error: 'Not found' }` — 404 rather than 403 so the endpoint does not confirm the existence of another org's SOP.

Load-bearing ordering, and the point of the whole plan: in `parse/route.ts` this guard block must sit ABOVE the `sop_images` / `sop_sections` deletes at lines 79-80, and above the `parse_jobs` status update. In `transcribe` and `restructure` it must sit above the `parse_jobs`/`sops` status updates and above any model call.

CLAUDE.md [2026-07-28] CR-01 rule — the org used downstream must be the SESSION's, not the fetched row's: where these routes later read an org id for a write (for example `parse/route.ts`'s image-upload path re-fetching `sops.organisation_id`), use the `organisationId` from `getSessionContext()` instead. Once the guard has proven equality the values are identical, so this is a rename, not a behaviour change — but it removes the attacker-influenced variable from the code entirely, which is what the learning asks for.

Do not otherwise restructure these routes: the parse pipeline, the retry-semantics delete comment, the stage updates and the error handling all stay exactly as they are. This is a guard insertion, not a refactor.

Also fold in 40-REVIEW.md WR-03 in `src/app/api/sops/ai-prompt/route.ts`: extend `aiPromptSchema` in `src/lib/validators/sop.ts`... — no. `const deptSchema = z.object({ departmentIds: z.array(z.string().uuid()).max(20).optional().default([]), allDepartments: z.boolean().optional().default(false) })`, `safeParse(body)`, 400 on failure. This gives the trust-boundary validation WR-03 asks for (uuid element types instead of a bare `Array.isArray`) without touching a file another wave-1 plan owns. Note in the SUMMARY that folding these two fields into `aiPromptSchema` proper is the tidier end state and is a one-line follow-up once 40-10 has landed.
