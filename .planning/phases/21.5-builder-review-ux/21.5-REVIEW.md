# Phase 21.5: Code Review Report

**Reviewed:** 2026-06-02
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

This phase refactors the SafeStart admin builder into a staged Build → Review → Publish
shell composing presentational components, plus a humanized block-type label map and a
3-zone Review Station. The safety invariant (SPEC R10 — server publish gate + no-bulk-verify)
is **preserved correctly**: the server route still returns `400 unverified_blocks`
(`publish/route.ts:97-102`), the shell delegates the publish button solely to `PublishStage`,
and `handleStageSelect` re-guards `publish` on `effectiveIsReady`.

The label map and its tests are sound. However there is **one functional wiring bug** that
silently breaks source-pane scroll-to-region from the Review Station's AI flag clicks, plus
several controlled-component / robustness issues. The integration spec is source-contract-only
(reads files from disk, no runtime), so none of the runtime behavior below is actually exercised
by CI — these defects would pass the phase's own test suite.

## Critical Issues

### CR-01: ReviewStation passes a bare provenance region but ReviewerFlagsPanel reads `.region` — flag-click source scroll silently broken

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/ReviewStation.tsx:578`
**Issue:**
`ChecklistBlock.provenance` is typed as `SourceProvenanceRegion | null` (a *region object* like
`{ kind: 'pdf', page, bbox, ... }` — see `useVerifyChecklist.ts:43` and
`source-viewer/types.ts:12`). ReviewStation passes it straight through:

```tsx
<ReviewerFlagsPanel
  sopId={sopId}
  blockId={activeBlock.id}
  blockProvenance={activeBlock.provenance}   // a SourceProvenanceRegion
/>
```

But `ReviewerFlagsPanel`'s click handler reads a **nested** `.region` off that prop
(`ReviewerFlagsPanel.tsx:56`):

```ts
const region = blockProvenance?.region ?? null   // .region is ALWAYS undefined here
setActiveProvenance(region, blockId)
```

A `SourceProvenanceRegion` has no `.region` member, so `region` is always `null`. Every AI-flag
click in the Review Station therefore scrolls the source pane **nowhere** (passes `null`), even
when the block has valid provenance. Note the same component is mounted elsewhere
(`BuilderClient.tsx:291`) with **no** `blockProvenance` prop at all — so ReviewStation is the only
caller, and it's the only one that got the shape wrong. The mismatch is invisible because the
phase's integration spec is source-contract only and never renders the component.

`ReviewStation` itself already calls `selection.setActiveProvenance(block.provenance ?? null, block.id)`
correctly (lines 70, 109, 125, 132) — i.e. it passes the bare region, which is the right shape for
that API. So the panel prop is the inconsistent path.

**Fix:** Either pass the wrapper shape the panel expects, or (cleaner) wrap it:
```tsx
// Option A — wrap to match the panel's `.region` read:
blockProvenance={activeBlock.provenance ? { region: activeBlock.provenance } : null}
```
Or fix the panel to accept a bare region (and update its type from `any`):
```ts
// ReviewerFlagsPanel.tsx
const region = (blockProvenance ?? null) as SourceProvenanceRegion | null
setActiveProvenance(region, blockId)
```
Pick one and align the `blockProvenance` type (currently `any`) so the compiler catches future drift.

## Warnings

### WR-01: Stage state can become stranded on `publish` when verification is revoked

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/BuilderStageShell.tsx:179-190, 293-305`
**Issue:**
`handleStageSelect` guards entry into `publish` on `effectiveIsReady`, but nothing re-evaluates
`activeStage` when `isReady` later flips back to `false`. Scenario: admin verifies all blocks →
navigates to Publish → opens Review in another tab / uses the keyboard `d` (decline) elsewhere, or
a `router.refresh()` / query invalidation drops `verifiedCount`. `effectiveIsReady` becomes `false`
while `activeStage` is still `'publish'`. The Publish stage stays mounted; the button correctly
disables (`PublishStage` gates on `isReady`), but the stepper now shows Publish as the active chip
while simultaneously rendering the "🔒 N of M steps left to verify" reason — a contradictory state,
and the user is parked on a dead-end stage with no automatic bounce back to Review.
**Fix:** Add an effect that demotes the active stage when its precondition is lost:
```tsx
useEffect(() => {
  if (activeStage === 'publish' && !effectiveIsReady) setActiveStage(hasSourceDoc ? 'review' : 'build')
}, [activeStage, effectiveIsReady, hasSourceDoc])
```

### WR-02: `handleApprove` "advance to next" can land on the just-verified block (stale `activeIdx` closure)

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/ReviewStation.tsx:114-135`
**Issue:**
After `await checklist.approve(activeBlock.id)`, the code searches
`checklist.blocks.findIndex((b, i) => i > checklist.activeIdx && b.verified_by_admin_id === null)`.
`approve()` is optimistic and invalidates the query (`useVerifyChecklist.ts:184-187`), so by the time
the `await` resolves, `checklist.blocks` may be a **new array** while `checklist.activeIdx` is read
from the same render's closure. If a refetch reorders or the optimistic flip hasn't propagated into
the `blocks` reference captured here, the "next unverified" search can skip the intended block or
re-select the current one. The fallback branch (`activeIdx < blocks.length - 1`) compounds this by
advancing by a raw `+1` against a possibly-changed array. Because `handleApprove` depends on the whole
`checklist` object, the closure is at least refreshed per render, but the `await` straddles a state
update, so the post-await reads are not guaranteed coherent.
**Fix:** Capture the current index/id before the await and compute the next target from the resolved
state, or drive "advance" from a `useEffect` keyed on `verifiedCount` rather than inline after the
mutation. At minimum, recompute against `checklist.blocks` *after* the await using the captured
`activeBlock.id` to find the current position rather than the closed-over `activeIdx`.

### WR-03: `handlePrev` does not move source-pane selection in sync with the active step

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/ReviewStation.tsx:142-144`
**Issue:**
`handleSelectRow`, `handleApprove`, and the keyboard `focusSourcePane` all call
`selection.setActiveProvenance(...)` so Zone 3 (Original document) tracks the active step. `handlePrev`
(the "◀ Previous step" action-bar button) only calls `checklist.setActiveIdx(...)` and never updates
selection. Result: clicking "Previous step" moves the highlighted nav row and the centre card but
leaves the source pane scrolled to the *previous* step's region — directly contradicting the Zone 3
header copy "Auto-scrolled to the part this step came from" (line 627).
**Fix:** Mirror the other handlers:
```tsx
const handlePrev = useCallback(() => {
  const idx = Math.max(0, checklist.activeIdx - 1)
  checklist.setActiveIdx(idx)
  const b = checklist.blocks[idx]
  if (b) selection.setActiveProvenance(b.provenance ?? null, b.id)
}, [checklist, selection])
```

### WR-04: `OrientationStrip` and shell hardcode "Step 2 of 3" — wrong/misleading in the 2-stage flow

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/BuilderStageShell.tsx:281`
**Issue:**
The shell always passes `stageBadge="Step 2 of 3"` to `OrientationStrip`. The OrientationStrip only
mounts inside the `review` branch which is already gated on `hasSourceDoc`, so the "of 3" is
technically only shown in 3-stage mode — but the value is a hardcoded string duplicating the stepper's
ordinal logic (`BuilderStageStepper.tsx:215-219`). If the adaptive-stepper contract (R8) ever changes
the Review ordinal, this literal silently drifts out of sync. SPEC R8/R9 treat stage ordinals as
derived; this is the one place they're hand-typed.
**Fix:** Derive the badge from the same `stageToOrdinal`/`chips` source the stepper uses (e.g. pass
`stageBadge={`Step ${reviewOrdinal} of ${chips.length}`}`), or lift a shared helper. Avoid the magic
string.

### WR-05: AI-flag count in the panel header reads from a different render path than `flags_count`, can disagree

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/ReviewStation.tsx:98-101, 562-565`
**Issue:**
The Zone-2 header count uses `reviewer.byBlockId.get(activeBlock.id)` directly via the
`ReviewStation`'s own `useReviewerFlags(sopId)` instance, while the NavRow flag badges use
`block.flags_count` which `useVerifyChecklist` computes from *its own* internal `useReviewerFlags(sopId)`
instance (`useVerifyChecklist.ts:142, 150`). There are now three independent `useReviewerFlags(sopId)`
mounts in this subtree (ReviewStation, useVerifyChecklist, ReviewerFlagsPanel). They share a TanStack
query key so the cache is shared, but the `byBlockId` Maps are memoized per-hook-instance; during a
re-run mutation the instances can briefly hold different envelopes (one updates via `onSuccess`
`setQueryData`, others via the next `useQuery` read), so the header "N things to look at" can disagree
with the nav-row badge and the inline `ReviewerFlagsPanel` rows for a frame or two.
**Fix:** Thread a single `reviewer` result down (the shell already could own it) rather than calling
`useReviewerFlags(sopId)` three times; or accept the eventual-consistency window explicitly. Not a
correctness bug for the gate, but it produces visibly inconsistent counts.

### WR-06: `transcriptSegments` rebuilt on every render (new array identity) → unnecessary downstream churn

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/BuilderStageShell.tsx:143-164`
**Issue:**
`transcriptSegments` is computed inline in the component body (not memoized), so a fresh array is
produced on every render and passed to `ReviewStation` → `SourceViewerPane`. Combined with the three
`useReviewerFlags` mounts and the checklist query, any state change (publishing toggle, error set,
stage change) re-creates this array and forces referentially-keyed children to treat the prop as
changed. For a video SOP with many segments this re-runs the parse/validate loop each render.
**Fix:** Wrap in `useMemo` keyed on `parseJob` and `sourceType`:
```tsx
const transcriptSegments = useMemo<TranscriptSegment[]>(() => { /* existing loop */ }, [parseJob, sourceType])
```
(Flagged as a correctness-adjacent robustness issue, not raw perf: the unstable identity is what makes
WR-05's inconsistency window more frequent.)

## Info

### IN-01: NavRow mixes a Tailwind `hover:` class onto an inline-`style` element — hover background never applies

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/NavRow.tsx:119, 123`
**Issue:**
The row sets `background: active ? '#eff4ff' : 'transparent'` via inline `style` AND
`className="hover:bg-[var(--paper-2)]"`. Inline styles win over class-based backgrounds, so the
`hover:bg-*` utility is dead — the documented "hover → background --paper-2" state (file header,
lines 11) never renders for non-active rows.
**Fix:** Drive hover via CSS (a `<style>` rule like the grid uses) or `onMouseEnter/Leave` state, not a
Tailwind class layered over an inline `background`.

### IN-02: Unit tests import from `@playwright/test` to test a pure module — no Playwright runtime needed

**File:** `src/lib/builder/__tests__/block-type-labels.test.ts:10`
**Issue:**
`block-type-labels.test.ts` and `builder-review-flow.spec.ts` are pure-logic / file-read assertions but
import `test`/`expect` from `@playwright/test`, pulling the browser test harness for what are really
unit tests. This is an established project pattern (per playwright.config projects), so it's not a
defect — noting that these "tests" never exercise rendered component behavior, which is why CR-01,
WR-01..03 slip through CI. Consider one real render/integration test for the Review Station handlers.

### IN-03: `humanizeBlockType` dead type-guard branch

**File:** `src/lib/builder/block-type-labels.ts:97`
**Issue:**
`if (!type || typeof type !== 'string') return FALLBACK_LABEL` — the parameter is typed `string`, so the
`typeof` check is unreachable under TypeScript callers. Harmless defensive code; keep if runtime callers
may pass non-strings (the snapshot `kind` is `unknown`-derived upstream), otherwise it's dead.
**Fix:** Either keep and document the runtime-safety intent, or simplify to `if (!type) return FALLBACK_LABEL`.

### IN-04: `<style>` injected inline in client components duplicates per mount

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/ReviewStation.tsx:213-264`, `BuilderStageStepper.tsx:228-235`
**Issue:**
Responsive rules are emitted via inline `<style>{...}</style>` inside the render tree. With React 19 these
de-dupe by content in many cases, but the `.review-station-grid` / `.stepper-chip-label` selectors are
global and would collide if either component ever mounts twice. Low risk given single-mount usage; flagged
for maintainability — prefer a CSS module or a global stylesheet for these static rules.
