# Phase 21.5: Builder Review UX — Specification

**Created:** 2026-06-02
**Ambiguity score:** 0.19 (gate: ≤ 0.20)
**Requirements:** 10 locked

## Goal

Restructure the admin SOP builder's authoring-to-publish surface from 5–6 always-on, jargon-labelled panels into a sequenced **Build → Review → Publish** flow where a first-time admin can, without guidance, understand each pane's purpose and complete review and publish.

## Background

The builder route `(protected)/admin/sops/builder/[sopId]` renders `BuilderWithSourceViewer.tsx`, a horizontal flex of: the Puck editor (`BuilderClient.tsx`, itself a 3-column palette/canvas/fields plus `SectionListSidebar` and `ReviewerFlagsPanel`), a 520px-min `SourceViewerPane`, and a 320px-min `VerifyChecklistGate`. On a 1440px laptop ~840px is reserved by the two right panes before the editor gets space. Nothing states what the screen is for, where to start, or in what order. Real evidence of failure: the project owner (who built the app) was confused on first use during Phase 21 UAT. Specific drivers: no orientation/sequence; two unlinked review systems (AI reviewer badges vs human verify checklist); internal symbol labels leak to the UI (`{block.type}` renders `StepBlock`/`PhotoGrid`); verify actions are single letters (`a`/`d`); the publish button is greyed with its reason only in a hover tooltip; the publish surface is buried in the far-right gate.

A design direction was sketched and validated with the owner (`sketch-builder-redesign-01.html`) on the paper/ink `sketch-findings-SOPstart` system. The data/query layer, AI reviewer orchestrator, verify semantics, and publish gate (shipped in Phase 21) are correct and stay — this phase restructures and restyles the **UI shell** around them.

## Requirements

1. **3-stage stepper shell**: The builder presents an explicit Build → Review → Publish sequence.
   - Current: No stage model; all surfaces render at once with no indication of order
   - Target: A persistent stepper shows the three stages and which one is active; completed stages read as done, future stages as todo
   - Acceptance: Stepper is visible in all builder states and correctly marks the active stage as the user moves between Build, Review, and Publish

2. **Review Station — one step at a time**: The Review stage shows a single step with its context, not all panels at once.
   - Current: `SourceViewerPane` + `VerifyChecklistGate` + `ReviewerFlagsPanel` all render simultaneously alongside the full Puck editor
   - Target: Review stage = three zones — step navigator (left), the selected step rendered as the worker sees it (centre), the source document auto-scrolled to that step's region (right); selecting a step in the navigator updates centre + right
   - Acceptance: In Review, exactly one step's content is shown in the centre; clicking another navigator row switches both centre and source-right to that step

3. **Inline AI check**: AI reviewer flags are attached to the step they concern.
   - Current: `ReviewerFlagsPanel` is a separate region disconnected from the block it flags
   - Target: A step's reviewer flags render inside that step's card in the Review centre zone
   - Acceptance: A step with ≥1 reviewer flag shows those flags within its own card; a step with no flags shows none; no standalone reviewer-flags panel remains in the Review stage

4. **Humanized labels**: No internal/code identifiers appear in the UI.
   - Current: `{block.type}` renders raw symbols like `StepBlock`, `PhotoGrid` (mono-uppercase) in the checklist rows
   - Target: Every block/step type displays a human label (e.g. `Step`, `Photo grid`, `Hazard`, `Measurement`)
   - Acceptance: A grep/visual check finds no internal symbol names (`*Block`, `PhotoGrid`, etc.) rendered to the user anywhere in the builder review surface

5. **Plain-language verify actions**: Row actions read as words.
   - Current: Per-block actions are single letters `a` (approve) / `d` (decline)
   - Target: Actions read "Verify" and "Send back to edit" (keyboard shortcuts may remain as secondary hints)
   - Acceptance: The verify and send-back controls show word labels; single-letter `a`/`d` are not the primary affordance

6. **Visible publish-gate reason**: The blocked-publish reason is always on screen when blocked.
   - Current: Publish button is disabled with the reason only in a `title` hover tooltip (invisible on touch)
   - Target: When publish is blocked, the reason ("N of M steps left to verify") is rendered inline next to/under the control
   - Acceptance: With ≥1 unverified step, the remaining-count reason is visible without hovering; it disappears/updates when all steps are verified

7. **Dedicated Publish stage**: Publish is a named stage, not a buried button.
   - Current: The sole publish surface is a button inside the far-right `VerifyProgressIndicator`
   - Target: Publish is the third stepper stage with a confirmation surface; it remains gated (enabled only when the verify gate is satisfied)
   - Acceptance: A Publish stage exists and is reachable from the stepper; it is the only place publish is triggered; publishing still requires all applicable steps verified

8. **Adaptive stepper for source-less SOPs**: SOPs without a source document skip the parts that don't apply.
   - Current: `showPane`/`showVerifyGate` already gate the panes for AI-prompt and pre-Phase-20 SOPs, but there is no coherent flow around that
   - Target: When an SOP has no source file / bypasses the verify gate, the Review stage and source pane are omitted and the flow is Build → Publish
   - Acceptance: Opening an AI-prompt SOP (no source) shows a Build → Publish stepper with no source pane and no Review stage, and publishes without error

9. **Tablet-responsive layout**: The builder is usable down to tablet width.
   - Current: Fixed-width panes (520px + 320px minimums) force horizontal scroll / squashing below ~1300px
   - Target: At ≥768px the three Review zones reflow (stack/collapse) so no pane is clipped and there is no horizontal page scroll
   - Acceptance: At 768px viewport width, the Review stage shows all three zones' content without horizontal page scroll or overlapping panes

10. **Safety invariants preserved**: The redesign changes UI only, not the safety gates.
    - Current: Phase 21 ships a defence-in-depth publish gate (UI-disabled + server 400) and the SCP-VERIFY-05 / D-21-07 no-bulk-verify lock (CI grep guard)
    - Target: The new UI preserves both — no bulk/approve-all affordance, and publish is still server-rejected when unverified blocks remain
    - Acceptance: `tests/lint/no-bulk-verify-ui.spec.ts` stays green; a direct publish POST with ≥1 unverified parser-created block still returns HTTP 400 `unverified_blocks`

## Boundaries

**In scope:**
- 3-stage Build → Review → Publish stepper shell wrapping the existing builder
- Review Station 3-zone layout (navigator / step-in-app / source) rendering one step at a time
- AI reviewer flags rendered inline within each step card
- Humanized type labels and plain-language verify/send-back actions across the review surface
- Inline publish-gate reason and a dedicated Publish stage as the sole publish surface
- Orientation / pane-purpose microcopy
- Adaptive stepper for source-less / AI-prompt / pre-Phase-20 SOPs (Build → Publish)
- Tablet-responsive behaviour at ≥768px
- Restyle of the Build (Puck editor) stage to sit inside the new shell

**Out of scope:**
- Puck block-editing internals, block schema, or the block library — reused as-is, only rehoused in the Build stage
- Server publish logic, RLS, verify semantics, or the AI reviewer orchestrator — UI-only restructure (no API/data-layer changes)
- Worker-facing walkthrough surfaces — this phase is the admin builder only
- Phone/mobile (<768px) builder layout — admins author on desktop/tablet
- New block types or new AI reviewer jobs — none added here
- Bulk-verify / approve-all / trust-score skip — permanently excluded by SCP-VERIFY-05 / D-21-07

## Constraints

- **Reuse shipped Phase 21 components** (`BuilderWithSourceViewer.tsx`, `SourceViewerPane`, `VerifyChecklistGate`, `ReviewerFlagsPanel`, `useVerifyChecklist`, `useReviewerFlags`, `useSelectionSync`) — restructure/restyle, do not rebuild the data/query layer.
- **Design system**: paper/ink `sketch-findings-SOPstart` tokens — JetBrains Mono (technical) + Inter (prose), 20px grid, small radii (≤6px), semantic accent colours (step=blue, hazard=red, measure=orange, decision=pink, signoff=yellow, ok=green, inspect=cyan).
- **Admin-only isolation (D-21-09)** preserved — pdfjs/mammoth/reviewer code must not leak into the worker bundle (keep dynamic imports / route boundaries).
- **Safety gates preserved** — defence-in-depth publish gate (UI + server 400) and the D-21-07 no-bulk-verify lint guard must remain in force.
- **Responsive floor** = 768px (tablet); no phone layout required.

## Acceptance Criteria

- [ ] A Build → Review → Publish stepper is visible in all builder states and marks the active stage correctly
- [ ] In the Review stage, exactly one step shows at a time across navigator (left) / step-in-app (centre) / source (right); selecting another step updates centre + source
- [ ] A step's AI reviewer flags render inside that step's card; no standalone reviewer-flags panel remains in Review
- [ ] No internal symbol names (`StepBlock`, `PhotoGrid`, `*Block`) are rendered to the user anywhere in the builder
- [ ] Verify and "Send back to edit" actions show word labels, not single letters, as the primary affordance
- [ ] When publish is blocked, the remaining-count reason is visible without hovering
- [ ] A dedicated Publish stage is the sole publish trigger and stays gated on the verify checklist
- [ ] An AI-prompt SOP (no source) renders a Build → Publish stepper (no Review stage, no source pane) and publishes without error
- [ ] At 768px viewport, the Review stage shows all three zones without horizontal page scroll or overlapping panes
- [ ] `tests/lint/no-bulk-verify-ui.spec.ts` stays green AND a direct publish POST with an unverified parser-created block still returns HTTP 400 `unverified_blocks`
