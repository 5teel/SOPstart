## Summary

Phase 21.6 reconfigures the Puck 0.21.2 Build/edit stage from its current double-panel layout (left palette + right fields + Puck outline) to a single step-centric tree rail with inline canvas text editing. The phase is **UI-led and reconfigure-in-place** — `layout_data`, autosave, junctionId stamping, and the publish gate are untouched.

The three biggest technical risks have been resolved by reading the installed Puck source:

1. **Inline canvas editing (E4)** — Puck 0.21.2 has native `contentEditable: true` on `text`, `textarea`, and `custom` field definitions, implemented via the `InlineTextField` component. Setting this flag causes the field value to render as an editable span directly on the canvas (hover → contentEditable="plaintext-only"). Edits dispatch a Puck `replace` action which goes through the `onChange` callback → `useBuilderAutosave`. This is the correct path — no custom contentEditable wiring needed.

2. **Hiding Puck's native palette + outline (E3)** — The `overrides.components` and `overrides.outline` props accept render functions. Returning `<></>` from each effectively removes those panels. Additionally, passing `ui={{ leftSideBarVisible: false, rightSideBarVisible: false }}` as the initial `ui` prop to `<Puck>` suppresses both sidebars at mount. The `createPuckOverrides` factory must be extended to add `components` and `outline` null-renderers, while preserving `componentItem` and `componentOverlay`.

3. **Programmatic block insert (D-03)** — `usePuck()` exposes `dispatch`, which accepts an `InsertAction: { type: "insert", componentType, destinationIndex, destinationZone }`. The root zone identifier is `"root:default-zone"` (confirmed from Puck chunk source). The `AddMenu` can dispatch inserts at any index, then stamp `junctionId` via the existing pattern.

**Primary recommendation:** Add `contentEditable: true` to the `text`/`textarea` fields for StepBlock, HeadingBlock, CalloutBlock, TextBlock, StepWithPhotosBlock, HazardCardBlock, ZoneBlock, and EscalateBlock; hide sidebars via `overrides.components`/`overrides.outline` and initial `ui` prop; build `BuilderTreeRail` as a custom React component (not a Puck override) that replaces `SectionListSidebar`.

### Pattern 1: Hiding Puck's Native Panels

**What:** Return empty fragments from `overrides.components` and `overrides.outline` to suppress Puck's left palette and outline panels. Pass `ui={{ leftSideBarVisible: false, rightSideBarVisible: false }}` to `<Puck>` to hide both sidebars at mount.

**When to use:** Always in BuilderClient for the reconfigured Build stage.

**Example:**
```typescript
// Source: node_modules/@puckeditor/core/dist/actions-C3e2nJ9v.d.ts (Overrides type)
// In createPuckOverrides():
return {
  components: () => <></>,   // hides component palette (left panel)
  outline: () => <></>,      // hides outline tree (left panel tab)
  componentItem: /* existing BlockOverflowMenu wiring — unchanged */,
  componentOverlay: /* existing AI flags + badge wiring — unchanged */,
}

// In BuilderClient.tsx, on the <Puck> element:
<Puck
  key={activeSection.id}
  config={puckConfig}
  overrides={overrides}
  data={sanitizedInitial}
  onChange={handleChange}
  viewports={BUILDER_VIEWPORTS}
  ui={{ leftSideBarVisible: false, rightSideBarVisible: false }}
/>
```

**Confirmed:** `UiState.leftSideBarVisible` and `UiState.rightSideBarVisible` are both boolean props in the `UiState` type (verified from `actions-C3e2nJ9v.d.ts:541`). `<Puck>` accepts `ui?: Partial<UiState>` as an initial-state prop (verified from `index.d.ts:6302`). The `overrides.components` and `overrides.outline` are both present in the `Overrides` type (verified from `actions-C3e2nJ9v.d.ts`).

### Pattern 2: Native Puck Inline Text Editing

**What:** Set `contentEditable: true` on `text` and `textarea` field definitions in `puck-config.tsx`. Puck 0.21.2 renders an `InlineTextField` component on the canvas (a `<span contentEditable="plaintext-only">` that activates on hover/focus). On each input event, Puck dispatches a `replace` action which flows into the existing `onChange` callback → `useBuilderAutosave`.

**When to use:** For all text-bearing fields in Step, Heading, Text, Callout, StepWithPhotos, Hazard, Zone, Escalate blocks.

**Example:**
```typescript
// Source: node_modules/@puckeditor/core/dist/chunk-PK2F2YZX.mjs (InlineTextField)
// In puck-config.tsx — StepBlock.fields:
StepBlock: {
  fields: {
    number: { type: 'number', min: 1 },
    text: { type: 'textarea', contentEditable: true },  // ADD contentEditable
  },
  // ...
}

// HeadingBlock:
HeadingBlock: {
  fields: {
    text: { type: 'text', contentEditable: true },  // ADD contentEditable
    level: { type: 'select', options: [...] },
  },
  // ...
}
```

**InlineTextField behaviour (verified from Puck source):**
- Default: `contentEditable="false"` (non-editable span)
- On hover: `contentEditable="plaintext-only"` (editable)
- On focus: remains `contentEditable="plaintext-only"`
- On `input` event: dispatches `replace` action to Puck store at the correct `destinationIndex` / `destinationZone` (resolved from Puck's internal `nodes` index)
- `onChange` is called with the updated `Data` object → `useBuilderAutosave` picks it up
- Uses `registerOverlayPortal` to stop drag propagation while editing (prevents accidental block drags)

**D-04 compliance:** The InlineTextField activates on hover (not always-on), satisfying the click-to-edit requirement. The span starts `contentEditable="false"` and only becomes editable on hover/focus.

### Pattern 3: Programmatic Block Insert from AddMenu

**What:** Use `usePuck().dispatch` with an `InsertAction` to add a new block at a specific index. The root zone is `"root:default-zone"` (a.k.a. `rootDroppableId`).

**When to use:** In the AddMenu component when the user selects a block type.

**Example:**
```typescript
// Source: node_modules/@puckeditor/core/dist/actions-C3e2nJ9v.d.ts (InsertAction)
// node_modules/@puckeditor/core/dist/chunk-754HNMU2.mjs (rootDroppableId)
import { usePuck } from '@puckeditor/core'

function AddMenu({ insertAfterIndex }: { insertAfterIndex: number }) {
  const { dispatch } = usePuck()

  function handleAddBlock(componentType: string) {
    dispatch({
      type: 'insert',
      componentType,
      destinationIndex: insertAfterIndex + 1,
      destinationZone: 'root:default-zone',  // rootDroppableId
    })
    // After insert, caller must stamp junctionId if it's a library block
    // (for inline-authored blocks, no junctionId → graceful no-op in overlays)
  }
}
```

**junctionId stamping contract:** The `InsertAction` takes an optional `id` (Puck item id). For the "From library…" path, the existing `addBlockToSection` server action returns a junction id; the caller sets `props.junctionId` on the inserted item via a follow-up `replace` action (same pattern as Phase 13 block picker). For inline (non-library) blocks, no junctionId is stamped — overlays handle this gracefully.

**Important:** `usePuck()` is only callable from within the Puck component tree. The `AddMenu` must be rendered inside Puck's tree OR use `useGetPuck()` from outside. The cleanest approach: render `AddMenu` as part of the Puck `overrides.puck` wrapper or as a portal inside the canvas area, so `usePuck()` is in scope.

**Alternative for external use:** `useGetPuck()` returns a getter `() => UsePuckStore<Config>` that can be called outside Puck's tree. This allows `BuilderTreeRail` (rendered outside `<Puck>`) to dispatch inserts by capturing the getter at mount.

### Pattern 4: Step-Grouping Derivation (E1/E2/D-01/D-02)

**What:** Derive a presentation-only tree from the flat `layout_data.content[]` array. This is a pure transform — no mutations to `layout_data`.

**Data shape confirmed from codebase:**
```typescript
// layout_data.content[] items follow this shape:
type PuckItem = {
  type: string          // e.g. 'StepBlock', 'HazardCardBlock'
  props: {
    id: string          // Puck's canvas item id
    junctionId?: string // stamped by Phase 13 picker
    text?: string
    number?: number
    // ... block-specific props
  }
}
```

**Step types:** `StepBlock` | `StepWithPhotosBlock` (confirmed from `puck-config.tsx` fields definitions)

**Grouping algorithm (from D-01/D-02):**
```typescript
// Source: CONTEXT.md D-01/D-02 + puck-config.tsx type inspection
type TreeNode =
  | { kind: 'step'; item: PuckItem; stepNumber: number; children: PuckItem[] }
  | { kind: 'flat'; item: PuckItem }  // non-step section (D-02)

const STEP_TYPES = new Set(['StepBlock', 'StepWithPhotosBlock'])

function deriveStepTree(content: PuckItem[]): TreeNode[] {
  const hasSteps = content.some(item => STEP_TYPES.has(item.type))

  if (!hasSteps) {
    // D-02: all blocks as flat rows
    return content.map(item => ({ kind: 'flat', item }))
  }

  // D-01: step-centric with nesting
  const nodes: TreeNode[] = []
  let stepNumber = 0
  let current: TreeNode | null = null
  const preFlight: PuckItem[] = [] // blocks before first step

  for (const item of content) {
    if (STEP_TYPES.has(item.type)) {
      stepNumber++
      current = { kind: 'step', item, stepNumber, children: [] }
      nodes.push(current)
    } else if (current === null) {
      preFlight.push(item)
    } else {
      current.children.push(item)
    }
  }
  // preFlight blocks group under "section-start" header (E1)
  if (preFlight.length > 0) {
    nodes.unshift(...preFlight.map(item => ({ kind: 'flat' as const, item })))
  }
  return nodes
}
```

**Preview text extraction:** Use `item.props.text ?? item.props.title ?? item.props.label ?? item.props.prompt ?? ''` (covers all 16 block types). Truncate at 60 chars for step rows, 40 for child rows (per UI-SPEC copywriting contract).

### Anti-Patterns to Avoid

- **Don't wrap the right-side fields panel with a `display:none`** — Puck attaches event listeners to panels; hiding via CSS leaves listeners active and may conflict with structured-field popover positioning. Use `overrides.fields = () => <></>` to remove it cleanly if needed.
- **Don't add `contentEditable: true` to `array`, `select`, `radio`, `number` fields** — InlineTextField only applies to `text`, `textarea`, and `custom` field types per the Puck source. Structured fields must stay in the panel/popover.
- **Don't dispatch `insert` outside the Puck tree without `useGetPuck()`** — `usePuck()` throws outside of Puck's context. Use `useGetPuck()` for `BuilderTreeRail` since it renders outside `<Puck>`.
- **Don't call `setUi({ leftSideBarVisible: false })` repeatedly** — use the initial `ui` prop on `<Puck>` mount; repeated `setUi` dispatches during render cause Puck internal state conflicts.
- **Don't rename the `"Unanchored figures"` string in `parsed-sop-to-layout-data.ts`** — E6 is a display-only relabel. The parser string stays unchanged; the `BuilderTreeRail` and canvas render check for the title at display time. Changing the parser would break existing saved SOPs.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Inline text editing on canvas | Custom contentEditable sync | Puck's native `contentEditable: true` on field definitions | Puck handles caret placement, input sync, dispatch to store, and overlay portal registration (stops drag-while-editing bugs) |
| Programmatic block insert | Direct mutation of `layout_data` | `usePuck().dispatch({ type: 'insert', ... })` | Puck manages internal zones index, node tree, history — direct mutation corrupts state |
| Hiding Puck sidebars | CSS `display:none` | `overrides.components`, `overrides.outline`, `ui` prop | CSS hides visually but leaves listeners; overrides are the clean removal path |
| Section drag-reorder | New DnD implementation | Fold HTML5 drag logic from `SectionListSidebar.tsx` | Already tested, uses `reorderSections` RPC, handles optimistic revert |

**Key insight:** Puck 0.21.2 already has the inline editing primitive built-in — the `contentEditable: true` field option is exactly the click-to-edit canvas behaviour specified in D-04. Using it costs one line per field; bypassing it would require hundreds of lines of contentEditable sync code with identical edge-case handling.

### Q2: Hiding Puck's Native Palette + Outline (E3 / D-01/D-03) — RESOLVED

- `components: RenderFunc` — wraps the entire component palette. Return `<></>` to suppress it. [VERIFIED: puck type definition]

- `ui?: Partial<UiState>` is a `<Puck>` prop. `UiState.leftSideBarVisible: boolean` and `UiState.rightSideBarVisible: boolean` are confirmed. [VERIFIED: puck type definition]

**What must be preserved in `createPuckOverrides()`:**
- `componentItem` — `BlockOverflowMenu` three-dot menu (Phase 13 library save)
- `componentOverlay` — `UpdateAvailableBadge` + `ReviewerFlagsPanel` + `SelectionSyncTap` (E7)

**What can be hidden without breakage:**
- `components` — the palette drawer
- `outline` — the layer tree

### Q3: Programmatic Block Insert (D-03) — RESOLVED

**Answer: Use `usePuck().dispatch(InsertAction)` with `destinationZone: "root:default-zone"`.**

- `InsertAction` shape: `{ type: "insert", componentType: string, destinationIndex: number, destinationZone: string, id?: string }` [VERIFIED: puck type definition]
- Root zone: `"root:default-zone"` (= `rootDroppableId` = `${rootAreaId}:${rootZone}` = `"root:default-zone"`) [VERIFIED: puck source chunk-754HNMU2.mjs]
- `usePuck()` must be called inside Puck's component tree (throws outside). `BuilderTreeRail` renders OUTSIDE `<Puck>` → must use `useGetPuck()` which returns a getter callable anywhere. [VERIFIED: puck exported functions]
- After insert, the new item appears in `onChange`'s next `Data` — `useBuilderAutosave` picks it up automatically.

**Integration with Phase 13 library picker:** The "From library…" flow uses `addBlockToSection` (server action) + the existing block picker modal. After the modal resolves with a `blockContent`, the caller: (1) inserts a new Puck item via `dispatch`, (2) receives the new item's `id` from the Puck store, (3) stamps `junctionId` via a follow-up `replace` action. This is the same contract as the existing Phase 13 wizard (confirmed in `sop-section-blocks.ts` comment: "caller is responsible for stamping `props.junctionId`").

## Common Pitfalls

### Pitfall 1: `usePuck()` Outside Puck Tree
**What goes wrong:** `BuilderTreeRail` renders adjacent to `<Puck>`, not inside it. Calling `usePuck()` throws: "usePuck must be used inside a Puck component".
**Why it happens:** Puck uses React context; the context is only available inside the `<Puck>` component tree.
**How to avoid:** Use `useGetPuck()` in `BuilderTreeRail` instead. `useGetPuck()` returns a stable getter function `() => UsePuckStore<Config>` that can be called at any time from outside the tree.
**Warning signs:** "usePuck must be used inside a Puck component" runtime error on mount of `BuilderTreeRail`.

### Pitfall 2: `InsertAction` destinationZone Wrong
**What goes wrong:** Block inserts into a DropZone that doesn't exist, silently fails, or inserts at wrong location.
**Why it happens:** Puck's root content zone is `"root:default-zone"` — this is not obvious from the API; it's derived from two internal constants (`rootAreaId = "root"`, `rootZone = "default-zone"`).
**How to avoid:** Hard-code `destinationZone: 'root:default-zone'` in `AddMenu`'s dispatch call (verified from Puck source `chunk-754HNMU2.mjs`).
**Warning signs:** Insert silently has no effect; Puck console error about unknown zone.

### Pitfall 3: contentEditable Strips Other Props
**What goes wrong:** InlineTextField calls `setDeep(node.data.props, propPath, value)` then dispatches a `replace` with only the modified prop tree. If `setDeep` has a bug or the prop path is wrong, `junctionId` or other props could be lost.
**Why it happens:** The `setDeep` utility does a deep merge; it should preserve sibling keys. But if `propPath` is misconfigured (e.g. nested vs flat), it could create a nested key instead of updating the flat prop.
**How to avoid:** Set `contentEditable: true` only on top-level props (e.g. `text`, `content`, `title`) — all of these are flat string props, so `propPath` is a single-segment path. Do not attempt inline editing of nested props (array items, etc.).
**Warning signs:** After inline edit, the block loses its `junctionId` or other props; `componentOverlay` shows no badge where one was expected.

### Pitfall 4: Conflicting contentEditable + Puck Drag
**What goes wrong:** Clicking on an inline-editable block text area accidentally starts a drag on the block.
**Why it happens:** Puck's drag system uses `pointerdown` events; contentEditable elements need `pointerdown` to place the caret. Without intervention, both fire.
**How to avoid:** Puck's `InlineTextField` already calls `registerOverlayPortal` on the span, which stops `pointerdown` propagation during focus. This is handled natively — no extra code needed.
**Warning signs:** Clicking on step text starts dragging the block instead of focusing the text.

### Pitfall 5: Puck Left Sidebar State Persisting
**What goes wrong:** The left sidebar re-appears after section change or Puck remount because the `key={activeSection.id}` remount recreates Puck with default UI state.
**Why it happens:** When `<Puck key={activeSection.id}>` remounts (new section), the `ui` prop is applied fresh. If the `ui` prop is not passed, Puck defaults to `leftSideBarVisible: true`.
**How to avoid:** Always pass `ui={{ leftSideBarVisible: false, rightSideBarVisible: false }}` on the `<Puck>` element. Because it's a prop (not just an initializer), Puck will respect it on every remount.
**Warning signs:** Left sidebar flashes on section change.

### Pitfall 6: Reference Images Label Override Mutates layout_data
**What goes wrong:** If `sanitizedInitial` post-processes the HeadingBlock text to say "Reference images", this mutation is visible to `onChange` and gets autosaved back to Dexie/Supabase, overwriting the original "Unanchored figures (review)" string permanently.
**Why it happens:** `onChange` fires on ANY `Data` change, including the initial sanitized data if Puck sees it as a change.
**How to avoid:** Do NOT rename the title in `sanitizedInitial`. Apply the label substitution only in `BuilderTreeRail` (where you read `item.props.text` for display) and in the canvas via `componentOverlay` (which renders OVER the block without changing props). The `layout_data` stored in Dexie/Supabase keeps the original "Unanchored figures (review)" string.

### Pitfall 7: New lint spec not registered in playwright.config.ts
**What goes wrong:** A new `tests/lint/no-raw-block-types-in-build.spec.ts` (E2 guard) is created but no `playwright.config.ts` project's `testMatch` includes it → spec never runs in CI.
**Why it happens:** Known pattern from CLAUDE.md learning 2026-05-25.
**How to avoid:** After creating any new spec under `tests/lint/` or `tests/builder/`, immediately add its filename to the `phase15-stubs` regex (or a new `phase21.6-stubs` project regex) in `playwright.config.ts`. Validate with: `npx playwright test --list --project=phase21.6-stubs | grep <filename>`.
