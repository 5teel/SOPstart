# Phase 21.6: Builder Edit Stage Redesign - Context

**Gathered:** 2026-06-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Reconfigure the existing Puck-based **Build/edit stage** of the admin SOP builder so a first-time admin thinks in **Steps** (not "Blocks"): one ordered, humanised step list as the spine, no block-type jargon, the redundant second list removed, and text edited inline on the central canvas. UI-led, in place — no change to `layout_data`, autosave, junctionId stamping, AI overlays, or the publish gate. Review/Publish stages (21.5) and AI photo-anchoring (deferred to 21.7) are out of scope.

</domain>

<decisions>
## Implementation Decisions

### Sections + Steps layout
- **D-01:** Use a **single collapsible left rail = nested tree** (`Section ▸ Steps`), NOT two columns and NOT a section switcher. Sections are parent rows (retain drag-reorder per E5), steps are children under the expanded section. The canvas takes all remaining width so inline editing + structured-field popovers have room (works at ≥768px). This satisfies E5 (sections clearly distinct from steps) within one rail and replaces both the standalone `SectionListSidebar` neighbour role and Puck's native outline.

### Non-step sections
- **D-02:** Sections with **no** `StepBlock`/`StepWithPhotosBlock` (e.g. "Tools & Materials" = all PPE/Photo/Hazard) present **each top-level block as its own humanised row** — no forced "Step N", no synthetic pseudo-steps. This is the same rule as SPEC E1's "blocks before the first step group under a section-start header": when a section has zero steps, every block is effectively a section-start row. Sections WITH steps still number steps (Step 1, 2…) and nest other blocks under the nearest preceding step.

### Add step / add block flow
- **D-03:** Replace Puck's removed palette with a **single "＋ Add" control** that opens a menu of **humanised** block types PLUS a "From library…" entry that preserves the shipped Phase 13 global-block picker (`addBlockToSection` / "Pick from library" wizard). A new item inserts **after the currently selected step**, or at **section end** when nothing is selected. Do NOT drop the library picker — global blocks are a shipped feature.

### Inline editing surface
- **D-04:** **Click-to-edit** text on the canvas (caret on click — NOT always-on `contentEditable`, which risks accidental edits to safety-critical content). Structured fields (photo layout enum, decision branches, measurement units, etc.) open in a **popover anchored to the selected block**, keeping attention on the canvas. The planner MAY fall back to a **slim contextual rail** for the few high-complexity blocks (e.g. Decision arrays, Measurement) if a popover proves cramped — that fallback is allowed, not mandated. All edits persist through the existing `useBuilderAutosave` → Dexie → `useDraftLayoutSync` → Supabase path.

### Claude's Discretion
- Exact Puck override mechanics to hide the native palette/outline, and whether the step tree is a custom React rail vs a Puck `overrides.outline` replacement — planner/researcher's call, as long as one persistent list results (E3) and Puck's data/autosave/junction wiring stays intact (E7).
- Inline-edit implementation (Puck field `render` with `contentEditable`, a custom canvas editor, etc.) — researcher should confirm Puck's inline-edit capability; behaviour (click-to-edit) and persistence path are fixed, mechanism is open.
- Whether the slim-rail fallback (D-04) is needed for Decision/Measurement — decide during planning after assessing popover real estate.

</decisions>

## Existing Code Insights

### Reusable Assets
- `humanizeBlockType` / `BLOCK_TYPE_LABELS` (`block-type-labels.ts`) — the single label + semantic-pill source; already used by `NavRow`/`BlockChecklistRow`, now extend to the Build step list + Add menu.
- Phase 13 `addBlockToSection` + "Pick from library" wizard / block picker — reuse behind the "From library…" entry of the new "＋ Add" menu (D-03).
- `SectionListSidebar` drag-reorder logic (`reorderSections` RPC, optimistic update) — fold into the nested-tree section rows.
- `createPuckOverrides` (`componentOverlay`) — keep for AI flag overlays + update badges; the inline-edit + one-list changes must not remove this wiring (E7).
- 21.5 components (`BuilderStageStepper`, `NavRow`) — visual/label precedent for humanised, pill-coded rows in the same paper/ink system.

### Established Patterns
- Flat `layout_data` per section, 16 Puck block types; a "step" = `StepBlock` / `StepWithPhotosBlock`. Step-grouping is presentation-only over this flat list (SPEC E1, D-01/D-02).
- Autosave is `onChange` → `useBuilderAutosave` (Dexie) → `useDraftLayoutSync` (Supabase). Any new editing surface must route through this, not a parallel path (E7).
- junctionId stamped onto Puck items drives the publish gate + 13-04 update badges — must remain intact through any list/add/edit refactor.
- New `tests/lint/*` or stub specs MUST be registered in a `playwright.config.ts` project regex (CLAUDE.md learning 2026-05-25) — applies to E2/E7 guards.

### Integration Points
- The nested-tree rail replaces both `SectionListSidebar`'s neighbour role and Puck's native outline; Puck's canvas stays as the center editing surface.
- The "＋ Add" menu connects to Puck's add-component path + Phase 13 `addBlockToSection`.
- Inline edit connects block text fields to the existing autosave `onChange`.

</code_context>

<specifics>
## Specific Ideas

- "Users think in **Steps**, not Blocks — align the UI to the user's thinking; make blocks a sub-class of steps" (Simon, 21.5 UAT) → presentation-layer step nesting (D-01/D-02), not a data-model change.
- Orphan photos are "an AI-review problem to fix — there should be zero unanchored photos; any photo the AI omits must carry an explicit AI-written reason" (Simon) → this phase only relabels the gallery (E6); the AI capability is Phase 21.7.
- Visual language follows the validated paper/ink + JetBrains Mono + 6-semantic-pill system from `sketch-findings-SOPstart`, consistent with the 21.5 Review/Publish stages.

</specifics>
