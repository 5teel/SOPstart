# Phase 21.6: Code Review Report

**Reviewed:** 2026-06-05
**Depth:** standard
**Files Reviewed:** 11
**Status:** issues_found

## Summary

Phase 21.6 reconfigured the SOP builder's Build stage around a step-centric tree rail, inline canvas editing, and humanised block-type labels. The E7 safety-critical wiring (autosave, junctionId stamping, publish gate, AI overlay) is intact. The E2 lint guard, E3/E4/E5/E6 structural invariants, and the no-bulk-verify-ui guard all pass correctly.

However, the integration wiring has one critical gap: the `addMenuOpen` state flag is never set to `true` anywhere in the codebase, so the `AddMenu` component is permanently unreachable. The "＋ Add step or block" button in `BuilderTreeRail` has an intentionally empty `onClick` that was documented as "AddMenu wired in Plan 04" — but Plan 05 (integration) never completed this wiring, and the `BuilderClient` has no mechanism to open the menu either. This means E3's "single explicit add affordance" is unresponsive in production.

Four warnings are also present: a computed variable that is derived but silently discarded, a stale-prop issue with section ordering, an event-listener closure that only partially closes over `onClose`, and a missing `aria-modal` on the dialog popover. Three info items cover dead code, duplicate function definitions, and a test-file assertion gap.

## Critical Issues

### CR-01: AddMenu is permanently unreachable — add-control `onClick` is a no-op and `setAddMenuOpen(true)` is never called

**File:** `src/components/admin/builder/BuilderTreeRail.tsx:385` and `src/app/(protected)/admin/sops/builder/[sopId]/BuilderClient.tsx:317`

**Issue:** The "＋ Add step or block" button in `BuilderTreeRail` (`data-testid="add-control"`) has `onClick={() => { /* AddMenu wired in Plan 04 */ }}` — a complete no-op. Plan 05 was supposed to wire this but instead added `addMenuOpen` state and the `AddMenu` JSX block in `BuilderClient`. However, `setAddMenuOpen(true)` is called nowhere in the entire codebase. The only calls to `setAddMenuOpen` are to `false` (close). The menu can never open.

This breaks E3 ("a single explicit add control inserts a humanised-typed block") entirely: the add affordance is visible but completely inert. The only way to add a new block is via drag-from-palette, which is now hidden (null-rendered). New-content insertion in the Build stage is blocked for all users.

**Fix:** The add-control `onClick` in `BuilderTreeRail` needs to call the parent-provided open callback. The component needs a new prop, and `BuilderClient` needs to wire it:

```tsx
// BuilderTreeRail.tsx — add to Props interface:
onOpenAddMenu?: () => void

// BuilderTreeRail.tsx — replace the no-op onClick at line 385:
onClick={() => {
  onStepSelect?.(activeStepIndex ?? -1)
  onOpenAddMenu?.()
}}

// BuilderClient.tsx — add to BuilderTreeRail mount (line 467):
onOpenAddMenu={() => setAddMenuOpen(true)}
```

The `insertBlock` function defined inside `BuilderTreeRail` (lines 187–195) is also dead code as a consequence — it is never called because `AddMenu` (which should be the caller) is never opened from the rail. Once the open wiring is fixed, `AddMenu` already handles dispatch via its own `useGetPuck` call, so the `insertBlock` helper in `BuilderTreeRail` can remain as a secondary dispatch path or be removed.

## Warnings

### WR-01: `displayLabel` variable computed but silently discarded in flat-node branch

**File:** `src/components/admin/builder/BuilderTreeRail.tsx:339`

**Issue:** Inside the `stepTree.map` callback, when `node.kind === 'flat'`, the code computes `const displayLabel = getDisplayLabel(node.item)` on line 339 but never uses the variable — `<TreeBlockRow>` is rendered without passing `displayLabel` or any override label to it. `TreeBlockRow` re-derives the label internally via `humanizeBlockType`. The E6 "Reference images" substitution computed in `getDisplayLabel` (which checks for `'Unanchored figures'` heading text) is therefore silently lost for flat nodes rendered in the tree rail. Only the `componentOverlay` chip in `puck-config.tsx` applies the E6 relabelling for the canvas; the rail itself shows the heading's plain `humanizeBlockType` label (which is "Heading") — not "Reference images".

This is a correctness gap for E6: the spec requires "Orphan photos render under a humanised 'Reference images' label" in the Build stage. The canvas chip handles it for the Puck canvas view, but the tree rail silently drops the substitution.

**Fix:** Either pass `displayLabel` through to `TreeBlockRow` via an optional `overrideLabel` prop, or apply the E6 check inside `TreeBlockRow` itself:

```tsx
// Option A — add overrideLabel prop to TreeBlockRow and use it in the label span:
<TreeBlockRow
  key={node.item.props?.id ?? nodeIdx}
  item={{ ...node.item }}
  overrideLabel={displayLabel}  // use the already-computed value
  onSelect={() => {}}
/>

// Option B — move getDisplayLabel logic into TreeBlockRow.tsx
// and call it from the label render path there.
```

### WR-02: `order` state in `BuilderTreeRail` is seeded once from `sections` prop and never re-synced when the prop changes

**File:** `src/components/admin/builder/BuilderTreeRail.tsx:168`

**Issue:** `const [order, setOrder] = useState<SectionLite[]>(() => [...sections].sort(...))` seeds the local display order from the `sections` prop at mount time. If `BuilderClient` re-renders with a new `sections` array (e.g. after a server-side section add/rename upstream of `BuilderClient`), the displayed order in the rail becomes stale and diverges from the server state. The only update path is the optimistic `commitReorder` call, which handles the drag-drop case but not external changes.

In practice, `BuilderClient` receives `initialSop` once from RSC and does not re-fetch sections on the client, so this cannot be triggered by the current architecture. However, if an upstream parent ever refreshes `sections` (e.g. after adding a new section), the rail would silently show the old order.

**Fix:** Add a synchronisation effect:

```tsx
useEffect(() => {
  setOrder([...sections].sort((a, b) => a.sort_order - b.sort_order))
}, [sections])
```

This is safe because the optimistic update also calls `setOrder` directly; the effect only fires when the prop identity changes (i.e. a genuine external update).

### WR-03: `StructuredFieldPopover` Escape-key listener depends on `onClose` identity — can miss closes if parent re-renders

**File:** `src/components/admin/builder/StructuredFieldPopover.tsx:54`

**Issue:** The Escape-key `useEffect` has `[onClose]` in its dependency array. In `BuilderClient`, `onClose` is an inline arrow function `() => { setSelectedBlockId(null); setSelectedBlockType(null) }` defined directly in JSX (line 507). Inline arrow functions have a new identity on every render, so the effect tears down and re-adds the `window` listener on every `BuilderClient` render. This is not a security issue but creates unnecessary churn. More critically, the mousedown click-outside listener (lines 65–74) has the same pattern — both listeners are re-registered on every parent render, creating a brief window between teardown and re-add where an Escape keypress could go unhandled.

**Fix:** Stabilise the `onClose` callback in `BuilderClient` with `useCallback`:

```tsx
const handlePopoverClose = useCallback(() => {
  setSelectedBlockId(null)
  setSelectedBlockType(null)
}, [])

// Then pass it:
<StructuredFieldPopover
  ...
  onClose={handlePopoverClose}
/>
```

### WR-04: `StructuredFieldPopover` is missing `aria-modal="true"` on its dialog element

**File:** `src/components/admin/builder/StructuredFieldPopover.tsx:96`

**Issue:** The popover uses `role="dialog"` but omits `aria-modal="true"`. For `role="dialog"`, screen readers (particularly NVDA and VoiceOver with browse mode) will read behind the dialog into the canvas content when `aria-modal` is absent, as the dialog is not technically trapping focus (there is no focus trap implemented either). This breaks AT usability when the popover is open.

**Fix:**

```tsx
<div
  ref={popoverRef}
  role="dialog"
  aria-modal="true"
  aria-label={`Edit ${humanizeBlockType(blockType)} fields`}
  data-testid="structured-field-popover"
  ...
>
```

A focus trap (moving focus to the first interactive element in the popover on open, returning focus on close) would be the complete fix, but `aria-modal` alone is the minimum for screen-reader correctness.

## Info

### IN-01: `insertBlock` function in `BuilderTreeRail` is dead code

**File:** `src/components/admin/builder/BuilderTreeRail.tsx:187`

**Issue:** The `insertBlock(componentType, afterIndex)` helper defined inside `BuilderTreeRail` is never called. It was documented as "dispatch wired in Plan 04; defined here as source of truth" — but `AddMenu` has its own `useGetPuck`/dispatch logic and the add-control button never fires (CR-01). This function is unreachable dead code. It also captures `getPuck` from the outer component scope, making it a closure over a hook call, which is valid but unnecessary if the function is removed.

**Fix:** Remove the function after fixing CR-01. If a centralised insert path through the rail is desired for future use, keep it but document the intent clearly.

### IN-02: `getPillStyle` is defined three times verbatim across `TreeStepRow.tsx`, `TreeBlockRow.tsx`, `BuilderTreeRail.tsx`, and `AddMenu.tsx`

**File:** `src/components/admin/builder/TreeStepRow.tsx:51`, `src/components/admin/builder/TreeBlockRow.tsx:35`, `src/components/admin/builder/BuilderTreeRail.tsx:135`, `src/components/admin/builder/AddMenu.tsx:30`

**Issue:** The same 30-line `getPillStyle` switch is copy-pasted into four files. The summaries acknowledge this ("verbatim from NavRow.tsx") but the duplication now spans 4 builder files plus the pre-existing NavRow.tsx — 5 copies total. Any future pill variant addition requires 5 edits. This is below the threshold for a Warning given the codebase's explicit convention, but the duplication has grown past what was planned.

**Fix:** Extract to `src/components/admin/builder/pill-style.ts` and import from all four builder files. This was noted as a "shared implementation" concern but deferred; now that four copies exist in a single directory, extraction is straightforward.

### IN-03: E6 test assertion in `builder-edit-stage.spec.ts` only checks `BuilderTreeRail.tsx` — does not guard `puck-config.tsx` canvas chip

**File:** `tests/builder/builder-edit-stage.spec.ts:84`

**Issue:** The E6 test verifies the "Reference images" label exists in `BuilderTreeRail.tsx` and that "Unanchored figures" doesn't leak in that file. However, the E6 canvas chip implementation landed in `puck-config.tsx` (Plan 05). If the chip is accidentally removed from `puck-config.tsx` in a future phase, no test will catch it. The E6 requirement covers "render under a humanised 'Reference images' label" — which now requires both the rail label and the canvas chip.

**Fix:** Add a second assertion in the E6 test block:

```ts
test('E6: BuilderTreeRail uses "Reference images" label; does not leak "Unanchored figures"', () => {
  const railSrc = readSrc('src/components/admin/builder/BuilderTreeRail.tsx')
  // ... existing assertions ...

  // Also assert the canvas chip in puck-config
  const puckSrc = readSrc('src/lib/builder/puck-config.tsx')
  expect(puckSrc, 'puck-config componentOverlay must render "Reference images" chip').toContain('Reference images')
  expect(puckSrc, 'puck-config must guard with startsWith("Unanchored figures")').toContain("startsWith('Unanchored figures')")
})
```
