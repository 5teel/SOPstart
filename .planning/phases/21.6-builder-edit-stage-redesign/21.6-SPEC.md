# Phase 21.6: Builder Edit Stage Redesign — Specification

**Created:** 2026-06-05
**Ambiguity score:** 0.19 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

A first-time admin editing an SOP in the **Build stage** thinks in **Steps** (not "Blocks"): one ordered, humanised step list is the spine, block-type jargon is gone, the redundant second list is removed, and text is edited inline on the central canvas — all by reconfiguring the existing Puck editor in place, with no change to `layout_data`, autosave, junctionId stamping, or the publish gate.

## Background

The Build stage renders `BuilderClient` (`src/app/(protected)/admin/sops/builder/[sopId]/BuilderClient.tsx:329-404`): a 48px header + `SectionListSidebar` (256px) + the Puck editor (`src/lib/builder/puck-config.tsx`). Phase 21.5 redesigned the **Review** and **Publish** stages but left Build untouched. Current first-run problems, confirmed in 21.5 UAT:

- **Jargon** — Puck's palette and outline render raw type names ("StepBlock", "PhotoBlock", "HazardCardBlock"). `humanizeBlockType` / `BLOCK_TYPE_LABELS` exist (`src/lib/builder/block-type-labels.ts`, built in 21.5) but are consumed **only** by `BlockChecklistRow` and `NavRow` — never by Puck.
- **Two redundant lists** — Puck shows both a component palette (drag to *add* new) and an outline tree (*placed* blocks), with no clear differentiation.
- **No step mental model** — `layout_data` is a flat list of 16 block types per section; `StepBlock`/`StepWithPhotosBlock` are siblings of the rest, so nothing presents the SOP as an ordered sequence of steps the way users think about it.
- **Cramped editing** — block content is edited only in Puck's narrow right-side fields panel (~320–360px); there is no inline/canvas editing.
- **Unanchored figures** — the parser dumps orphan images as a `PhotoGridBlock` titled "Unanchored figures (review)" (`src/lib/parsers/parsed-sop-to-layout-data.ts:340-361`).

This phase is UI-led (reconfigure Puck in place) and produces a UI-SPEC downstream.

## Requirements

1. **E1 — Step-centric ordered list (the spine)**: The Build stage presents an ordered, humanised list of Steps as the primary in-section navigation.
   - Current: The active section is navigated via Puck's flat outline of raw block types; no step-centric framing.
   - Target: For the active section, an ordered list shows humanised **Steps** (numbered by position, e.g. "Step 1, 2, 3…") as the spine; selecting a step focuses it on the canvas. A "step" = `StepBlock`/`StepWithPhotosBlock`; every non-step block groups under its **nearest preceding step** for display (blocks before the first step group under a clear "section start" header). Grouping is presentation-only — `layout_data` stays flat.
   - Acceptance: A section with K step blocks renders K numbered "Step N" entries in source order; each non-step block appears nested under the correct step (or the section-start header); no raw block-type name appears in the list.

2. **E2 — Humanised labels everywhere in Build (no jargon)**: Every block-type label shown in the Build stage uses the 21.5 label map.
   - Current: Puck palette + outline render raw PascalCase type names; `humanizeBlockType` is unused in Build.
   - Target: All block-type labels rendered anywhere in the Build stage (step list, nested block chips, the add-block menu, any palette) resolve through `humanizeBlockType` / `BLOCK_TYPE_LABELS`. No raw PascalCase type, `"*Block"`, `"Grid"`, or `"PhotoGrid"` symbol leaks to the UI.
   - Acceptance: A Playwright source/render guard finds zero raw block-type identifiers rendered in the Build stage; `humanizeBlockType` is the single label source consumed by the Puck-facing surfaces.

3. **E3 — One content list, not two**: The redundant palette + outline collapse into a single list plus a deliberate add affordance.
   - Current: Puck shows both an always-on component palette (add) and an outline tree (placed) simultaneously.
   - Target: The Build stage presents exactly one persistent content list (the E1 Steps spine). Inserting a new step/block is a single explicit "＋ Add" control (button/menu of humanised types), not a second always-on palette list. The redundant second list is removed/hidden.
   - Acceptance: The Build stage renders exactly one persistent content list (no simultaneous always-on palette AND outline); an "Add" control exists and inserts a block whose label is humanised.

4. **E4 — Inline content editing on the canvas**: Text-bearing content is edited in place on the central canvas.
   - Current: Block content is editable only in Puck's narrow right-side fields panel; no inline/canvas editing.
   - Target: Text-bearing content (step text, headings, callout/body text) is editable inline on the central canvas (click-to-edit in place). Structured fields (photo layout enum, decision branches, measurement units, etc.) remain editable via a compact panel/popover. Edits persist through the existing autosave path (`useBuilderAutosave` → Dexie → Supabase).
   - Acceptance: Clicking a text-bearing block on the canvas edits it in place; the change autosaves and persists after reload; structured-only fields remain reachable and editable; no field that was editable in the old panel becomes unreachable.

5. **E5 — Section-list clarity**: The section rail is clearly distinguished from the in-section step list.
   - Current: `SectionListSidebar` lists section titles by `sort_order` with drag-reorder, but its purpose vs the block lists is unclear to first-timers.
   - Target: The section rail is visually and textually identified as the SOP's **sections** (distinct from the step list within a section), retains explicit `sort_order` ordering and drag-reorder, and reads clearly as "the chapters of this SOP".
   - Acceptance: The section rail carries a clear heading/label identifying it as sections; sections render in `sort_order`; reorder still works; (first-time-admin can distinguish sections from steps — confirmed via live UAT).

6. **E6 — Orphan photos as a labelled reference gallery (display only)**: Unanchored images render cleanly with no manual attach UI and no gate change.
   - Current: Orphan images render as a `PhotoGridBlock` titled "Unanchored figures (review)".
   - Target: In the Build stage, orphan/unanchored images render under a humanised, non-alarming "Reference images" label, with NO manual drag-to-attach UI and NO publish-gate condition added. (Eliminating orphans via AI is deferred to Phase 21.7.)
   - Acceptance: Orphan images appear under a humanised "Reference images" (not "Unanchored figures") label; no manual attach control is present; no publish-gate rule references unanchored photos.

7. **E7 — No regression to safety-critical wiring**: The reconfigure preserves all data and gate behaviour.
   - Current: Build feeds autosave (Dexie→Supabase), junctionId stamping (publish gate + 13-04 update badges), AI reviewer flag overlays (`componentOverlay`), and the per-block verify checklist.
   - Target: After the redesign, the Puck engine, `layout_data` schema, junctionId stamping, autosave, AI flag overlays, the server `400 unverified_blocks` publish gate, the no-bulk-verify lint guard, and the 21.5 Review/Publish stages all continue to function unchanged.
   - Acceptance: Existing publish-gate behaviour (server 400) and `no-bulk-verify-ui` lint guard still pass; `layout_data` schema is unchanged; autosave + junction stamping verified intact; the 21.5 Review and Publish stages still work.

## Boundaries

**In scope:**
- Step-centric ordered list (humanised) as the Build-stage spine, with presentation-only nesting of non-step blocks under their nearest step
- Humanising every block-type label in the Build stage (reuse `humanizeBlockType` / `block-type-labels.ts`)
- Collapsing the palette + outline into one list with a single "＋ Add" affordance
- Inline canvas editing for text-bearing content; panel/popover for structured fields
- Section-rail clarity (labelling + ordering, keep drag-reorder)
- Rendering orphan photos as a labelled "Reference images" gallery (display only)
- Preserving autosave, `layout_data` schema, junctionId stamping, AI overlays, and the publish gate

**Out of scope:**
- AI anchoring of photos / AI-written omission reasons / zero-unanchored guarantee — Phase 21.7 (AI-pipeline workstream, not Build UI)
- Manual drag-to-attach UI for orphan photos — unnecessary once AI handles anchoring (21.7)
- Real data-model nesting (blocks as children of steps in `layout_data`) — contradicts reconfigure-in-place; avoids parser/schema/gate churn
- Replacing the Puck engine or re-architecting the editor — reconfigure in place only
- Changes to the Review or Publish stages — delivered in Phase 21.5
- Worker-facing walkthrough changes — unrelated workstream
- New block types — not part of this UX pass
- Any change to publish-gate rules — none

## Constraints

- Must reuse `src/lib/builder/block-type-labels.ts` (`humanizeBlockType`) as the single label source — no second mapping.
- Puck stays the engine; `layout_data` schema is unchanged; junctionId stamping stays intact (publish gate AND the 13-04 update badges depend on it).
- Autosave path (`useBuilderAutosave` → Dexie → `useDraftLayoutSync` → Supabase) is preserved.
- AI reviewer flag overlays (`componentOverlay` in `createPuckOverrides`) and the verify-checklist linkage are preserved.
- Presentation grouping must be deterministic (nearest-preceding-step rule; blocks before the first step under a "section start" header).
- Admin builder is desktop-first; the redesign should not break at tablet width (≥768px) — consistent with 21.5's responsive approach, but full mobile is not required.
- Windows / Next.js 16 build conventions apply; any new `tests/lint/*` or stub spec MUST be registered in a `playwright.config.ts` project regex (CLAUDE.md learning 2026-05-25).

## Acceptance Criteria

- [ ] Build-stage ordered list shows humanised "Step N" entries in source order; non-step blocks nest under the nearest preceding step (or section-start header)
- [ ] No raw block-type identifier (PascalCase `*Block` / `Grid` / `PhotoGrid`) renders anywhere in the Build stage (grep/Playwright guard, single `humanizeBlockType` source)
- [ ] Exactly one persistent content list in Build (no simultaneous always-on palette + outline); a single "＋ Add" control inserts a humanised-typed block
- [ ] Clicking a text-bearing block on the canvas edits it inline; the edit autosaves and persists after reload
- [ ] Structured fields (photo layout, decision options, measurement units) remain editable via panel/popover
- [ ] Section rail is clearly labelled as sections, renders in `sort_order`, and reorder still works
- [ ] Orphan photos render under a humanised "Reference images" label; no manual attach UI; no new publish-gate condition
- [ ] Server publish gate (`400 unverified_blocks`) + `no-bulk-verify-ui` lint guard still pass; `layout_data` schema unchanged; 21.5 Review/Publish stages unaffected
