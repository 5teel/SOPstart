# Plan 21-05 — Parser → Library Junction Integration (Gap Closure)

## Context

**Why this exists:** Phase 21 verifier (PASS-WITH-NOTES) and UAT discovery on 2026-05-25 found a structural gap: the Phase 21 verify checklist iterates `sop_section_blocks` junction rows, but the parser (Phase 12 path) writes Puck items only into `sop_sections.layout_data`. The two paths never met — every freshly parsed SOP has zero junction rows, so the publish gate's `verifiedCount === totalCount` degenerates to `0 === 0 = true` (no-op).

Simon's call (2026-05-25): "production-ready, not pilot-in-name. Extend the library to support every Puck kind so the architectural model is consistent." This rules out the lighter "orphan junction rows" or "separate verification table" alternatives — we ship the correct shape.

**Locked decisions still in force:** All D-21-01..D-21-13 from `21-CONTEXT.md` apply. This plan adds no new locked decisions; it implements the contract that was assumed to already work.

## Tasks

### Task 4 — Parser integration: createBlock + addBlockToSection per Puck item

In `src/lib/parsers/parsed-sop-to-layout-data.ts`:

1. Build a `puckPropsToBlockContent(itemType: string, props: Record<string, unknown>): BlockContent` adapter that strips presentation fields and returns valid BlockContent for each of the 17 Puck types. Zod-validate on the way out — throw on shape mismatch (per T-21-05-03).

2. Add a new exported function `materializeJunctionsForLayout(sopId, organisationId, sectionId, puckItems, supabaseAdmin)` that:
   - For each Puck item, calls `createBlock({ scope: 'org', kindSlug: <derived from itemType>, name: <auto-generated from content first 60 chars>, category: 'parsed_inline', content: puckPropsToBlockContent(...), organisationId })`
   - Then calls `addBlockToSection({ sopSectionId: sectionId, blockId: createdBlock.id, pinMode: 'pinned', blockProvenance: item.props.block_provenance })`
   - Mutates the Puck item in place: `item.props.junctionId = junction.id`
   - On ANY failure: throws an error that propagates up to the parse pipeline (per T-21-05-02 — no partial state)

3. Wire `materializeJunctionsForLayout` into the existing parser flow in `src/lib/parsers/parse-pipeline.ts` so each parsed section's items get junctions before `layout_data` is written. Order matters: createBlock+addBlockToSection FIRST, then UPDATE sop_sections.layout_data with the (now-junctionId-stamped) Puck items.

Acceptance:
- Integration test (`src/lib/parsers/__tests__/parser-creates-junctions.test.ts`): given a minimal extracted SOP, after `materializeJunctionsForLayout` runs, (a) blocks rows exist with `category='parsed_inline'`, (b) sop_section_blocks rows exist with `block_provenance` populated, (c) the returned puckItems all have `props.junctionId` set.
- A second test verifies partial-failure mode: forced error on item 3 of 5 throws and rolls back (or marks parse_job failed — no orphan rows committed).
