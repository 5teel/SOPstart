<objective>
CAP-02: sign-off authority on a SOP carries edit rights on that SOP, enforced server-side at both layers this codebase uses — a new object-level guard in the server actions, and the three content RLS policies as the backstop.

Today `sops.owner_user_id` can already be any org member (Phase 28 `setSopOwner` + `OwnerPicker` list every role), but ownership grants nothing: every content write is gated on `role IN ('admin','safety_manager')`. This plan closes exactly that gap and nothing wider.

Purpose: the locked meeting decision, in code rather than in a document — with the negative half proven, because this schema area has shipped two cross-tenant holes in the last month (00061, 00062).
Output: `requireSopEditAccess`, 9 guarded write paths, migration 00063 applied live, and the CAP-02 probe set green.

**Stated assumption (A1) — surface to Simon at verification:** "sign-off authority" is read as `sops.owner_user_id` (Phase 28's single accountable owner), not approval-chain approvers (Phase 29) and not completion sign-off (`signOffCompletion`, which is a supervisor confirming a *worker performed* the SOP — a different noun). If Simon means chain approvers, the fix is one predicate swap in `requireSopEditAccess` plus the same swap in the migration.

**Stated assumption (A2):** "edit" = SOP content (sections, steps, images, layout_data, block junctions). Publish, verify-blocks, delete, version-supersede/clone and owner-reassignment stay admin/safety_manager-only. Probe 7 in the live spec asserts this containment.

No route changes and no new screens (CONTEXT: "no route work"), so `src/lib/journeys/journeys.ts` needs no edit this phase — recorded here so the convention check is a decision, not an omission. A SOP owner without admin nav gains the server-side capability but not a UI path to it; that is intentional for Phase 46 and is recorded as RESEARCH Open Question 1.
</objective>
