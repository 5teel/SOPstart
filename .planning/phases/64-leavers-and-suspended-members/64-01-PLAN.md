<objective>
Ship the database half of membership states and prove it live before any app code depends on it: migration 00082 (status column, column-level UPDATE lock, RLS helpers that re-check the membership row on every call, the access-token hook skipping non-active rows, the raw-claim policies and the observations own-arm closed, `revoke_user_sessions`, three ledger kinds), the kind registries that are spec-locked to it, ADR-0024, and an apply script with audit, live assertions and a rollback.

**Ordering decision (schema push requirement).** The migration is applied to the live project in this plan, first, and every later plan's app code assumes it. That order is safe because 00082 is backwards compatible with the code deployed today: the new column defaults to `active` for every row; the redefined helpers return exactly the old values for an active member (and NULL instead of an enum-cast error for a `pending` claim); the hook change is a no-op for active rows; the UPDATE lock leaves `role` updatable, which is the only column the deployed code updates with a session client (`updateMemberRoleSafe`); `removeMember`'s service-role delete is untouched; the kind CHECK only widens. The reverse order (app first) would break every request, because app code filtering on `status` errors on a missing column. A `--rollback` mode restores the old helper and hook bodies within a minute if any live probe fails.

Decisions implemented: D-01 (three states, text + CHECK, `status_changed_at` / `status_changed_by`, backfill active), D-06 (every membership-resolving RLS path requires an active row; the token's organisation claim only selects the row), D-07 mechanism (`revoke_user_sessions`, service_role only, no ban), D-12 (kinds), D-13 (ADR-0024), D-19 (sop-videos SELECT scoped to the organisation folder when the live check allows it, else an accepted residual in the ADR), D-20 (IDs).

Purpose: the cut-off has to live in the database, because PostgREST and Storage read RLS with tokens that stay valid for up to an hour (RESEARCH Summary, Pitfall 1).
Output: 00082 live with assertions passing, 64-BASELINE.md, ADR-0024, registries, `phase64` project.
</objective>
