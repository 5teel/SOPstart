- D-01 — Dedicated org-scoped tables (`sop_agent_metadata` + `block_agent_metadata` + append-only memory/proposal tables) are the source of truth. `layout_data` stays FROZEN (26 D-01); agent metadata never rides on props and never touches the editor autosave path.

**Memory & learning proposals**
- D-05 — Memory scope: per-SOP + org-wide. Append-only observations tied to a SOP ("workers pause at step 4", "torque value flagged twice") plus org-level conventions ("this org says 'isolation' not 'lockout'").
- D-06 — All four signal sources feed the layer: (1) completion data — `sop_completions` + step ack traces; (2) AI-reviewer flags + verify send-back history; (3) voice Q&A transcripts; (4) admin edit patterns after AI drafts.
- D-07 — Learning proposals reuse the X-03 approval path, extended with structured evidence. Proposals ride `gateWrite` → `pending_approval` → admin review (no parallel approval machinery); the proposal record carries evidence (source memory rows, signal counts).

## Summary

This phase adds a parallel, admin-only "machine layer" over every published SOP: dedicated append-only Postgres tables (metadata, memory, proposals) populated by a real synthesis job, plus two UI surfaces (a builder toggle panel and an org dashboard). Architecturally this is the *easiest* kind of phase to plan safely — it is purely additive, follows THREE existing precedents almost exactly (00038 `ai_field_proposals`, 00039 `sop_image_annotations`, and the X-03 registry/approval spine), and touches the publish route only as a post-success hook. The two genuinely new pieces of technology are Voyage AI embeddings (a new external API + new npm dependency) and pgvector (a new Postgres extension, well-supported on Supabase). Scheduling has no existing precedent in this codebase, but Railway's native Cron Jobs feature (min. 5-minute interval, separate one-shot service, no shared in-memory state) is available and better-suited than a bespoke `node-cron` interval loop, which would violate the single-process/no-PM2-cluster assumption baked into every other scheduled-work discussion in this codebase.

The one real gap the planner must account for: **voice Q&A transcripts are not currently persisted anywhere.** `/api/voice/query/route.ts` calls `answerSopQuestion()` and returns the result directly — there is no `sop_voice_qa_log` table or equivalent. D-06 lists "voice Q&A transcripts" as signal source #3, but as of today that data simply does not exist to read. The plan must add a write path (or accept the source is degraded/absent until a follow-on phase adds it) — this is a blocking dependency, not a nice-to-have, for the synthesis job to be non-trivial on that signal.

The second thing the planner should flag back to the user (not silently override, per CONTEXT.md's own instruction not to downgrade the provider): Voyage AI's naming has moved on since "Voyage-3" was chosen — `voyage-3` (bare) is still available, but `voyage-3.5` and `voyage-3.5-lite` are the current-generation successors at the same $0.06/$0.02 per-1M-token price points and same 32k context, and `voyage-4` family has since shipped. This doesn't override the locked D-03 decision, but the model ID should live behind a shared constant + env override (matching the D-16 pattern) precisely so this kind of drift is a one-line change, not a re-plan.

**Primary recommendation:** Model this phase as three additive migrations (schema mirroring 00038/00039's append-only + org-scoped-SELECT-only shape) + one new lazy-init Voyage client (mirroring `verify-sop.ts`'s Anthropic pattern) + a post-publish hook that fires the synthesis pipeline + a Railway Cron-triggered catch-up route for the non-publish-triggered signals (completions, voice Q&A, reviewer flags) + two new UI surfaces reading through plain server actions (no new AI-fields registrations needed for read-only display; only the proposal-approve/decline actions extend `gateWrite`/`ai_field_proposals`... actually proposals here are a NEW evidence-carrying table, not reusing `ai_field_proposals` verbatim — see Pattern 3 below for the exact extension shape).

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Voyage-3 (locked D-03) | OpenAI `text-embedding-3-large` | Already installed `openai` SDK, zero new dependency — but D-03 explicitly rejected this after deliberate comparison (hard-negative retrieval quality for near-duplicate industrial SOPs). Do not silently substitute. |

### Pattern 1: Append-only, org-scoped, no-cross-table-policy schema (mirror 00038/00039)

**What:** Every new table follows the EXACT shape already used twice in this codebase: `organisation_id` direct column, RLS SELECT policy referencing `current_organisation_id()` ONLY (never joining `sops` or any other table from within the policy), NO authenticated INSERT/UPDATE/DELETE policy, writes exclusively via `createAdminClient()` in a server action that self-enforces org-scope.

**When to use:** All four new tables (`sop_agent_metadata`, `block_agent_metadata`, `agent_memory`, `agent_learning_proposals`).

**Example:**
```sql
-- Source: supabase/migrations/00039_sop_image_annotations.sql (verbatim pattern to copy)
create table if not exists public.sop_agent_metadata (
  id                uuid primary key default gen_random_uuid(),
  organisation_id   uuid not null references public.organisations(id) on delete cascade,
  sop_id            uuid not null references public.sops(id) on delete cascade,
  summary           text,
  tags              text[] not null default '{}',
  entities          jsonb not null default '[]'::jsonb,
  embedding         vector(1024),  -- voyage-3 default output dim; see Assumptions Log A2
  assessment        text not null default 'fresh' check (assessment in ('fresh','drifting','needs-review')),
  regenerated_at    timestamptz,
  created_at        timestamptz not null default now(),
  updated_at        timestamptz not null default now()
);

alter table public.sop_agent_metadata enable row level security;

-- CRITICAL: do NOT reference public.sops from this policy — 42P17 recursion risk
-- (CLAUDE.md 2026-05-13; matches 00038/00039 precedent exactly).
create policy "sop_agent_metadata_org_read" on public.sop_agent_metadata
  for select to authenticated
  using (organisation_id = public.current_organisation_id());

-- NO authenticated INSERT/UPDATE/DELETE policy — writes via createAdminClient()
-- in the synthesis pipeline, which MUST self-enforce org-scope (CLAUDE.md 2026-06-15).

create index if not exists idx_sop_agent_metadata_org on public.sop_agent_metadata(organisation_id);
create unique index if not exists idx_sop_agent_metadata_sop on public.sop_agent_metadata(sop_id);
create index if not exists idx_sop_agent_metadata_embedding on public.sop_agent_metadata
  using hnsw (embedding vector_cosine_ops);
```

### Pattern 2: Publish-hook integration — additive, fire-and-forget, does not touch the frozen gate

**What:** The existing publish route (`/api/sops/[sopId]/publish` — its internal gate logic is FROZEN per 26 D-01/D-02 and the 2026-07-03 full-bespoke-swap learning) gets exactly one new line: after the existing 200 response logic succeeds, fire the synthesis job. Follow the SAME fire-and-forget pattern already used for the AI reviewer (SCP-AI-06 — "all five jobs auto-run on first parse without admin invocation").

**When to use:** D-04 (generate/refresh on publish).

**Example:**
```typescript
// Source: pattern matches src/lib/parsers/ai-reviewer orchestration being
// fired non-blocking from parse-completion sites (Phase 21 SCP-AI-06).
// Inside the publish route, AFTER the existing gate/response logic:
if (publishSucceeded) {
  // Fire-and-forget — do not await, do not block the publish response.
  // Errors are caught and logged; a failed synthesis run does NOT fail publish.
  triggerAgentSynthesis(sopId, organisationId).catch((err) => {
    console.error('[agent-layer] synthesis trigger failed:', err instanceof Error ? err.message : err)
  })
}
```

### Pattern 3: Extending X-03 for evidence-backed proposals (sibling table, not shared table)

**What:** `agent_learning_proposals` is a NEW table shaped like `ai_field_proposals` (same append-only + org-scoped-SELECT + service-role-write shape) but with an `evidence jsonb` column carrying the memory rows / signal counts that justify the proposal, per D-07. The *behaviour* — pending → admin approves/declines → status flips — reuses the exact state machine `gateWrite`/`acceptProposal`/`rejectProposal` already implement; only the schema is a sibling, not a shared row shape, because `ai_field_proposals.context`/`field_id` are single-field-write-specific and don't carry evidence.

**When to use:** D-07 proposal creation + D-10 admin approve/decline actions in the panel/dashboard.

**Example:**
```typescript
// Source: src/lib/ai-fields/approval.ts gateWrite — the SAME two-path shape
// (auto-apply vs pending_approval) generalizes here, but proposals from the
// agent layer are ALWAYS pending (never auto-applied — D-07/D-10: admins
// review every proposal, there is no "low-stake" tier for learning proposals).
export async function createLearningProposal(
  organisationId: string,
  sopId: string,
  proposal: { kind: string; description: string; evidence: EvidenceRow[] },
): Promise<string> {
  const admin = createAdminClient()
  const { data, error } = await admin
    .from('agent_learning_proposals')
    .insert({
      organisation_id: organisationId,   // self-enforced — service-role bypasses RLS
      sop_id: sopId,
      kind: proposal.kind,
      description: proposal.description,
      evidence: proposal.evidence as unknown as Json,
      status: 'pending',
    })
    .select('id')
    .single()
  if (error || !data) throw new Error(`[agent-layer] proposal insert failed: ${error?.message}`)
  return data.id as string
}
```

### Anti-Patterns to Avoid
- **Reusing `ai_field_proposals` for learning proposals:** conflates two different approval semantics (single-field low/high-stake writes vs. evidence-backed pattern observations). Use a sibling table (Pattern 3).
- **Generating embeddings in the autosave path:** explicitly forbidden by D-04. The synthesis job runs ONLY on publish (+ scheduled catch-up), never on every keystroke/debounce save.
- **An in-process `setInterval`/`node-cron` scheduler inside the Next.js server:** violates the documented single-process/no-PM2-cluster assumption (see `/api/voice/query/route.ts` comment) and doubles up across zero-downtime deploys. Use Railway Cron (separate one-shot service) instead.
- **Hand-editing machine metadata in the UI:** explicitly forbidden by D-10 — the panel is read-only + proposal-actions only; any "edit" affordance on tags/entities/embeddings would silently be clobbered on next publish and is a footgun, not a feature.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Vector similarity search over Postgres | A custom cosine-similarity loop in JS pulling all embeddings client-side | pgvector `<=>` operator inside a `SECURITY DEFINER` SQL function, called via `supabase.rpc()` | PostgREST does not expose pgvector operators directly — the wrapping-function pattern is Supabase's documented approach, and doing the math in Postgres avoids pulling every embedding row over the wire for every query `[CITED: supabase.com/docs/guides/database/extensions/pgvector]` |
| Scheduled job runner | A custom polling loop, or a new background-worker process on Railway | Railway's native Cron Jobs feature | Railway explicitly built this to avoid paying for idle compute and to sidestep in-process scheduler pitfalls; the codebase has zero existing cron infra to extend, so there's no "extend the existing thing" option here anyway |
| Voyage AI HTTP client | Hand-rolled `fetch()` calls against `POST /v1/embeddings` | The official `voyageai` npm SDK (`VoyageAIClient`) | Official SDK handles auth headers, batching (up to 1000 texts/request), and response typing; a hand-rolled fetch wrapper would just reimplement this with more risk of missing edge cases (e.g. `output_dtype`, batch limits) |
| Model-ID hardcoding | Bare string `'claude-haiku-4-5-20251001'` or `'voyage-3'` scattered across files | A single shared constant per model, overridable via env var | CLAUDE.md 2026-06-02 learning — hardcoded model IDs silently rot when the vendor retires the model; the codebase already has 2 precedents (`TTS_MODEL`, `VERIFY_MODEL`) for exactly this pattern |

**Key insight:** Nothing in this phase needs a novel algorithm — every hard part (vector search, scheduling, approval gating, append-only audit tables) already has either a Postgres-native primitive, a platform-native feature (Railway Cron), or an in-repo precedent (00038/00039, X-03 registry) to copy verbatim. The actual engineering risk in this phase is almost entirely in the FOUR SIGNAL SOURCES being real and complete — and one of them (voice Q&A) currently is not.

## Common Pitfalls

### Pitfall 1: Voice Q&A signal source doesn't exist yet
**What goes wrong:** D-06 lists voice Q&A transcripts as signal source #3. The planner assumes a table like `sop_voice_notes` (which exists but is for the *worker's own recorded voice notes* on `VoiceNoteBlock`, not the Q&A assistant transcripts) already captures this. It doesn't — `/api/voice/query/route.ts` computes an answer and returns it directly; nothing is written to any table.
**Why it happens:** `sop_voice_notes` is easy to mistake for "the voice table" because it's the only voice-adjacent table in `database.types.ts`; the actual Q&A route has no persistence step at all (by design — it was built as a stateless request/response endpoint in Phase 15).
**How to avoid:** The plan MUST include a task to add a lightweight append-only write (question, answer, citations, sopId, orgId, timestamp) to `/api/voice/query/route.ts` BEFORE the synthesis job can read this signal meaningfully. Treat this as its own small migration + one-line addition to the existing route, not part of the "read signals" task.
**Warning signs:** If a plan task says "read voice Q&A transcripts from the existing table" without first adding a write path, that task will silently produce an empty/no-op signal source forever — same failure mode as the 2026-06-02 "all-error + zero-cost = infra failure, not no-findings" learning, but here it'd be "zero-rows = never-collected, not no-questions-asked."

### Pitfall 2: Voyage-3 vs Voyage-3.5/4 naming drift
**What goes wrong:** CONTEXT.md D-03 locks "Voyage-3" as a deliberate, reasoned choice. Since that decision was made, Voyage AI's own docs list `voyage-3.5`/`voyage-3.5-lite` as the *current* generation (same 32k context, same or better MTEB scores, same price band) and a `voyage-4` family has since shipped, with bare `voyage-3` retained only for back-compat.
**Why it happens:** Vendor model naming moves faster than a locked planning decision; nobody silently downgrading is good (per the user's own "margin for error is low" framing) but nobody silently missing a strict same-price upgrade is also a miss.
**How to avoid:** Do NOT silently swap the model. Put the exact model string behind `EMBED_MODEL` env-overridable constant (mirroring D-16's Haiku pattern) and flag to Simon in the plan/discuss step which literal string to pin — `voyage-3` (exactly as decided) or `voyage-3.5` (same price, newer). This is Assumption A1 below — it needs a one-line confirmation, not new research.
**Warning signs:** If a plan hardcodes `'voyage-3'` inline in 5+ files instead of one constant, this becomes an expensive multi-file edit the next time Voyage retires a model version (same shape as the `VERIFY_MODEL` 404 incident from 2026-06-02).

### Pitfall 3: pgvector similarity queries silently bypass RLS via PostgREST
**What goes wrong:** PostgREST does not support pgvector's `<=>`/`<->` operators over `.select()`/`.filter()` — a naive attempt to do `supabase.from('sop_agent_metadata').select().order(...)` with a raw vector comparison will fail or silently return unfiltered/wrong results.
**Why it happens:** pgvector operators are Postgres-native SQL syntax, not something PostgREST's query-string DSL can express.
**How to avoid:** Wrap every similarity query in a `SECURITY DEFINER` Postgres function (taking `p_organisation_id`, `query_embedding`, `match_count`) called via `.rpc()` — mirrors the `current_user_sub_trades()`/`sub_trade_id_intersects()` SECURITY DEFINER precedent from migration 00030. The function must filter by `organisation_id` INSIDE its body (SECURITY DEFINER bypasses RLS, same self-enforcement discipline as every service-role write in this codebase).
**Warning signs:** Any plan task that calls `.select()` with a vector column directly (not via `.rpc()`) is structurally broken.

### Pitfall 4: HNSW index build cost + Dashboard query timeout
**What goes wrong:** Supabase's SQL editor / Dashboard has an internal ~2-minute query timeout; building an HNSW index on a large table through the Dashboard can silently fail or hang.
**Why it happens:** HNSW build is compute-intensive relative to IVFFlat, especially before pgvector 0.6+'s accelerated build path.
**How to avoid:** At 50-500 SOPs/org this is a non-issue (tiny table), but build the index via the Supabase CLI migration path (`supabase db push`) or the Management API script pattern already used in this project (per the 2026-06-15 PGRST205 learning) rather than pasting raw SQL into the Dashboard SQL editor for anything beyond a trivial table size.
**Warning signs:** N/A at this scale — flagging for completeness since the phase explicitly targets "up to 500 SOPs/org."

### Pitfall 5: Fire-and-forget synthesis job silently failing forever (same shape as the 2026-06-02 VERIFY_MODEL incident)
**What goes wrong:** A synthesis job triggered fire-and-forget from the publish route can fail on every single invocation (bad model ID, missing `VOYAGE_API_KEY` on Railway, RLS/self-enforcement bug) and the publish flow will never surface this — publish "succeeds" and the dashboard/panel just show permanently empty/stale state.
**Why it happens:** Exactly the pattern already documented in CLAUDE.md 2026-06-02 (`VERIFY_MODEL` 404 for weeks, invisible because the orchestrator wraps everything in try/catch and fails open).
**How to avoid:** Log a distinct, greppable error line on synthesis failure (not silently swallowed); consider a lightweight "last synthesis run: {status, error}" field on `sop_agent_metadata` or an org-level counter so an all-failing state is at least observable from the dashboard itself, not just server logs. `VOYAGE_API_KEY` must be confirmed present on Railway BEFORE the first deploy that ships this feature (same checklist item as the Deepgram key).
**Warning signs:** All-error + zero embeddings-generated after a "successful" publish with no visible error to the admin.

### pgvector similarity RPC wrapper (SECURITY DEFINER, org-scoped inside the function body)
```sql
-- Source: pattern mirrors current_user_sub_trades()/sub_trade_id_intersects()
-- SECURITY DEFINER precedent (migration 00030) + Supabase's documented
-- "PostgREST can't express vector operators, wrap in a function" guidance.
create or replace function public.match_sop_agent_metadata(
  p_organisation_id uuid,
  query_embedding vector(1024),
  match_count int default 10
)
returns table (sop_id uuid, similarity float)
language sql stable security definer
as $$
  select sop_id, 1 - (embedding <=> query_embedding) as similarity
  from public.sop_agent_metadata
  where organisation_id = p_organisation_id  -- self-enforced org-scope, SECURITY DEFINER bypasses RLS
  order by embedding <=> query_embedding
  limit match_count
$$;
```

// Called via .rpc(), never via .select() (PostgREST can't express <=> directly)
const { data } = await supabase.rpc('match_sop_agent_metadata', {

  match_count: 10,
