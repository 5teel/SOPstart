# Phase 26.5: Agent Metadata Layer - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

The **human-invisible per-SOP + per-block machine layer** — semantic tags, entities, embeddings, cross-SOP links, memory, learning proposals, review state — that agents read, write, and traverse individually and collectively. Builds on Phase 23 X-03 (universal AI field read/write via the `FieldDescriptor` registry) + graphify. Delivers the `⚇ Agent layer` surfacing (builder toggle + org dashboard) and the scheduled synthesis job that Phase 26 only wired contract hooks for (26 D-02).

**This phase ships infrastructure + surfacing only** — no flagship user-facing agent capability (cross-SOP summarise/Q&A etc. belong to the conversational phases that follow). But the layer must NOT ship as dead UI: the synthesis job populates memory, assessments, and proposals from real org signals.

</domain>

<decisions>
## Implementation Decisions

### Storage model & granularity
- **D-01 — Dedicated org-scoped tables** are the source of truth (e.g. `sop_agent_metadata` + `block_agent_metadata` + append-only memory/proposal tables). `layout_data` stays FROZEN (26 D-01); agent metadata never rides on props and never touches the editor autosave path.
- **D-02 — SOP + block granularity from day one.** Per-block rows keyed by `sop_section_blocks` junction id — the same identity provenance and verify-state already use.
- **D-03 — Embeddings: Voyage-3 + pgvector.** Chosen deliberately over OpenAI after comparison: retrieval-specialised hard-negative training fits the near-duplicate industrial SOP corpus (LOTO Furnace A vs B), 32k context embeds whole SOPs unchunked. Accepts one new dependency + one new Railway API key (`VOYAGE_API_KEY` — must be set on Railway before deploy, per the Deepgram-key precedent). pgvector via `create extension vector` migration; RLS org-scoping applies. No external vector DB.
- **D-04 — Generate/refresh on publish.** Embeddings + derived metadata (tags, entities, links) regenerate when an SOP version publishes. No autosave-path generation. Drafts keep last published metadata.

### Memory & learning proposals
- **D-05 — Memory scope: per-SOP + org-wide.** Append-only observations tied to a SOP ("workers pause at step 4", "torque value flagged twice") plus org-level conventions ("this org says 'isolation' not 'lockout'").
- **D-06 — All four signal sources feed the layer:** (1) completion data — `sop_completions` + step ack traces (durations, skipped/slow steps); (2) AI-reviewer flags + verify send-back history; (3) voice Q&A transcripts (what workers ask reveals unclear steps); (4) admin edit patterns after AI drafts.
- **D-07 — Learning proposals reuse the X-03 approval path, extended with structured evidence.** Proposals ride `gateWrite` → `pending_approval` → admin review (no parallel approval machinery), but the proposal record carries evidence (source memory rows, signal counts) so admins see WHY the agent proposes a change.
- **D-08 — Memory writes are free append-only** (no approval gate). Memory is observations, not content — it never touches SOP text; only proposals derived from memory go through the X-03 gate. Append-only = auditable.

### ⚇ Agent layer surfacing
- **D-09 — Two surfaces: builder toggle + org-level dashboard, admin/safety-manager only.** (1) The sketch's `agentview` toggle inside the admin builder revealing the purple per-SOP panel + per-block metadata rows over the same canvas; (2) an org-wide agent dashboard. Workers never see the layer.
- **D-10 — Read-only + proposal actions.** Admins inspect tags/entities/links/memory and approve/decline proposals from the panel/dashboard, but do NOT hand-edit machine metadata (it regenerates on publish; hand edits would be overwritten).
- **D-11 — Dashboard = proposals queue + activity feed.** Pending evidence-backed proposals are the primary surface; a recent-activity feed of memory writes and metadata refreshes second. No cross-SOP graph viz this phase.
- **D-12 — Review state = agent assessment per SOP.** Machine-maintained status (e.g. fresh / drifting / needs-review) derived from memory signals (completions slowing, flags recurring, content aging). Distinct from the human verify checklist. Surfaces in the panel + dashboard.

### Phase payoff
- **D-13 — Infrastructure + surfacing only.** No flagship capability (summarise/related-SOPs deferred to conversational phases).
- **D-14 — Scheduled synthesis job included.** A periodic (or on-publish-triggered) agent job reads the 4 signal sources, writes memory, derives per-SOP assessments, and raises evidence-backed proposals. Without it the queue/feed/assessment ship as permanently-empty dead UI.
- **D-15 — Backfill all currently-published SOPs** with a one-off batch job (embed + tag + link) so the layer is useful day one. Cents at 50–500 SOPs/org scale.
- **D-16 — Synthesis model: Claude Haiku 4.5** (`claude-haiku-4-5-20251001`) via the Anthropic SDK already in the project. Shared model constant + env override per the CLAUDE.md 2026-06-02 model-rot learning.

### Claude's Discretion
- Table/schema design (names, columns, memory compaction, retention) — provided append-only memory and junction-id block keying hold.
- Scheduler mechanics on Railway (no cron infra exists — options: on-publish triggers + a lightweight interval runner, or an external cron hitting an authed API route). Must respect the single-process Railway deploy (no PM2-cluster in-memory assumptions per CLAUDE.md).
- Cross-SOP link semantics (similarity threshold, shared-entity links, how graphify's build-time graph relates to runtime DB links — graphify-out/ is a local artifact, not available at runtime).
- Per-org cost guardrails on synthesis/embedding calls.
- Exact assessment states + thresholds (fresh/drifting/needs-review are directional, not locked labels).
- Where the assessment badge appears beyond panel + dashboard (e.g. admin SOP list rows).

</decisions>

<specifics>
## Specific Ideas

- The sketch's agent layer aesthetic is the target: purple `--ai` bordered panel, monospace key/value rows, `⚇` glyph, sticky agent banner when agentview is on — machine-layer-made-visible, clearly distinct from human content.
- Voyage-3 was chosen specifically because the SOP corpus is hard-negative-rich (many near-identical procedures differing only in machine/department/direction) — the user probed this trade-off deeply; don't silently downgrade the provider.
- "Margin for error is incredibly low when working with SOPs" — retrieval quality matters to the user even though embeddings are candidate-generation behind approval gates; keep top-k generous and combine tag-filter + vector search.

</specifics>
