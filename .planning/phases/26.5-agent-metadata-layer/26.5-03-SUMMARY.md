# Phase 26.5 Plan 03: Voice Persistence + Signal Readers Summary

**One-liner:** `/api/voice/query` now writes an append-only `sop_voice_qa_log` row per answer (closing RESEARCH Pitfall 1), and `src/lib/agent-layer/signals.ts` + `similarity.ts` give Plan 04's synthesis pipeline four org-scoped, error-isolated signal readers plus a pgvector RPC wrapper.

## What Was Built

**Task 1:** `/api/voice/query/route.ts` gained `logVoiceQaTranscript()` — called right after `answerSopQuestion()` resolves, inserting `{ organisation_id, sop_id, user_id, question, answer, citations }` into `sop_voice_qa_log` via `createAdminClient()` (the table has no authenticated write policy per migration 00040). `organisation_id` comes from the already-fetched, RLS-verified `sop` row (cast to `SopWithSections`), not a JWT decode. The insert is wrapped in try/catch at two levels (synchronous construction + the promise's `.then` error branch) so a log failure can never change the worker's 200 answer. `voice-qa-persistence.spec.ts` is now live: asserts the insert is wired (table name + `.insert(` + `createAdminClient`), asserts `organisation_id` is set explicitly and `atob(` is never used, and asserts the log call happens strictly after `answerSopQuestion` resolves (call-order check, not just string presence — per the 2026-06-05 source-contract learning).

**Task 2:** `src/lib/agent-layer/signals.ts` exports four async readers + `readAllSignals` + `SignalBundle`:
- `readCompletionSignals` — `sop_completions.step_ack_trace`, aggregated into per-step ack counts.
- `readReviewerSignals` — `parse_jobs.ai_review_results` (typed as `ReviewerRunEnvelope`), aggregated into flag counts by severity; also flags `allRunsErrored` (all `job_status` entries `'error'`) so an all-failing synthesis input is observable rather than silently read as "no findings" (2026-06-02 learning).
- `readVerifySignals` — `sop_section_blocks` verify/override state, scoped through `sop_sections.sop_id` after confirming the SOP belongs to the caller's org (the junction table has no `organisation_id` column of its own).
- `readVoiceSignals` — recent `sop_voice_qa_log` questions for the SOP (the source this plan's Task 1 just made real).

Each reader independently try/catches and returns a neutral empty result + `error` message on failure — one failing source never blanks `readAllSignals`'s bundle (mirrors the ai-reviewer orchestrator's per-job isolation).

`src/lib/agent-layer/similarity.ts` exports `matchSopAgentMetadata(organisationId, queryEmbedding, matchCount)`, calling `.rpc('match_sop_agent_metadata', ...)` — never a raw `.select()` with `<=>` (PostgREST can't express the operator; D-03/Pitfall 3).

`tests/phase26.5/signal-readers.spec.ts` made live: asserts all four table references, all four exported reader names + `SignalBundle`, ≥4 try/catch blocks, and that `similarity.ts` uses `.rpc(` with no vector operator inside a `.select(`.

## Deviations from Plan

**1. [Rule 3 - Blocking] `sop.organisation_id` access surfaced a stale `database.types.ts` gap**
- **Found during:** Task 1
- **Issue:** Reading `sop.organisation_id` directly off the raw Supabase query result (rather than through the existing `as unknown as SopWithSections` cast) triggered `TS2339` — the generated-select type collapsed to `SelectQueryError` because the select string includes `source_type`, a real column (migration 00020) missing from the `sops` Row type in `database.types.ts` (a pre-existing manual-type-extension gap, not something this task's select string caused).
- **Fix:** Read `organisation_id` off the existing `sopWithSections` cast (already used for `answerSopQuestion`) instead of the raw `sop` object — no select-string or `database.types.ts` `sops` edits needed; the broader `source_type` typing gap is out of this task's scope and left as-is (the route's runtime behaviour was never affected — only compile-time property access was).
- **Files modified:** src/app/api/voice/query/route.ts
- **Commit:** a23ce56

**2. [Rule 3 - Blocking] `database.types.ts` Functions map was missing `match_sop_agent_metadata`**
- **Found during:** Task 2
- **Issue:** Migration 00040 (Plan 02) created the RPC live on the DB, but Plan 02's `database.types.ts` extension only added the 5 tables' Row/Insert/Update types, not the corresponding `Functions` entry — `similarity.ts`'s `.rpc('match_sop_agent_metadata', ...)` call would not typecheck without it.
- **Fix:** Added the `match_sop_agent_metadata` entry to the `Functions` map (`Args: { p_organisation_id, query_embedding, match_count? }`, `Returns: { sop_id, similarity }[]`), matching the RPC's real SQL signature from 00040.
- **Files modified:** src/types/database.types.ts
- **Commit:** 2207bb9
