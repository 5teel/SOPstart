## Summary

Phase 26.5 (Agent Metadata Layer) is broadly well-defended: every service-role write in `agent-proposals.ts`, `signals.ts`, and `synthesis.ts` sets/filters `organisation_id` explicitly; the new server actions use `parseJwtPayload` (not `atob`); migration 00040's RLS policies use `current_organisation_id()` directly with zero cross-table references (42P17 class avoided); the sweep route fails closed on missing `CRON_SECRET` with a constant-time compare; agent UI renders all AI-generated text through JSX text nodes (no `dangerouslySetInnerHTML` — no XSS path); `journeys.ts` and `uat/tests.ts` were updated in-phase; and the `tests/phase26.5/**` project regex registers all 9 specs.

Two Critical issues survive: the new pgvector RPC is a cross-tenant read hole (caller-supplied org id, default PostgREST EXECUTE exposure — exactly the class the 00030 helpers avoided by deriving identity from `auth.uid()`), and the publish route — touched by this phase — still carries the raw-`atob` JWT decode that the 2026-06-26 learning documented as a crash class and that this phase's own voice-route test explicitly forbids. Six Warnings cover silent-failure and cost/runaway behaviours in the fire-and-forget pipeline.

The frozen publish-gate contract is intact: steps 1–3 of `publish/route.ts` are untouched; the phase's addition is the additive step 5 `triggerAgentSynthesis` call (never awaited, `.catch` wired).

## Critical Issues

### CR-01: `match_sop_agent_metadata` RPC is callable by any authenticated user with an arbitrary `p_organisation_id` — cross-tenant read

**File:** `supabase/migrations/00040_agent_metadata_schema.sql:222-235` (consumed via `src/lib/agent-layer/similarity.ts:17-30`)
**Issue:** The function is `SECURITY DEFINER` and its only org guard is `where organisation_id = p_organisation_id` — but `p_organisation_id` is a **caller-supplied parameter**, and the migration contains no `REVOKE EXECUTE`. Supabase's default privileges grant EXECUTE on new `public` functions to `anon` and `authenticated`, and PostgREST exposes it at `POST /rest/v1/rpc/match_sop_agent_metadata`. Any authenticated user (a worker in org A) can call the RPC with org B's UUID and any query vector and receive org B's `sop_id`s ranked by semantic similarity — cross-tenant data disclosure. This is precisely the trap the migration's own comment claims to have avoided: the 00030 precedent it cites (`current_user_sub_trades()`) is safe because it derives identity from `auth.uid()` internally and takes **no** caller-supplied identity parameter. `match_sop_agent_metadata` is the first SECURITY DEFINER function in this codebase whose org scope is attacker-controlled input. (Same family as the [2026-06-15]/[2026-06-26] service-role cross-org recurrences — self-enforcement that trusts caller input is not enforcement.)
**Fix:** Follow-up migration — lock the function down to the service role (the only intended caller, per `similarity.ts`):
```sql
revoke execute on function public.match_sop_agent_metadata(uuid, vector, int)
  from public, anon, authenticated;
-- service_role retains access via its default grant; if not:
grant execute on function public.match_sop_agent_metadata(uuid, vector, int) to service_role;
```
Alternatively (belt-and-braces), drop the parameter and derive org internally: `where organisation_id = public.current_organisation_id()` — but since the production caller is `createAdminClient()` (no JWT org claim), the REVOKE approach is the correct one here. Also add `and embedding is not null` to the body (see IN-01).

### CR-02: Publish route still decodes the JWT with raw `atob` — the documented Base64URL crash class, in a file this phase modified

**File:** `src/app/api/sops/[sopId]/publish/route.ts:29-33`
**Issue:** `JSON.parse(atob(session.access_token.split('.')[1]))` — JWT payloads are Base64URL (`-`/`_`, no padding); Node's `atob` throws `InvalidCharacterError` on those characters, so any user whose token payload happens to encode with a `-` or `_` gets an unhandled 500 on **every publish attempt**. This is the exact pattern CLAUDE.md [2026-06-26] documents as fixed across "10+ server callsites" via `parseJwtPayload` in `src/lib/supabase/jwt.ts` — this callsite was missed (or predates the sweep) and this phase edited this file (step 5) without repairing it. The inconsistency is stark: this phase's own `agent-layer.ts:23` imports `parseJwtPayload` and its own test (`voice-qa-persistence.spec.ts:32`) asserts `not.toContain('atob(')` on the voice route — while the publish route, the single most important write path the phase hooks into, keeps the broken decode.
**Fix:**
```ts
import { parseJwtPayload } from '@/lib/supabase/jwt'
// ...
const jwtClaims = session?.access_token ? parseJwtPayload(session.access_token) : {}
const organisationId = jwtClaims['organisation_id'] as string | undefined
```
Per rule #5 ("fix the scope"), grep `atob(` across `src/` in the fix pass — `src/actions/departments.ts`, `blocks.ts`, `auth.ts`, `assignments.ts`, `sections.ts`, `completions.ts`, `flow-graph.ts` all still show raw `jwtClaims['user_role']` decode sites that may carry the same legacy pattern (agent-layer.ts:12 itself calls departments.ts "a legacy instance of the pre-fix pattern").

## Warnings

### WR-01: BuilderClient approve/decline swallow action failures — a failed proposal decision silently disappears from the panel

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/BuilderClient.tsx:139-146`
**Issue:** `handleApproveProposal`/`handleDeclineProposal` optimistically remove the row from state **before** awaiting the action, then ignore the result entirely. If `approveProposalAction` returns `{ error }` (session expired, org mismatch, DB error) the proposal vanishes from the UI but remains `pending` in the DB — the admin believes they approved it; it reappears on next fetch with no explanation. Contrast `AgentDashboardClient.tsx:49-75`, which correctly awaits, checks `'error' in result`, surfaces `actionError`, and only filters on success.
**Fix:** Mirror the dashboard pattern — await first, check the result, only remove on success (and surface an error state on failure):
```ts
async function handleApproveProposal(proposalId: string) {
  const result = await approveProposalAction(proposalId)
  if ('error' in result) { /* set an error state / toast */ return }
  setSopProposals((prev) => prev.filter((p) => p.id !== proposalId))
}
```

### WR-02: No proposal dedupe — every synthesis run re-raises the same pending proposals

**File:** `src/lib/agent-layer/synthesis.ts:243-290` (`raiseProposalsFromSignals`), `src/lib/ai-fields/agent-proposals.ts:78-92`
**Issue:** `createLearningProposal` inserts unconditionally; there is no check for an existing `pending` proposal of the same `(sop_id, kind)`. The conditions ("critical flags > 0", ">50% unverified") persist across runs, and synthesis runs on every publish, every backfill invocation, **and every 5-minute sweep hit** (any new completion/voice row makes the SOP "stale"). A busy SOP with one lingering critical flag accrues a duplicate `reviewer-critical-flags` pending proposal per run until an admin declines them one by one — the dashboard's primary queue (D-11) degrades into noise, and `MAX_PROPOSALS_PER_RUN` caps per-run volume only, not accumulation.
**Fix:** In `raiseProposalsFromSignals` (or inside `createLearningProposal`), skip insert when a pending row already exists:
```ts
const { data: existing } = await admin.from('agent_learning_proposals')
  .select('id').eq('organisation_id', organisationId).eq('sop_id', sopId)
  .eq('kind', kind).eq('status', 'pending').limit(1)
if (existing?.length) return
```
(Or a partial unique index `on (sop_id, kind) where status = 'pending'` + upsert-ignore.)

### WR-03: Sweep starvation and infinite retry — unordered 100-row candidate window plus error rows that never leave the stale set

**File:** `src/app/api/agent-layer/synthesis-sweep/route.ts:61-85`; `src/lib/agent-layer/synthesis.ts:344-355`
**Issue:** Two compounding defects. (1) `findStaleSops` selects published SOPs with `.limit(100)` and **no `.order()`** — with more than 100 published SOPs platform-wide (the stated target is 50-500 per org, multi-tenant), the candidate window is an arbitrary, roughly-fixed subset; SOPs outside it are never evaluated and never swept. (2) The error path in `synthesizeSop` upserts `last_synthesis_status: 'error'` but **omits `regenerated_at`** — a persistently failing SOP (bad content, revoked key mid-run, oversized doc) stays `regenerated_at IS NULL`, is classified stale forever, and is retried on every 5-minute cron tick: it permanently occupies one of the 20 `MAX_SOPS_PER_SWEEP` slots and re-bills Voyage/Anthropic attempts indefinitely. Twenty such SOPs deadlock the sweep entirely.
**Fix:** (1) Add a deterministic rotation, e.g. `.order('updated_at', { ascending: false })` or paginate by `id`. (2) Set `regenerated_at: new Date().toISOString()` on the error-path upsert too (the attempt *was* the regeneration; `last_synthesis_status='error'` already records that it failed), or have `findStaleSops` skip candidates whose `last_synthesis_status === 'error'` and are younger than a backoff window.

### WR-04: `allRunsErrored` is vacuously true for envelopes with missing/empty `job_status` — false 'needs-review' assessments

**File:** `src/lib/agent-layer/signals.ts:123-125`
**Issue:** `runs.every((run) => Object.values(run.job_status ?? {}).every((s) => s === 'error'))` — `Array.prototype.every` on an empty array returns `true`, so a run whose envelope lacks `job_status` (older/legacy `ai_review_results` shapes, or a malformed envelope that still passed the `Array.isArray(r.flags)` filter) counts as "all jobs errored". If every stored run for an SOP has that shape, `allRunsErrored === true` → `deriveAssessment` returns `'needs-review'` (synthesis.ts:91) and a false "All AI reviewer runs errored" memory observation is appended on every run — the exact inverse of the 2026-06-02 lesson (this flag exists to distinguish infra failure from no-findings; here it manufactures a fake infra failure).
**Fix:** Require a non-empty `job_status` before a run can count as errored:
```ts
runs.every((run) => {
  const statuses = Object.values(run.job_status ?? {})
  return statuses.length > 0 && statuses.every((s) => s === 'error')
})
```

### WR-05: Backfill script reports `OK`/`sopsProcessed` for runs that failed — its FAIL branch is dead code

**File:** `scripts/backfill-agent-metadata.mjs:103-113`
**Issue:** The loop wraps `await synthesizeSop(...)` in try/catch and counts `sopsSkipped` on throw — but `synthesizeSop` **never throws**: it catches everything internally and records `last_synthesis_status='error'` (synthesis.ts:339-359). So the `FAIL` branch is unreachable, every SOP prints `OK`, and a backfill run with an invalid `VOYAGE_API_KEY`/`ANTHROPIC_API_KEY` (or 100% DB write failures) ends with a summary claiming full success — the [2026-06-02] "all-error run is invisible" failure mode reproduced in the one tool whose whole job is a verifiable one-off pass.
**Fix:** After each call, read back the status and report truthfully:
```js
const { data: meta } = await admin.from('sop_agent_metadata')
  .select('last_synthesis_status, last_synthesis_error').eq('sop_id', sop.id).maybeSingle()
if (meta?.last_synthesis_status === 'ok') { sopsProcessed++; console.log(`  OK    ${sop.title}`) }
else { sopsFailed++; console.error(`  FAIL  ${sop.title}: ${meta?.last_synthesis_error ?? 'no metadata row written'}`) }
```
Exit non-zero when `sopsFailed > 0` (or when all failed).

### WR-06: Agentview fetch chain has no `.catch` — offline/failed loads show "No synthesis run yet" with an unhandled rejection

**File:** `src/app/(protected)/admin/sops/builder/[sopId]/BuilderClient.tsx:118-137`
**Issue:** `Promise.all([...]).then(...).finally(...)` — if any of the three server-action calls rejects at the transport level (this is an offline-first app; the builder even tracks `isOnline`), the `.then` handler is skipped, the rejection propagates unhandled, and the panel silently renders the "No synthesis run yet for this SOP" empty state — indistinguishable from genuinely-unsynthesised. Server actions returning `{ error }` are likewise mapped to the same empty state (lines 125-129) with the error string discarded.
**Fix:** Add `.catch(() => { if (!cancelled) setSopAgentData(null) /* + set an agentError state */ })` before `.finally`, and surface `sopRes.error` in the panel instead of conflating it with "no data".

## Info

### IN-01: `matchSopAgentMetadata` is dead code this phase, and the RPC returns null-similarity rows

**File:** `src/lib/agent-layer/similarity.ts:17`; `supabase/migrations/00040_agent_metadata_schema.sql:230-234`
**Issue:** `matchSopAgentMetadata` has zero callers in `src/` (links are always upserted as `[]`; no consumer ships this phase). Additionally the RPC body doesn't exclude `embedding IS NULL` rows — when fewer than `match_count` embedded SOPs exist, rows with `similarity = null` pad the result set.
**Fix:** Acceptable as deliberate D-13 infra-only scaffolding, but add `and embedding is not null` to the function body when fixing CR-01 (same follow-up migration).

### IN-02: `readVoiceSignals.totalQuestions` is capped at 20 by the query limit but reported as a total

**File:** `src/lib/agent-layer/signals.ts:174-186`; surfaced at `src/lib/agent-layer/synthesis.ts:216-223`
**Issue:** `totalQuestions: data?.length ?? 0` after `.limit(20)` — an SOP with 300 logged questions produces the memory observation "20 worker voice questions logged for this SOP".
**Fix:** Use a `head: true, count: 'exact'` count query for the total, keep the limited fetch for `recentQuestions`.

### IN-03: `embedBlocks` embeds raw `JSON.stringify(snapshot_content)`, including the literal string `"null"`

**File:** `src/lib/agent-layer/synthesis.ts:159-169`
**Issue:** `JSON.stringify(null)` → `"null"`, which passes `!text.trim()` and burns a Voyage call to embed the word "null"; non-null blocks embed JSON syntax/keys/ids rather than content text, diluting embedding quality.
**Fix:** `if (block.snapshot_content == null) continue` and consider extracting text fields rather than embedding raw JSON.

### IN-04: `approveProposal`/`declineProposal` never set `reviewed_by` despite the schema providing it

**File:** `src/lib/ai-fields/agent-proposals.ts:107-130`; caller has the id at `src/actions/agent-layer.ts:231-263` (`ctx.user.id`, unused)
**Issue:** `agent_learning_proposals.reviewed_by uuid references auth.users(id)` (00040:155) is always NULL — no audit trail of *which* admin decided, only when. In a safety-compliance product, decision attribution matters.
**Fix:** Thread `ctx.user.id` through: `approveProposal(orgId, proposalId, reviewerId)` → include `reviewed_by: reviewerId` in the update.

### IN-05: Tag chips keyed by tag value — duplicate AI-generated tags collide React keys

**File:** `src/components/admin/builder-v2/agent/AgentPanel.tsx:68-72`; `src/components/admin/builder-v2/agent/AgentBlockMeta.tsx:50-54`
**Issue:** `key={t}` — `extractTagsAndEntities` takes Haiku's `tags` array verbatim with no dedupe; a duplicate tag produces duplicate React keys (console warning, potential mis-render).
**Fix:** Dedupe at write time in `extractTagsAndEntities` (`[...new Set(parsed.tags)]`) — fixes both the render and the stored data.

### IN-06: `loadPublishedSop` does not filter `status = 'published'` despite its name and docs

**File:** `src/lib/agent-layer/synthesis.ts:60-80`
**Issue:** Both current callers pre-guarantee published status (publish route runs post-transition; sweep/backfill filter on `status='published'`), but the function itself would happily synthesize a draft if a future caller passes one — and the D-04 contract is publish-triggered-only.
**Fix:** Add `.eq('status', 'published')` to the query so the invariant is self-enforced, not caller-trusted.
