# v9.0 Dev Plan — Hot End Pilot

_Drafted 2026-08-25 from the Joe + Simon working session (2026-08-04) and the v9.0 scoping pass (paused 2026-08-08 at D3). Source decisions: `.planning/.continue-here.md`, decision artifact `6de44250`._

## What the milestone is

Ship the hot end department (Grade Two Operator → Grade One Operator → Wear Maker) as the pilot for role-based SOP permissions, then roll out horizontally. Everything downstream of Joe's data.

## Locked decisions (from the meeting + D1/D2)

- Hot end only this milestone; three roles, ~12 SOPs each, SOPs cumulative up the ladder.
- **Inheritance is visibility-only** — the role ladder never confers training obligation; obligation is manager-set.
- Self-adding a SOP is a bookmark, never an obligation.
- Separate SOPs for operators vs engineers (no shared SOP with role-filtered content).
- Sign-off authority ⇒ edit rights.
- All block edits logged with user + timestamp.
- Feedback: tab at bottom of SOP → email to sign-off manager → read-only visible to everyone with access.
- AI voice drafting stays available, not a priority (no work this milestone).
- Keep it simple — remove features that add complexity rather than adding scaffolding.
- **D1 = C**: Phase 44 split into 44a (obligation record) → 44b (role ladder). The training matrix currently derives required SOPs from *access* tables (`competency.ts:332-343`); shipping the ladder first would flood every senior worker's overdue list. 44a repoints the matrix first; backfill obligation = today's access so no existing matrix moves.
- **D2 = B**: 44a + 46 run now, in parallel with v8.0 Phase 41 (no route collisions). 45 waits for 41.
- **D3 = B (linked), generalised** *(Simon, 2026-08-25)*: not one universal start/end pair — a **Standard Steps library**: org admins create any number of standard steps (start/end sequences, hazards, PPE), and each SOP links the subset that applies. Edit the library source once → every linked SOP updates. Many SOPs share the same steps; none are forced to.
  - Implementation direction: extend the existing `blocks` library + `sop_section_blocks` junction with by-reference semantics (linked, not copy-on-insert) rather than a new entity.
  - **Open sub-question (resolve at 49 planning):** when a linked step changes, do published SOPs silently update or drop back to needs-re-verification? Interacts with the per-block verify checklist and publish gate.
- **D4 = C** *(Simon, 2026-08-25)*: worker feedback is removable only by the sign-off manager + admin, with every removal logged. Matches who receives the feedback email; the log preserves defensibility.
- **D5 = B** *(Simon, 2026-08-25)*: SOP edit history is visible read-only to everyone with access to that SOP — same transparency model as feedback.
- **A1 = approvers** *(Simon, 2026-08-25, post-Phase-46)*: "sign-off authority" = the SOP's category **approval-chain approvers** (Phase 29 `approval_chains` steps, matched by userId or role), NOT the single `sops.owner_user_id`. CAP-02's edit-rights grant follows the chain; a SOP whose category has no chain is editable only by admin/safety_manager (accepted consequence). Feedback email routing (FBK-02, Phase 48) should follow the same definition.
